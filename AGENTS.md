# TeamCode contributor instructions

- All repository content must be English. Root package and Gradle group: `me.nathanfallet.teamcode`.
- Squash-merge pull requests; do not create merge commits or rebase-merge PRs.
- Remove temporary diagnostic branches and their clean, owned worktrees when the investigation is finished; preserve findings and verification evidence in the pull request description.
- There is no V1/V2 split any more: `main` is the current product and all of it is in scope. It ships the gateway (pooled Claude Max and Codex accounts, quotas, routing, forecasts, dashboard), the native CLI, TeamCode Desktop and the companion apps (`companion`, `companion-android`, `companion-desktop`, the iOS shell in `companion-ios/`), Kubernetes cloud sessions and remote sessions hosted on a member's device (`teamcode cloud`, `teamcode remote`, the runner `teamcode cloud runner`), the MCP gateway (one `/mcp/<server>` endpoint per server) with the hosted-stdio host (`mcp` module), environment/MCP variants, team hooks, the skill catalog (server side), artifacts, service keys and webhooks. Each feature page under `docs/` (`cloud-sessions.md`, `mcp-gateway.md`, `mcp.md`, `variants.md`, `hooks.md`, `skills.md`, `artifacts.md`) records what is implemented and what is planned; check it against the code and correct it in the same PR when your change makes it wrong.
- Still planned, not implemented (the authoritative list is the "What is planned" section of each feature page; these are the main items): synchronizing assigned skills into the local agent before `teamcode run` (`docs/skills.md`, "What is planned"), reporting team-hook approval status to the server and Codex cloud sessions running team hooks (`docs/hooks.md`), a member-driven delegated OAuth flow for MCP servers (`docs/mcp-gateway.md`), group decisions for skills and hooks, and open-source model providers. Cross-provider translation exists but is experimental and off by default (`experimentalCrossProviderTranslation`). Many pages under `docs/` (at least `roadmap.md`, `progress.md`, `v1-review.md`, `v2-validation-handoff.md`, `product.md`, `testing.md`, a few sentences of `skills.md`) and the README introduction still use the old V1/V2 wording and predate these features: read that wording as history, and trust the code first, then the feature pages' status tables.
- Work in your own worktree and branch. Do not modify, merge or delete another agent's or person's worktrees and branches.
- Standalone public project. No ControlResell dependencies, registries, secrets, infrastructure or CI.
- Use TeamClaude as the behavioral reference. Before implementing account enrollment, provider routing, agent launchers or service integration, inspect the corresponding implementation and regression tests in the sibling `teamclaude` checkout. Reuse its established behavior where applicable; document adaptations required by native Kotlin, team authorization or shared persistence. Do not invent a parallel mechanism without first checking the reference.
- Keep `cli -> client -> api`, with `config` shared by `cli` and `companion-desktop`, `companion -> client`, `companion-android -> companion` and `companion-desktop -> companion + config + client`. The CLI and the companion apps must never depend on server domain or infrastructure modules.
- Server layers: `app -> presentation + infrastructure + domain + api`; `presentation -> domain + api`; `infrastructure -> domain`. Domain and API do not depend on other project modules. `mcp` (the stdio host) depends on `api` only. `python3 scripts/check-module-graph.py` enforces all of this, the Exposed-only query rule and the companion's layering; CI runs it.
- Use the Exposed DSL for all database queries, mutations and locks, including test fixtures. Do not write raw SQL or call `exec` with SQL strings. Keep HikariCP for connection pooling and Flyway for migration execution; generate new migrations from Exposed table definitions and review their output. Preserve already-published Flyway migrations unchanged.
- Every new or changed query on a request path (gateway, admission, dashboard reads, polling loops) needs `EXPLAIN ANALYZE` evidence in its PR, run on MySQL 8.4 with a table seeded to production scale (hundreds of thousands of `reservations` rows, not an empty schema). Paste the plan before and after, and add or adjust an index when it shows a filter applied after an index lookup, a table scan or a temporary table. Queries that run inside the team lock or on every polling tick count by cost times frequency, not per execution.
- No N+1: never call a store or service method per row from a list, dashboard page or loop (`people.map { store.read(it.id) }`); add a batch method that reads everything in one transaction with `inList`/joins, and share what the rows have in common (group, pool or team aggregates) instead of recomputing it per row. A page load should cost a small, fixed number of transactions regardless of team size; state that number in the PR. Also avoid unbounded selects (always `limit`), `COUNT(*)` where `exists`/`limit(1)` is enough, `OFFSET` pagination (use keyset), fetching large text/blob columns on list endpoints, and holding a transaction (or the team lock) across a network call.
- Prefer indexes that match the filter order (equality columns first, then the range or sort column); a filter that the plan applies after the index lookup means the index is missing a column.
- Put business rules in use cases and services, never in HTTP routes or CLI commands. Use constructor injection and Koin in the server composition root.
- Native CLI: no JVM at runtime. Test the actual native binary; JVM tests alone do not validate TLS, streaming or process behavior.
- Build with JDK 21 and the checked-in Gradle wrapper. CI (`.github/workflows/build.yml`) is the authoritative list of commands: the `jvm` job runs the module tests with `./gradlew :api:jvmTest :client:jvmTest :domain:test :infrastructure:test :presentation:test :config:jvmTest :cli:jvmTest :app:test :mcp:test :app:buildFatJar :mcp:buildFatJar` (and more), the `companion` job the companion and desktop tests. Other checks are the `scripts/smoke-*.py` scripts and `docs/testing.md`.
- Do not run overlapping Gradle tasks concurrently in the same checkout/output directories. Batch them in one invocation or use isolated owned worktrees.
- Never log credentials, prompts or response bodies. The only exception is the initial administrator temporary password, printed once after first-run creation commits, as explicitly requested by the project owner. Never print it again on restart. No real provider calls in normal tests or PR CI.
- Extend providers through `ProviderTransport` and `OAuthEnrollmentProvider`; extend incoming HTTP formats through `InboundProtocol` and request/stream formats through `ProtocolAdapter`. Keep team policy and account selection shared. Document capability limits and test real protocol fixtures before claiming support.
- Preserve coroutine cancellation. Bound request bodies, queues, retries and network waits. Never replay a stream after committed output.
- Put verification evidence in the pull request description, not in a shared log file. Do not add a shared status or changelog file that every PR edits: it puts all waiting PRs in conflict at each merge. Never present a planned command as implemented.
- Never stop processes or Gradle daemons started by someone else. Never kill by process name.

- Keep ordinary push/PR CI on Linux (JVM, Helm and Docker). Paid native matrices, including every macOS job, run only on version tags or explicit manual `full_validation=true`. Batch native changes before requesting that matrix; do not dispatch it per commit. Keep full native acceptance mandatory for versioned CLI releases.
