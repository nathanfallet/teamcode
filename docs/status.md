## Live agent text, sessions waiting for a person, cut events keeping their identity (2026-10-23)

Three additions to the cloud session API for clients that show a session as it runs ([contract](cloud-conversations.md)):

- **Live text** (`cloud.transcript.live.v1`). With `liveText` from `POST /cloud/runner/agent`, the runner starts Claude Code with `--include-partial-messages` and turns its `text_delta` lines into `message.agent.delta` events `{messageId, index, text, parentToolUseId?}`, coalesced per block (500 ms, about 2,000 characters, or the block's end). `message.agent` now carries `messageId` and, for a streamed block, `index`: it replaces that block's deltas, and no delta of the block follows it. Thinking and tool input are never streamed; an interrupted turn's held text is dropped. `logs` and `attach` print final messages only; the companion app ignores the type. Codex is unchanged. Behavior checked locally against Claude Code 2.1.309 (the image pins 2.1.306): one `assistant` line per content block, carrying the API message id, written before that block's `content_block_stop`; `stream_event` lines carry `api_message_id` and `parent_tool_use_id`.
- **`waiting` on the session view** (`cloud.sessions.waiting.v1`): `{reason, requestId?, since, eventSeq}` while a permission request is open, the newest when several are, the next one still open when it closes. Stored on `cloud_sessions` (migration `V20261023230000.2`, five nullable columns) in the transaction of the transcript event or the answer's acknowledgement that changes it, under the session row lock already held; the session store clears it when the session stops taking answers. Read with the session row: no extra query per session in a list.
- **Cut events keep their identity**: the `{truncated, originalBytes}` marker of an event above 60,000 bytes keeps `id`, `parentToolUseId`, `toolUseId`, `requestId`, `messageId`, `inputId` (strings of at most 128 characters), `name` (200), `isError` and `index`.

Evidence: `CloudAgentTest` (live text, the host's clock, logs skipping deltas), `CloudTranscriptSanitizerTest`, `CloudHumanWaitTest`, `CloudConversationRoutesTest` (capabilities, `liveText`, `waiting` in a read and a list), `CloudConversationPersistenceTest` (MySQL 8.4: migration drift, `waiting` across answers, expiries, turn ends, a pause and session writes, deltas stored).

## Shared local configuration module (2026-10-23)

The CLI's local configuration moves into a new module, `:config` (Kotlin/Native for the CLI's five targets and JVM for the desktop app): the path of `config.json` (`XDG_CONFIG_HOME`, else `~/.config`), its format and validation, `installation-id` (created without replacement) and a new advisory lock, `config.lock`. The lock is a POSIX record lock (`fcntl`, the lock the JVM's `FileChannel.lock` takes, so the native CLI and a JVM app exclude each other) or `LockFileEx` on Windows, held by login, logout and `teamcode configure` around their read-modify-write and never across a network call; a command waits up to 10 seconds, then refuses, and the file is never deleted to guess that a holder died. Login revokes the session its new configuration replaced; logout removes the file only if it still holds the session it revoked. Private writes stay behind an interface: the CLI's native writers (0600/0700, protected DACL through the Windows interop) are unchanged, and the module adds the JVM writer the desktop app needs, POSIX permissions or, on Windows, an owner-only ACL entry for the token user (a path owned by someone else or a reparse point is refused). `scripts/check-module-graph.py` knows `cli -> config`.

Evidence: `ConfigurationTest` and `ConfigStoreTest` (format unchanged, unreadable file named without its content, replace and conditional delete, a second acquisition refused after its timeout, installation identity) on the JVM and macOS ARM64; `JvmPrivateFilesTest` (0600 file in a 0700 directory, a symbolic link never followed, create never replaces, 8 concurrent writers leave one complete content and no temporary file, 8 concurrent creators agree on one identity); `JvmConfigLockTest` (threads take the lock one at a time; another JVM holding it makes this one wait then refuse, and the lock is free once it exits); `PosixConfigLockTest` (a forked process sees the lock while held and not after; the lock file is `0600`). `:cli:jvmTest` and `:cli:macosArm64Test` pass; the CLI compiles for Linux x64 and Windows x64, and the module's Windows tests compile. Not run locally: the Windows paths (the module's native tests and its JVM tests on Windows run in the tag and full-validation `windows` job).

## Cloud resume in a new pod, proven on kind (2026-10-23)

`scripts/smoke-cloud-kind.py` (opt-in, not in pull-request CI) now also proves, on a real kind cluster with two server replicas (separate connection pools, stores, cluster clients and reconcilers over one MySQL 8.4), that a paused session resumes in a new pod: pausing leaves no pod labelled with the session while keeping its claim; two concurrent resume requests, one through each replica's service (at least one accepted, the other accepted or refused with a conflict), end with exactly one pod, `tc-<id>-e2`, whose Kubernetes `metadata.uid` differs from the first pod's, on the same claim and PersistentVolume; the cluster's TokenReview of a token bound to that pod returns the new UID and the token authenticates as epoch 2; and 15 more rounds of both reconcilers leave one pod, never deleted and recreated (same UID), and one execution per epoch. A second creation attempt of the same pod name would be refused by Kubernetes, so the proof is the unchanged UID, the epoch and the execution rows, not a count of creation calls. Kind imports images by tag only, so the script also names the imported image by its digest on the node, as a registry pull would, because a resumed session pins the digest of its first pod. Both replicas run on parallel threads; replica 2 reconciles and takes one of the two resume requests, while the runner calls, token review and cluster reads of the assertions go through replica 1. Local evidence, 2026-10-23: the run passes with no failed reconciliation round. Not covered: process memory or agent continuation (the runner is a stand-in) and creation through the HTTP API and CLI, which `CloudRoutesTest` and the CLI tests cover without a cluster.

## Queue turns only apply when someone is limited (2026-10-22)

Production (0.6.6, `(last wait: queue_turn)` on all 62 `queue_timeout`): 35 waiters in `admission_waiters`, about 20 from one session, every member at `max_concurrent = 0`, pool budget 20 billion. Every waiter had a free account but only the ticket holding the turn could take it, and the next turn was taken only when that ticket polled again (0.5 to 2 s), so a burst of parallel requests drained one per round and the tail hit the 90 s limit. `consumeQueueTurn` now enforces the turn only when a waiter in the scope has a member concurrency limit (`max_concurrent > 0`); without any limit a free account admits every ready waiter in the same round, while the turn counter still rotates. Run and group concurrency keep working as before: such waiters are marked blocked and are not candidates. Test: `QueueTurnWithoutLimitPersistenceTest` (no limit: four waiters admitted in one round; one limited member: the turn order is back).

## `queue_timeout` names what the request was waiting for (2026-10-22)

On the 0.6.4 replicas (5 pods, 5 minutes up) 29 requests timed out after 90 s with no way to tell why: waiting hides the refusal that caused it (`member_concurrency`, `queue_turn`, `pacing_delay`...). 194 of 201 dispatches went to one account. The 503 message and the server log line now end with `(last wait: <code>)`, so the next errors say whether a member's concurrency limit, another member's turn or pacing holds the queue.

## Admission queue polls less the longer it waits (2026-10-22)

Every queued request polled every 500 ms, each poll a team-locked transaction (`reserveQueued`, about 20 queries) plus a `renew` that recomputed account placement. With up to 128 waiters this saturated the connection pool and starved dashboard reads; in production 3 h of logs showed p90 admission waits of 68.6 s and `queue_timeout` 503s. Now the first 4 polls stay at 500 ms (a freed slot is still taken quickly), then 1 s up to attempt 10, then 2 s, with +-20% jitter (`AwaitAdmissionUseCase.pollDelay`), and the queue scope (`renew` with placement) is refreshed every 4th attempt instead of every one; the lease is still renewed on each. A long-waiting request now costs about a quarter of the transactions. Not done: waking waiters when a reservation settles (a freed slot on another replica can wait up to 2 s) and a lock-free pre-check; measure the p90 wait and the `queue_timeout` count after release before going further.

## Dashboard overview and capacity pages: one transaction for all members (2026-10-22)

Both pages called `AdmissionStore.capacity` once per member: one transaction of about a dozen queries each, N sequential connection checkouts, and the same group aggregates recomputed for every member. On a 400,000-row `reservations`/`reservation_groups` fixture, the per-group daily spend (`readGroupUsage`) alone took 24.8 ms for a group-day of 4,445 rows, and was repeated per member and per group. `AdmissionStore.capacities` now reads all members in one transaction and computes each group's usage and each pool's total weight once (`CapacityReadCache`); the default implementation keeps other stores working. Checked by `FairSchedulingHttpTest` (batch equals one-by-one). Other findings of this audit: all other list/detail queries examined use an index matching their filter order (agent runs, audit events, quota history, cloud sessions, token usage); `AGENTS.md` now states the N+1 and index-order rules.

## Query audit of the admission and dashboard paths (2026-10-22)

Production symptoms: dashboard pages taking seconds, `503 queue_timeout` after 90 s even in observation-only mode. Logs of the two production replicas over 3 h: 538 admissions, p50 wait 5.6 s, p90 68.6 s, max 92 s; every 503 was `queue_timeout`. Observation-only only disables pacing directives; it does not skip the admission queue.

Measured with `EXPLAIN ANALYZE` on MySQL 8.4 seeded with 400,000 `reservations` rows (20 members, 90 days):

- Fixed here: the member "active requests" count in `readMemberCapacity` (and the same filter elsewhere) matched `member_daily (member_id)` and filtered `state`/`expires_at` afterwards, reading all 37,104 rows of the member (68 ms). New index `member_active (member_id, state, expires_at)` turns it into a range scan.
- Not fixed, needs a decision: every queued request polls every 500 ms (`AwaitAdmissionUseCase.POLL_MILLIS`) and each poll runs `reserveQueued` (about 20 queries under `lockTeam`) plus `renew` (`lockTeam` and `accountPlacement` again). With up to 128 waiters per team that is hundreds of team-serialized transactions per second against a pool of 8 connections (`Database.kt`, `connectionTimeout` 5 s). Dashboard reads and settlements queue for a connection behind them. Candidates: backoff with jitter on the poll, waking waiters when a reservation settles, a cheap pre-check before taking the team lock, a configurable pool size.
- Also changed here: the connection pool per replica is `TEAMCODE_DATABASE_POOL_SIZE` (default 16, was a fixed 8 since the first commit) and the chart defaults to 3 replicas (was 2): 48 connections against MySQL's 151, with room for a rolling-update surge. More connections let dashboard reads stop queueing behind admission transactions; they do not remove the team lock, so the polling change above is still the real fix.
- `poolSpends` (11.5 ms for 7,680 rows of one pool-day) runs on every poll; keep an eye on it as traffic grows.

## Pacing without a concurrency ceiling (2026-10-21)

Supersedes the progressive slow-down sizing below. On 2026-10-21 production directives were `SLOW_DOWN`, one request, 10 s for every active member: each account's seven-day window was graded as overshooting because a one-hour burn rate was extrapolated over a reset six days away (13% weekly projected to 95% in about 55 h). Admission enforced the concurrency, the per-member queue cap of 8 filled and agents got `queue_full`/`queue_timeout` 503. Pacing now only spaces admissions (light 2 s, moderate 5 s, severe 10 s, PAUSE 30 s); its concurrency is the member, group or launch limit, zero for none, and admission no longer refuses on a directive's concurrency. The per-account judgment is replaced by a projection of the team's current burn rate over the remaining capacity of every usable account (`AccountHeadroomUseCase` from the raw token ledger work), accounts sorted by reset, five-hour and seven-day windows together: pacing slows down only when every account is projected to run out before a reset gives some capacity back, graded by that gap's length and proximity (see [capacity](capacity.md#forecasting)). Replayed on the production observations of 17:50Z, the three usable accounts last about eleven hours at the team's weekly rate and the exhausted one returns in 24 hours: a moderate 5 s spacing instead of one request every ten seconds. The per-member queue cap applies only to members with a concurrency limit; unlimited members are bounded by the team queue of 128. Every inference refusal is logged (`TeamCode inference refused member=… code=… status=… reason="…"`), and admissions that waited at least 1 s log `waitedMs`.

Evidence: `CapacityProjectionTest` (the case table: a single account with headroom, an exhausted account bridged until its reset, levels by gap length and proximity, staggered five-hour and seven-day resets, both windows binding, exhausted and disconnected accounts, an account without data, a zero rate, a brief peak, no usable account, a past reset, exact boundaries, hysteresis, the production replay), `AccountHeadroomTest` (exhausted accounts listed apart), `ProgressivePacingTest` (spacing without a ceiling at every level and in PAUSE), `ProgressivePacingPersistenceTest` (a sixth parallel request in a slowed session is admitted once the interval has passed), `AdmissionQueuePersistenceTest` (an unlimited member queues nine requests), `PoolGatewayTest` (refusal log format) and `StatusRenderTest` (`no concurrency cap`).

## Unlimited member concurrency and progressive slow-down (2026-10-21)

A member's concurrent request limit now defaults to zero, meaning unlimited; administrators can still set 1 to 32 (`member_policies.max_concurrent DEFAULT 0`). Saved policies are not rewritten on upgrade. Without a limit, NORMAL, CAN_INCREASE and UNKNOWN pacing admit parallel requests immediately, bounded only by group/launch limits. The limit of two active requests per physical account is removed for every provider (Claude and Codex): placement still prefers the least loaded account but never refuses or queues because an account is busy (`pool_busy` is no longer raised), and only quota pacing slows an account down. Conversation pins now hold for as long as their account stays eligible (no spill when busy, no priority preemption); only a relevant window at the quota pressure threshold (95% by default), disablement, cooldown, reconnect, exclusion or a pool change moves one, and the one-hour hint lifetime is unchanged. SLOW_DOWN is now progressive: the affordable share of the current burn rate before reset selects light (half the observed parallelism, 2 s gap), moderate (a quarter, 5 s) or severe (one request, 10 s). ## Skill pin on publication (2026-10-21)

## Skills and hooks for all members (2026-10-23)

A skill or a team hook can be delivered to **all members** instead of only to members set to *Yes*: every member without an explicit decision receives the pinned version, including members who join later, and an explicit *No* still excludes a member (`SkillAccessPolicy`: member decision, then groups, then the audience). An administrator sets the audience on the skill's or hook's page or with `PUT /api/v1/skills/{name}/audience` / `PUT /api/v1/hooks/{name}/audience`; a publication sets it with `"allMembers": true`, idempotently, in the publication's transaction. For skills, a key needs the new administrator-only `skills:assign` scope besides `skills:publish`, so a leaked publishing key cannot widen who receives a skill. For hooks, no new scope: a `hooks:publish` key may ask for it only while the hook has no pinned version (the interactive pin then approves the code and its audience together) and is refused with `403 hook_audience_requires_administrator` on a pinned hook. Changing the audience afterwards is interactive only. Audit: `skill.audience.*` and `hook.audience.*`, with the key's `credentialId`. Capabilities `team.skills.all-members.v1` and `team.hooks.all-members.v1`. Migration `V20261023191500` (Exposed-generated, one `BOOLEAN DEFAULT FALSE` column on `skills` and `hooks`; existing items keep their per-member delivery). No new query: the audience is read from the catalog row the delivery and catalog queries already select. See [skills](skills.md#delivering-to-all-members) and [team hooks](hooks.md#delivering-to-all-members).

Evidence: `SkillCatalogTest` (precedence with the audience, delivery to members without a decision, `skills:assign` required on keys, audience changes interactive only), `HookCatalogTest`, `SkillRoutesTest` and `HookRoutesTest` (transport refusals, `PUT .../audience` closed to every key, dashboard form behind CSRF, capability), `SkillPersistenceTest` and `HookPersistenceTest` (MySQL 8.4, two pools: the migration matches the Exposed tables, a member created after publication receives the item, an explicit *No* wins, retries append no event, `skills:assign` refused on a non-administrator's key, a hook key refused on a pinned hook with nothing stored, one audit event per change carrying the key's `credentialId`).

## `accounts add` asks for the account type (2026-10-23)

`teamcode accounts add` first shows a numbered selector, as TeamClaude's login does: 1) Anthropic subscription (Claude Pro, Max, Team, Enterprise), 2) Codex subscription (ChatGPT Plus, Pro, Team), 3) Anthropic API key (Claude Console, console.anthropic.com). `--type anthropic-subscription|codex-subscription|anthropic-api` skips it for scripts; `--provider claude|claude-max|codex` keeps working. Without a terminal the selector reads its answer from standard input, and a closed stdin fails with the `--type` hint. The server holds refreshable OAuth sign-ins only (providers `anthropic` and `codex`), so choosing the API key type is refused with an explanation before any network call: API key accounts need server support (credential kind, transport without refresh, migration) and are not part of this change. Nothing secret is printed or stored differently.

Evidence: `AccountTypeTest`.
