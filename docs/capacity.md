# Capacity, policies and agent guidance

## Two independent limits

Subscription windows are provider observations: account-wide five-hour and weekly windows, plus model-specific windows when reported. TeamCode never sums percentages across plans or invents a token-to-subscription exchange rate. An account at or above the team's quota pressure threshold (95% by default, see [Quota pressure threshold](#quota-pressure-threshold)) on a relevant window is excluded until its known reset. If the reset is unknown, that observation excludes it only while it is at most five minutes old; later admission may probe the account again. Renewed saturated readings renew that protection. HTTP 429 updates relevant windows or adds a bounded cooldown. A rejected access token allows one coordinated renewal attempt; uncertain refresh ownership requires reconnect.

Team credits are an administrator-controlled daily budget. Current accounting is input tokens plus cached/read/creation input tokens plus five times output tokens. The request reserves raw request bytes + 16,384 + five times maximum output tokens before dispatch. Actual usage replaces the reservation on complete streams; missing usage or interruption retains the estimate. Failed admission spends nothing. A provider 4xx settles to zero. This conservative estimate can reject a large request even if its eventual output would be short.

Daily periods reset at 00:00 UTC. Weight shares are computed over enabled members in each pool, including administrators and members still awaiting their first password change. Weight zero grants no admission. An optional hard cap further limits a member's share; zero means no additional hard cap. All members' spend also counts against the total pool budget. Changing member weights or pools never resets existing spend. Historical reservations retain their original pool.

A member's concurrent request limit is optional: zero, the default, means unlimited (the dashboard shows it as such), and an administrator can set 1 to 32. Upgrading leaves every saved member policy unchanged, so a member configured with the former default of 2 keeps it; members without a saved policy become unlimited. To lift an explicit limit, set **Concurrent requests** to 0 in **Dashboard → Capacity**, or send `PATCH /api/v1/members/{id}/policy` with `"maxConcurrent":0` (the request replaces the member's whole policy, so repeat their current daily cap, weight, pool and overflow values). Unlimited members are still bounded by group and launch limits and by the forecast pacing below.

Budgets and reservations persist in MySQL. Member requests are admitted under a team lock, so concurrent arrivals cannot each claim the same remaining credit. Subscription accounts have no parallelism limit of their own, for Claude and Codex alike: placement picks the least loaded eligible account (fewest active requests, then fewest active conversations, then lowest utilization) within the pinned/home/priority order, and never refuses or queues a request because an account is busy. Quota windows, through the forecast pacing below and the exclusion at the quota pressure threshold, are what slow an account down. Active leases expire after 15 minutes; requests time out after 10 minutes. Expiring a lease releases concurrency, not its reserved credits. The server is currently a single-team deployment; the schema also keeps team ownership explicit.

## Raw token usage

Credits are a team policy unit, not what the provider meters. Next to them, TeamCode records the provider's own token counts for every dispatched request when it settles, in the same transaction and under the same "first settlement wins" rule as the credits, so a repeated or late settlement never counts twice. Four types are kept apart and never weighted: **input** (uncached), **cache writes**, **cache reads** and **output** (reasoning included). Messages streams report them as such; a Responses stream includes cached input in `input_tokens`, so its `input_tokens_details.cached_tokens` is split out once into cache reads (Responses reports no cache writes). The credit charge is unchanged.

`GET /api/v1/usage/tokens` (`usage:read`) returns one row per UTC day, member, agent launch (`runId`, null outside a registered `teamcode run`), provider and model: `requests`, `unmeteredRequests` and the four sums. `from` and `to` are inclusive UTC dates (`YYYY-MM-DD`, the last seven days by default, at most 366 days); pages of at most 500 rows follow the `nextAfter` cursor. A member and every `usage:read` key, an administrator's included, read the owner's rows; an interactive administrator or an administrator's `team:read` key reads one member's (`member=`) or the team's (`all=true`). The model is the one the provider served (after any route). A team can multiply these sums by its own price list to get an API-equivalent cost; TeamCode applies no price yet. Servers advertise `usage.tokens.v1`.

What is not in the sums: a request refused before dispatch or answered with an error status by the provider (4xx or 5xx: no tokens consumed) is absent; a dispatched request whose stream ended without terminal usage counts in `unmeteredRequests` only, never as zero tokens, and a later [usage reconciliation](usage-reconciliation.md) corrects its credits, not its tokens; a request whose lease expired without any settlement (a replica crash) is absent and appears in the usage review. The tokens are written right after the credit settlement, in their own transaction, by the settlement that won: a ledger failure never rolls back a charge, and a crash between the two loses those tokens, never the charge. A day row is the reservation's admission day (like credits), an account row the hour the request settled. The same tokens are also kept per subscription account and UTC hour (`account_token_usage`, internal, not exposed) as the history a future capacity estimate needs. Neither table has an automatic retention policy yet; rows are aggregates (one per day, member, launch and model), never prompts or responses.

## Group limits

[Groups](groups.md) add cumulative daily and concurrency caps without changing weighted shares or pool eligibility. Every active membership applies. Scoped managers can pause/resume admission for their group members; only administrators change budgets, assignments and roles. Original group snapshots retain spend after a membership move/removal, while actual usage settles in the existing reservation ledger. Archiving is an explicit administrator release of that group's constraints; restoring preserves same-day charges. Group concurrency waits in the bounded queue, while group budget exhaustion and pauses are hard refusals. Own capacity responses include group limits and usage, without exposing rosters to service keys.

[Temporary quota overrides](budget-overrides.md) let interactive administrators replace one member's total daily allocation with an audited, expiring exception. The deadline is at most the next UTC reset; zero stops new admissions. Capacity exposes both normal and effective allocations. Existing spend remains charged and pool/group/run/concurrency/provider policies still apply. A pool change revokes the exception. Increased shared-pool allocations are an explicit admin decision and do not reserve another member's future share.

## Agent launch limits

[Agent sessions](agent-sessions.md) add administrator-controlled lifetime credit/concurrency caps and admission pauses for registered launches. These never replace member/group/pool limits. Original reservation links and idempotent settlement maintain lifetime totals across midnight and detail retention. Run concurrency uses the shared queue; closure, pause and insufficient run credits are hard refusals. Recent associated run policies also constrain native-session pacing, with incomplete metadata producing unknown guidance.

## Shared overflow reserves

[Shared subscription overflow](shared-overflow.md) lets opted-in members use accounts from explicitly shared, named reserves with no primary members. Home accounts are preferred unless an eligible conversation pin uses a reserve. All existing member/group/run limits remain hard; reservations snapshot the logical home and physical source and count against both pool budgets. Other ordinary protected pools cannot be borrowed. Configuration is disabled by default.

## `teamcode status`

`teamcode status` prints the gateway's queue line, then the caller's own allowance and the subscription accounts they can be routed to; `--json` prints the same report. Every figure comes from the routes the dashboard reads, with no second calculation:

- **Your quota** (`GET /api/v1/capacity`): today's allocation and where it comes from (pool share, personal cap or temporary override), used credits, credits reserved by requests in flight, remaining credits, concurrency, the midnight UTC reset, each group's caps and pause, and the current pacing advice (`GET /api/v1/directives/current`; `none` in observation mode). Reserved credits are the 15-minute upper estimates of active requests; an expired lease stays charged until review.
- **Pool accounts** (`GET /api/v1/pools/accounts`, `usage:read`): state, current 5-hour, weekly and model-scoped window utilization with time to reset, and whether the account can take a request now, with the first reason it cannot (disabled, pending handover, reconnect required, cooling down, or a shared window at the team's quota pressure threshold, 95% by default). A model-scoped window bars only its model, so it never makes the row unusable. Interactive administrators and `team:read` keys see every team account by name. Members, and every other service key including an administrator's `usage:read` key, see only the accounts of their own pool plus opted-in shared overflow reserves, as neutral `Account N` labels without identifiers or pool names; the number follows this listing's priority order and names a row, not a lasting account identity. Nobody sees another member's allowance or usage through this command.

Only the gateway line is required; the three other reads run together and none of them can fail the command. When a section cannot be shown, `status` prints `unavailable` in its place with the reason: `from this server or credential` (`404` or `403`: a server older than these routes, capacity disabled, or a key without the scope), `unexpected response from the server` (a body of another shape), or `the read failed; try again` (any other HTTP error, a timeout or a network failure). A pacing read that fails shows `Pacing unavailable`, never `none`. `--json` leaves that field `null` and names the reason in `unavailable` (`{"capacity": "not_served" | "unexpected_response" | "read_failed"}`, likewise for `pacing` and `accounts`), so a script can tell a server without quotas from a transient failure.

## Shared admission queue

Temporary concurrency and forecast pacing restrictions wait before dispatch. MySQL stores pending metadata and the last served turn for each member, scoped by team, physical source pool and provider. Ready members alternate turns; requests from the same member use FIFO order. Interactive requests have priority, while background requests join that priority class after 30 seconds to avoid indefinite starvation. This is fairness by request turns, not by tokens or runtime. The member's weight controls the daily credit share independently; weight five does not grant five scheduling turns.

Requests default to interactive. Use `teamcode run claude --workload background -- ...` or `teamcode run codex --workload background -- ...` to mark unattended work; `--workload interactive` is explicit opt-in to the default. This selects a scheduling class, not process detachment. The setting applies to every inference request from that launch without modifying saved configuration or other launches sharing the service. The local proxy translates the launch-specific loopback path into `x-teamcode-workload: background` and forwards the canonical inference path. Conflicting or duplicate workload headers on that path are rejected. Older services without workload support are bypassed through a dedicated local proxy for that launch, never stopped.

HTTP/SDK integrations can also set `x-teamcode-workload: background` (or `interactive`) on the canonical inference endpoints; invalid or duplicate values are rejected by the server. The header is not sent to a provider. Workload selection is a caller-supplied scheduling hint, not an authorization boundary; protected pools and server-side budget/concurrency policies remain the enforcement mechanisms.

The queue admits at most 128 pending requests per team, and at most 8 per member only for a member with a concurrency limit: an unlimited member is bounded by the team queue alone. Each admission attempt waits at most 90 seconds, polling every 500 ms with a renewable 15-second lease. Waiting holds no database connection, physical slot or reserved team credits. At dispatch, a short team-locked Exposed transaction rechecks authentication, model/effort policy, route configuration, weighted allowances and account eligibility, then consumes the turn and creates the reservation atomically. A changed route or pool requires a fresh request. Crash leftovers expire; cancellation removes the pending row, with lease expiry as the cleanup fallback. Request bodies stay with their HTTP request, never in queue tables.

The dashboard capacity view and `teamcode status` expose waiting counts. Queue bounds/expiry return HTTP 503 if no configured fallback succeeds; hard allowance denials remain immediate. Existing streams are not preempted, so protected pools remain useful for reserved support capacity. The queue shares physical overflow capacity only through explicitly authorized reserves; it does not dynamically expand credit allowances or admission limits. [Unknown-usage review](usage-reconciliation.md) provides final, audited operator corrections using request-specific provider evidence, without automatic refunds from lease expiry or quota percentages. A [controlled two-replica HTTP contention fixture](scheduling-acceptance.md) covers interactive rotation, per-member overflow, pre-header cancellation, complete streams and exact shared settlement. Sustained real-agent fairness, broader backpressure and database polling cost remain acceptance work.

Both the central server and native local proxy cancel inference handlers on client disconnect, including while waiting for the first response headers. Upgrade both components to obtain this behavior end to end; older local proxies can keep the server request alive after the agent disconnects. All server replicas must use the queue-aware version before relying on shared scheduling.

## Forecasting

Usage is sampled sequentially, with at most eight accounts per sampling pass. Inference headers supply additional observations. A valid percentage is retained even when the provider omits its reset timestamp. API responses use `resetsAtMillis: null` and the dashboard displays `unknown`; zero usage is a real observation, while an absent or invalid percentage creates no observation. Newer unknown-reset readings replace older known-reset readings, and delayed samples cannot overwrite them. History retains one sample per minute per account/window, with seven-day retention; forecasts use the latest hour and matching reset epoch. At least three observations spanning one minute are required to infer a rate. A fresh reading already at the pressure threshold does not require a learned rate to identify exhaustion. A fresh exhausted window produces pause advice even if another window is absent. Without a known reset epoch, history cannot establish a stable rate, idle state or reset-before-exhaustion forecast. Resets, utilization decreases, duplicate timestamps and gaps longer than five minutes start a new learning segment. At least three continuous samples spanning a minute are needed to relearn after a gap or decrease; earlier segments never dilute that rate. Missing windows and observations older than five minutes yield unknown/stale guidance rather than optimistic headroom.

The controller projects the team's capacity as a whole: the goal is to never run out of quota entirely, and as long as some account has quota left, work goes on at full speed. It emits NORMAL, SLOW_DOWN, CAN_INCREASE, PAUSE or UNKNOWN. Tightening and unknown data take effect immediately. Easing requires the candidate state to remain stable across observations for two minutes; renewed pressure or a different candidate resets that recovery timer. The pending state is stored in MySQL and survives replica changes. Advice expires after three minutes without renewal. NORMAL, CAN_INCREASE and UNKNOWN never delay or cap admission: without a member limit, any number of simultaneous requests is admitted at once, even on a single account. SLOW_DOWN only spaces admissions: pacing never caps parallel requests, whatever the level (the advice's concurrency is the member, group or launch limit, zero for none).

The projection starts from the remaining capacity of every account the target can use (`AccountHeadroomUseCase`, the computation shared with capacity sizing: the threshold minus utilization, per current window, until its reset), with accounts at the threshold counting for nothing until their reset and disconnected, disabled, pending or cooling accounts not counting at all. The team's burn rate for a window is the sum of the rates learned on that window over the latest hour, as a share of one account's window per hour (accounts of one provider are taken as comparable). The whole load goes to one account at a time, the one whose next reset comes first, burning its five-hour and seven-day windows together; an account stops when either runs out, a window that resets refills to the threshold, and a window that is not observed never binds (unknown is not empty). The projection looks seven days ahead. It finds the first *gap*: a stretch when no account has quota left, from when the last one runs out to the first reset that gives some back. A depletion that falls exactly on a reset is no gap.

- No usable account now: PAUSE.
- A gap ahead: SLOW_DOWN, graded by the gap's *affordable share*, the share of the current burn rate that would last until capacity comes back, `(gap start − now) / (gap end − now)`. A longer or closer gap affords less.
- No gap, but an account without a fresh five-hour or seven-day observation, or no learned team rate for one of them: UNKNOWN.
- No gap even at twice the current rate: CAN_INCREASE; otherwise NORMAL.

| Level | Affordable share | Minimum gap between admissions |
|-------|------------------|--------------------------------|
| Light | at least 1/2 | 2 s |
| Moderate | 1/4 to 1/2 | 5 s |
| Severe | under 1/4 | 10 s |

A stronger level applies at once; a weaker level, like any easing, waits for the two-minute recovery, and moving to another level restarts it. PAUSE spaces admissions by thirty seconds, still without a ceiling. Requests held back by pacing wait in the shared queue below. The recent peak of parallel requests in a directive's scope is still stored with the directive for diagnostics; it no longer sizes anything. The account exclusion at the pressure threshold is enforced separately and uses the same configured value: an exhausted account, or one awaiting reconnection, is not chosen, and a conversation pinned to it moves to another eligible account. Advice to increase parallelism only applies to useful work already queued and remains bounded by the administrator's concurrency limit, when there is one.

Forecast contexts come from conversation placements admitted within the last two minutes. They retain the original input protocol and must match the current route fingerprint, requested/resolved model policy, reasoning effort and explicit thinking-budget ceiling. Without a valid active context, advice is UNKNOWN; idle capacity on an unrelated provider never justifies acceleration. Old hints without protocol metadata become usable after their next admission.

Each active target uses its provider's accounts in the member's assigned pool and authorized funded reserves, whatever their priority or pins (placement moves work to another account before one runs out, so only their total capacity says when work would stop), with shared quota windows and model windows applicable to the resolved model. For example, a Fable-only window does not pressure Opus; idle Codex does not hide Claude burn until work actually moves to Codex. Advice is capped only by the member, group and launch ceilings. Exhausted member shares, hard caps, group budgets/pauses or pool budgets produce an allowance-specific PAUSE; admission and advice read the same weighted-share calculation.

The controller stores separate advice for each client session and an aggregate member view. Within one session using several targets, the most constrained target controls that session’s advice. A busy Claude session no longer throttles an unrelated Codex session merely because both belong to one member. A changed route, model policy, pool, priority or eligible account set invalidates the old recovery state. Advice is recalculated by the controller, while hard authorization and budgets are checked at every admission. This does not reserve physical slots for advice recipients, predict the next request's cost or guarantee that another member will not consume available capacity. Requests without session metadata receive no route-based acceleration advice. Replay accuracy under real load remains acceptance work.

Interactive administrators can inspect per-account measurement curves, conditional projections and explicit unknown/stale states in [Dashboard → Forecasts](forecasts.md). This is a read-only snapshot, separate from the current member/session controller directive.

## Quota pressure threshold

One team-wide setting, the **quota pressure threshold**, decides when a provider window counts as under pressure. At or above it on a five-hour, seven-day or model window that applies to the request, an account is no longer chosen for new requests (until the window's known reset), conversations pinned to it move to another eligible account, and forecasts, pacing advice (PAUSE) and the Forecasts page treat the window as exhausted. Forecast ETAs and the dashed projections target the same value. Before this setting existed the forecast constant was 90% while admission excluded at 95%; both now read the one stored value, so the default of **95%** moves forecasts from 90% to 95%.

Administrators change it in **Dashboard → Agents** (field "Quota pressure threshold (%)") or with `quotaPressurePercent` on `PUT /api/v1/policy/pacing`; `GET` returns it for every signed-in member. It is a whole percentage from **50 to 100**; anything else is refused with `invalid_quota_pressure` (HTTP 400) and nothing is stored. Below 50% the controller already advises acceleration, so a lower value would contradict it, and 100% means only a fully used window is excluded. Omitting `quotaPressurePercent` in a `PUT` keeps the stored value, so older clients that only send `observationOnly` do not reset it. Lowering the value takes effect on the next admission and controller pass, without a replica-local cache; it never recalls requests already admitted.

Changes are audited as `pacing.quota_pressure_changed` (the subject records the previous and new value). The additive `quota_pressure_percent` column of `pacing_settings` defaults to 95, so existing teams keep the default. Upgrade every replica before relying on a non-default value: an older replica still excludes at 95% and forecasts at 90%. Rolling back the binary keeps the column and loses the setting.

## Observation-only controller mode

Administrators can enable **Observation only** in **Dashboard → Agents**, or send `{"observationOnly":true}` (optionally with `quotaPressurePercent`) to `PUT /api/v1/policy/pacing` using an interactive administrator login. `GET /api/v1/policy/pacing` exposes the effective mode to signed-in members. The default is false, preserving predictive pacing on existing installations. The typed client exposes `pacingSettings()` and `savePacingSettings(...)`.

The controller continues collecting samples and computing the same forecasts and recovery hysteresis in MySQL. The dashboard and `GET /api/v1/directives/preview` display the member's proposed aggregate directive with the effective settings; the typed client exposes `pacingPreview()`. Preview output is informational, not an agent delivery contract. Service/CI keys cannot read or change these management endpoints.

While observation is enabled, admission ignores predictive intervals and predictive concurrency ceilings. Both aggregate/session delivery reads and new delivery claims return no directive, so built-in hooks, manual hints and watchers do not send observation advice to agents. Hard member/group concurrency, group budgets/pauses, weighted shares/hard caps, pool isolation/budgets, physical account slots, provider quota exclusions and model/effort policy remain enforced. Turning observation off resumes delivery and predictive enforcement of fresh controller output. Already admitted work or already emitted/in-flight advice cannot be recalled.

Mode changes, admission and delivery claims use the same team lock and current shared authorization. Mode changes are audited as `pacing.observation_enabled` or `pacing.enforcement_enabled` (only when the mode actually changes); settings are read from the database, without a replica-local cache. The additive `pacing_settings` migration is generated from Exposed tables. Upgrade every replica before relying on observation mode: older binaries still enforce and deliver predictive guidance. Retain the table on rollback; reverting to an older application does not preserve observation behavior.

## Agent integration

`teamcode run claude -- ...` installs a temporary, session-only guidance plugin for the launched process. Its HTTP hooks call the authenticated loopback proxy at `UserPromptSubmit` and `PreToolUse`, without modifying personal/project settings or spawning a shell for each tool. The proxy sends only the session ID and delivery stage to the central server; prompts, tool arguments and transcript paths are discarded locally. It returns `hookSpecificOutput.additionalContext` using the [Claude Code hook protocol](https://code.claude.com/docs/en/hooks). Hook outages return empty context and do not change tool permissions or block execution. Use `teamcode run claude --no-guidance -- ...` to opt out; `--bare` also skips the plugin. Managed hook policy and explicit hook disabling remain respected.

Manual integrations can use `teamcode agents hint --session SESSION_ID --format claude` (also `text` or `json`). `teamcode agents watch --session SESSION_ID` emits scoped updates; without `--session`, watch shows the aggregate member view. Received-by-CLI and emitted-to-hook have independent delivery state, so watching does not consume the hook message. `teamcode run codex -- ...` installs invocation-only native command hooks for the same events. Review them in Codex `/hooks` before first use; TeamCode never bypasses hook trust. `--no-guidance` disables installation, and custom CLI hook overrides remain authoritative.

Session deliveries are claimed atomically in MySQL for 15 seconds. Parallel hooks/replicas cannot claim the same version simultaneously. An acknowledged version is suppressed; a lost response/acknowledgment can retry after the lease and may repeat the message. Receipts record bridge emission, never that the model read, accepted or obeyed it. Advice requires a currently active session belonging to the authenticated member. No raw session ID is stored. The detailed delivery contract and real-client fixture are in [agent guidance](agent-guidance.md).

Admission applies the scoped directive when session metadata exists and the member directive for requests without it. A new session begins without a forecast throttle until its own activity is observed; it never inherits another session’s throttle. Hard member concurrency, weighted allowance, pool budget and physical account limits remain independent and apply immediately, including to new or renamed sessions. Scoped pacing counts that session’s requests rather than all of the member’s work. TeamCode never kills agent processes.

## Refusals seen by agents

An inference refusal uses the envelope of the agent's own protocol, so the agent prints its message: Anthropic Messages `{"type":"error","error":{"type","message"}}` on `/v1/messages`, OpenAI Responses `{"error":{"type","code","message","param"}}` on `/v1/responses`. `error.type` is a documented value for the status (`rate_limit_error`, `billing_error` for an exhausted daily or run budget, `api_error` or `server_error` for 5xx, never `overloaded_error`, which Claude Code retries whatever the headers say). The TeamCode code is in `x-teamcode-error` and, for Responses, in `code`. Messages state the cause, what to do and when it unblocks; they count accounts per cause and never name accounts or other members.

| Refusal | Status | Retry |
|---|---|---|
| No usable account, and none will become usable by itself (accounts awaiting a handover, to reconnect, disabled, or none connected) | 503 | `x-should-retry: false` |
| No usable account, but some are cooling down or at a quota | 429 | `Retry-After` until the earliest known return; `x-should-retry: false` beyond 120 s |
| Daily member, group or pool budget used up | 429 | `Retry-After` until 00:00 UTC, `x-should-retry: false`; `Retry-After: 30` and retried while that budget is held by running requests, which settle at their real cost |
| Run budget used up | 429 | `x-should-retry: false` |
| Member, group or launch concurrency, pacing interval, queue turn (waited for in the queue before any refusal) | 429 | `Retry-After` of a few seconds |
| Queue wait expired or queue full | 503 | `Retry-After: 15` |
| Invalid request, model, effort or pause policy, ended run | 4xx | `x-should-retry: false` (except `route_changed` and `queue_context_changed`, which a resubmission resolves) |

Every refusal of an inference request is logged once by the server, without body or credential: `TeamCode inference refused member=<id> code=<code> status=<status> [retryAfter=<s>] reason="<public message>"`. An admission that waited at least one second in the queue is logged as `TeamCode inference admitted request=<id> member=<id> waitedMs=<ms>`.

Claude Code (and the Anthropic SDKs) skip their retries on `x-should-retry: false`, so a state only an administrator can fix is shown at once instead of looping on "API Error"; a 429 without that header is retried after `Retry-After`. Codex retries 5xx on its own and ignores the header. The local proxy of `teamcode run` relays these headers and prints the cause of a TeamCode refusal on stderr once per status and code every 10 minutes.

## Models and effort

Administrators edit the allow/deny patterns and allowed efforts in the dashboard. Deny takes precedence. Missing effort is represented as `provider-default`; an explicit token thinking budget also requires `budgeted` permission and must fit the administrator's cap. This policy validates the requested and resolved model names, so route aliases cannot bypass a forbidden model. The gateway checks native Claude/GPT requests and both sides of configured cross-provider routes; see [routing](routing.md) for conversion capability limits.

## Refresh ownership

An account added with `accounts add` comes from an OAuth sign-in TeamCode ran itself: nobody else holds that refresh token, so the account is `READY` at once, and signing in again this way also takes over an existing pending or reconnect-required account. Imported accounts are pending until explicit activation, and reimporting keeps their state. Normal handover confirms other token refreshers have stopped and gives TeamCode refresh ownership, from `accounts handover ID --confirm` or the Handover button of the subscription accounts dashboard page (administrators only, origin- and CSRF-checked, with an in-page confirmation checkbox standing for `--confirm`). While any account is pending, the overview and the accounts page show a banner; when no enabled account can serve, it states that every request returns `429 pool_unavailable`. Database row locks serialize refresh across server processes and prevent concurrent import from overwriting a newly rotated token. An uncertain refresh never reuses the old refresh token.

`accounts import --from teamclaude --access-only` is a temporary trial mode. It enables inference and quota reads using current access tokens, but never rotates them. At expiry, requests fail until credentials are imported again. Existing source agents can continue refreshing their own copy. Import never edits or stops the source application.


## Observation compatibility and upgrades

Claude usage accepts ISO reset dates and numeric seconds/milliseconds, plus the percentage/reset aliases covered by TeamClaude's usage fixtures. Codex header and usage parsers share a 10% tolerance around five-hour and seven-day window durations; primary/secondary position never determines duration, and hourly/monthly windows are not relabeled as weekly. Named weekly observations remain model-scoped. For Codex, headers and usage probes use the same canonical limit slug (`metered_feature` without `codex_`), independent of its display label. A response can bind the actual resolved model to `x-codex-active-limit` for that subscription. These bounded, durable bindings override model-name heuristics consistently in admission and forecasting. Shared windows still apply to every model. Responses without the header preserve existing bindings.

A successful usage probe with an explicit, structurally complete model-limit enumeration can retire previously listed model caps: `additional_rate_limits` for Codex and `limits` for Claude. Claude keeps valid legacy `seven_day_<family>` readings alongside the enumeration, including when the list is empty. A null legacy slot alone does not prove retirement; listed zero usage remains an actual observation. Missing or malformed lists remain partial observations. The probe is timestamped before its network request, so it cannot erase newer inference observations. A SQL snapshot watermark prevents delayed responses from resurrecting retired caps. Their history is retained, but forecasting excludes retired windows and never extrapolates across a later reintroduction. Malformed scoped entries or legacy model readings prevent a Claude probe from claiming complete enumeration. Shared windows are never removed by model-cap retirement. Further plan-specific fixtures and real quota/reset-boundary acceptance remain open.

Migration V10 makes the current-window and history reset columns nullable without rewriting known values. New replicas persist, read and gate unknown-reset observations through the same database. Deploy the new application to all replicas before relying on this behavior: older code ignores null-reset rows and older API clients expecting a mandatory number must update. Keep the schema migration when rolling back; a rollback loses this new protection and must not be advertised as equivalent quota handling.

The generated model-limit migration adds shared per-account model bindings, snapshot watermarks and a window-incarnation timestamp. Deploy all replicas before relying on these semantics: an old replica does not understand aliases or retirement watermarks and can still write legacy observations. Keep additive schema changes on rollback. Exposed queries, HikariCP connections and Flyway migrations preserve the same database-backed ownership model; no routing state is kept in a process-local cache.
