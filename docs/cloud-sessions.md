# Cloud agent sessions (V2)

TeamCode V2 runs agent sessions on a Kubernetes cluster that an administrator connects to the team. A session is a durable, logical identity: it survives pauses, pod replacements and server restarts, and keeps one workspace volume for its whole life. The CLI and the API share the same contract; the CLI never talks to Kubernetes.

This page is the contract and the record of what is implemented. It follows the [roadmap](roadmap.md) section on Kubernetes cloud sessions and builds on [stateless replicas](replicas.md), [audit](audit.md) and [service credentials](service-keys.md).

## Session states

`state` is a closed, stable enum. `phase` is an open, informational string; clients must tolerate unknown values.

| State | Meaning | Typical `phase` values |
| --- | --- | --- |
| `creating` | Accepted; waiting for capacity, provisioning the workspace and pod | `scheduling`, `waiting_capacity`, `starting_runner` |
| `preparing` | The runner registered for the first execution and is preparing the environment | `starting_runner` |
| `ready` | Prepared; accepts work | - |
| `active` | An agent turn is running (planned with the agent) | - |
| `pausing` | Draining and checkpointing | `draining`, `checkpointing`, `stopping_pod` |
| `paused` | No pod; workspace retained | - |
| `resuming` | A new execution is starting on the same workspace | `waiting_capacity`, `scheduling`, `starting_runner`, `restoring` |
| `transferring` | Changing owner at a paused boundary: no pod, recipient rechecked, then one transaction changes the owner | `transferring`, `stopping_pod` |
| `terminated` | Deleted or expired; no pod; workspace being deleted or deleted | `cleanup_pending`, `deleting_volume`, `cleaned` |
| `failed` | Unusable; the workspace never held work or is lost | - |

Other fields: `desiredState` (`running`, `paused`, `terminated`), `failure` and `resumeBlocked` (`{code, message, retryable}`), `resume` (`workspace`: `consistent`, `crash_consistent` or `lost`; `conversation`: `resumable`, `transcript_only` or `none`; always `none` until the agent lands), `workspaceDeletion` (see [deletion](#workspace-and-proven-deletion)), and `waiting` while the agent waits for a person (see [a session waiting for a person](cloud-conversations.md#a-session-waiting-for-a-person)).

## Coordination across replicas

API routes only write the desired state. A **leased reconciler** running on any replica does all cluster work, outside any database transaction:

- **Compare-and-set.** Every change is an Exposed conditional update `WHERE id = ? AND generation = ?` that increments `generation`. A lost race re-reads the row and evaluates the decision again (`TransitionCloudSessionUseCase`).
- **Lease per session.** `reconcile_owner`/`reconcile_until` use the database clock. A pass claims up to 8 due sessions with a 60 s lease; a session not reached within half the lease is released due immediately instead of being worked on with a lease about to expire. Reconciler writes also require the lease to still be held, so a stale owner whose lease expired cannot commit, and cannot release its successor's lease. A write made during a pass (for example a pause request) sets `reconcile_requested`, and the lease release schedules another pass immediately.
- **Epoch fencing.** Starting an execution advances `currentEpoch` by one and inserts the `cloud_executions` row in the same transaction, serialized on the cluster row with the capacity check. The `(session_id, epoch)` key and the generation check make a duplicate start impossible, even with two replicas holding the same stale view. The pod name is deterministic (`tc-<session>-e<epoch>`); creating an existing pod succeeds. Pods of older epochs are deleted and confirmed gone before the next epoch starts.
- **Runner fencing.** Every runner call is bound to `(session, epoch)` and to the pod name of the execution. Anything else returns `409 execution_fenced`; the runner must then stop its agent and exit without checkpointing.
- **Image pulls.** `InvalidImageName` and `ErrImageNeverPull` fail the start at once. `ErrImagePull` and `ImagePullBackOff` are retried by the kubelet (registry outage, rate limit, tag pushed late), so they fail the start only after 5 minutes.
- **Errors.** A step that throws (cluster or database unavailable, or a defect) is retried after 30 s; the reconciler takes an error callback so the server logs and counts it, and the raw error never reaches the session or its API view.
- **Bare pods.** A Job controller could recreate a pod outside TeamCode's epoch control, so the adapter creates bare pods with `restartPolicy: Never`; the reconciler alone decides whether to start again.
- **Exclusive volume.** The workspace claim requests `ReadWriteOncePod` by default, so the cluster itself refuses a second pod on the workspace. The runtime's workspace access mode `ReadWriteOnce` is for drivers without it (the local `kind` provisioner); the epoch rule above still applies.

Due times: about 2 s while a step is in progress, 5 s while waiting for capacity, 15 s while running (heartbeat watch), the expiry time while paused, 10 minutes while a deletion is blocked, and nothing once a deletion is proven.

`TeamCode-On-Behalf-Of: <memberId>` sets the effective member. It is accepted only from an interactive administrator or an administrator's `admin:cloud` key. On any other credential the header must be absent or equal to the caller's own id; otherwise `403 on_behalf_forbidden`. The target must be an enabled team member who completed password setup (`422 invalid_effective_member`), and for creation it must hold the profile assignment. The header never grants rights: the call is authorized with the caller's own rights.

For creation, the effective member becomes the owner; the retained-session cap and profile assignment resolve for that member.

### Attribution and audit

Sessions record `createdBy {initiatorId, credentialId, effectiveMemberId}`; `credentialId` is the id of the login session or key, never its token. The audit journal gained two nullable columns, `effective_member_id` and `credential_id`, exposed as optional fields of `GET /api/v1/audit` events. Journaled actions: `cloud.session.created`, `.paused`, `.resumed`, `.deleted` (by the caller), and `.pausing`, `.pause_cancelled`, `.paused_checkpoint`, `.ready`, `.ready_resumed`, `.execution_lost`, `.resume_blocked`, `.failed`, `.expired`, `.terminated`, `.workspace_deleted` (by `system`, with the owner as effective member); `cloud.cluster.saved`, `cloud.profile.saved`, `cloud.settings.updated`, `cloud.runtime.updated`, and `cloud.runtime.seeded` (by `system`, see [runtime](#runtime-on-off-runner-image-and-pod-callback)). Transfers add a third nullable column, `related_member_id` (`relatedMemberId` in the API): `cloud.transfer.offered`, `.requested`, `.accepted`, `.declined`, `.cancelled` (by the caller, subject the transfer), `.started` (the session enters `transferring`), `.expired`, `.failed` (by `system`, with the recipient as effective member and the former owner as related member), and `cloud.session.transferred` (subject the session, actor the transfer's initiator, effective member the recipient, related member the former owner). For transfer entries, `effectiveMemberId` is the member the action was done for (the delegated member of an on-behalf call, otherwise the actor; the recipient for system entries) and `relatedMemberId` is the other member concerned, so filtering the journal by member finds every transfer that gave a session to or took one from them. The dashboard audit page shows both.

### Idempotency

`POST /cloud/sessions` requires `Idempotency-Key` (1–128 characters from `[A-Za-z0-9._:-]`). Scope: team + initiating member + route. The server stores a SHA-256 of the canonical request (the decoded body with sorted labels, plus the effective member) in the same transaction as the session:

- same key, same request: `202` with the session and `Idempotency-Replayed: true`;
- same key, different request or effective member: `422 idempotency_conflict`;
- concurrent requests with one key are serialized on the member row; one creates, the others replay.

The replay returns the **current** view of the created session rather than a byte copy of the first response. Records expire after 24 hours (bounded purge).

Pause, resume and delete are naturally idempotent through the desired state. Messages take `Idempotency-Key` or its `clientMessageId` alias ([messages](cloud-conversations.md#messages-and-interrupts)). `POST /cloud/sessions/{id}/transfer` requires `Idempotency-Key`, with the same scope and digest rules as creation (the digest covers the session, the body and the effective member); accept, decline and cancel are idempotent through the transfer's state.

While cloud sessions are off, the requests that start new work answer `404` after authentication: creating a session, resuming, sending a message, attaching, offering or accepting a transfer, and starting a GitHub link (device flow start and web flow; the callback, which authenticates itself, completes a link started while cloud sessions were on), whatever the path spelling (the gate reads the path the way routing matches it). Reading, pausing, interrupting and deleting sessions, renewing an existing attachment, declining or cancelling transfers, unlinking GitHub, configuration and the runner channel stay available, so existing sessions can always be stopped and running pods keep their channel. No new pod starts while they are off: a session still queued waits until they are on again, and queued messages do not wake paused sessions. Routes that authenticate themselves (the runner channel, the GitHub callback) are never gated, so an anonymous caller cannot learn whether cloud sessions are on. A session the caller cannot see returns `404`. Errors use the existing `ApiError {error: {type, message}}`.

```json
  "idleTimeoutMinutes": 30,
  "environment": {
    "repositories": [{ "url": "https://github.com/example/api.git", "path": "api", "ref": "main", "branch": "task-1234" }],
    "workingDirectory": "api"
  },
  "initialMessage": "Fix the relist retry, see task 1234."
}
```

- `profileId` is the profile's id (`GET /cloud/profiles` lists the usable ones). No profile with that id is `404 profile_not_found`; a profile that exists but is not assigned to the effective member (administrators use every profile) is `403 profile_unassigned`. Telling them apart reveals nothing a member could not already know: a profile id is a random UUID, listed only to the administrators and to the members assigned to it, so a member who holds one learns only that it is not theirs, never its name or recipe. Names are never resolved by the server: clients resolve them among the profiles listed to the caller (see [CLI](#cli)), so a profile not assigned to a member cannot be found by its name.
- `image` must equal the profile image or match one of its `allowedImageOverrides` (`*` matches any run of characters, everything else is literal); otherwise `403 image_not_allowed`.
- `labels`: at most 16 pairs, lowercase keys up to 63 characters, values up to 256, not secret, filterable.
- `idleTimeoutMinutes` is clamped to the profile bounds set by the administrator (`minIdleTimeoutMinutes`..`maxIdleTimeoutMinutes`, at most 1,440); the profile's `idleTimeoutMinutes` applies when it is omitted. See [idle pause](#idle-pause).
- `agent.model` and `agent.effort` are recorded; they are checked against the member's model policy on every inference, as for local sessions.
- `environment` (with `cloud.environment.v1`) replaces the profile's `repositories` and `workingDirectory` for this session; setup commands, required variables and the other recipe fields come from the profile only. Null fields keep the profile's values.
- `initialMessage` (capability `cloud.sessions.initial-message.v1`): the first message for the agent, same rules as `POST .../messages` (1 to 32,000 characters, no control characters except newlines and tabs). It is queued with the session and delivered once the session is `ready`, written by the caller: an administrator creating on behalf of a member is its author, and needs the `message` permission on that member's sessions. It is part of the request digest, so a replay with the same `Idempotency-Key` queues nothing more, and a failure between the session and the message is repaired by that replay (the message wakes the session like any message, so a session paused meanwhile resumes for it; a replay whose rechecks now fail, for example a revoked `message` permission, leaves the session without it). A server with cloud sessions but without conversations refuses it with `400 initial_message_unsupported`. The creation body may be up to 256 KB.
- The server ignores unknown fields, so do not send `environment` or `initialMessage` before the matching capability is advertised.

The response is the session view: `id`, `name`, `ownerId`, `createdBy`, `state`, `phase`, `desiredState`, `generation`, `currentEpoch`, `profile {id, version}`, `image {reference, digest}`, `agent {kind, version, model, effort}`, `labels`, `activity {lastActivityAt, idleTimeoutMinutes}`, `resume`, `failure`, `resumeBlocked`, `workspaceDeletion`, `createdAt`, `updatedAt`, `pausedAt`, `expiresAt`, `terminatedReason`, `environment` (the resolved recipe), `waiting` (only while the agent waits for a person). The image digest is recorded from the first running container; every later execution uses `reference@digest`, so a moved tag does not change a resumed session.

**Session kinds.** A session has a `kind`, fixed at creation: `cloud` (an agent in a pod the server starts, everything described on this page) or `remote` (an agent on a member's own device, started by the desktop app or the CLI). Every session created before kinds existed is `cloud`. A remote session's view carries `host {deviceId, deviceName, platform, osVersion, directoryName}`: the [device](devices.md) it runs on, described as it is now (`platform` is `macos`, `windows`, `linux`, `ios` or `android`, null until the installation reported it), and the last segment of its directory, never the full path. `deviceId` and the device fields become null once the device is removed; the session keeps its transcript. A cloud session has no `host`. `GET /cloud/sessions?kind=cloud&kind=remote` lists both kinds; without `kind`, only `cloud` sessions are listed, so a client written before remote sessions never receives one it cannot show (`400 invalid_kind` for another value). Session events of the [feed](cloud-conversations.md#event-feed) carry `kind` and, for a remote session, `hostDeviceId`. The host view also carries `permissionMode` (`ask` or `bypass`), `online` (the current execution heartbeats) and `lastHeartbeatAt`. For a remote session, `profile` is `{id: "remote", version: 0}`, `image.reference` is `remote` and `workspaceDeletion` is `not_applicable`: it has no pod, profile, cluster, image or volume.

### Remote sessions

Advertised as `cloud.sessions.remote.v1` when cloud sessions and the runner channel are on. A remote session runs the same runner as a pod (registration, heartbeats every 15 s, drain and checkpoint, the agent in stream-json or app-server mode, the transcript, the input long-poll) on the member's own device, under the member's own login instead of a pod's token.

- **Creation.** `POST /cloud/sessions` with `kind: remote`, `agent {kind: claude|codex, model, effort}`, `directoryName` (the last segment only: 1 to 255 characters, not `.` or `..`, no `/`, `\` or control character, otherwise `400 invalid_directory_name`) and `permissionMode` (`ask` by default, or `bypass`; otherwise `400 invalid_permission_mode`), plus `name`, `labels` and `initialMessage` as for a cloud session. `profileId`, `image`, `idleTimeoutMinutes` and `environment` are refused for a remote session, `directoryName` and `permissionMode` for a cloud one (`400`). The host is the device of the caller's login: a service key or a login without a device gets `422 remote_requires_device`, and creating on behalf of another member `403 on_behalf_forbidden`. A remote session starts `creating` with `phase = waiting_host` and counts toward no running, retained or cluster cap; there is no per-device cap either.
- **Hosting.** `POST /cloud/sessions/{id}/host` (owner only, from the host device) opens a new epoch with a pending execution and answers `{teamId, epoch, session}`; the previous live execution ends as `replaced`. Another device gets `409 remote_host_mismatch` ("This remote session runs on <device>; resume it there."), a session whose device was removed `409 remote_host_removed`, a pause in progress `409 session_pausing` (retryable). The host then calls the [runner channel](#the-runner-and-the-pod) with that epoch and its own login: the server accepts a login of the owner, from the host device, for the current epoch only (`401` otherwise, `409 execution_fenced` for an older epoch). Inference goes through the CLI's local proxy as under `teamcode run`, for a registered run labelled `teamcode.session=<id>`; `POST /cloud/runner/inference` answers `409 inference_unavailable`.
- **Permissions.** With `ask`, Claude Code keeps its permission checks and each request goes to the team's clients through the [permission relay](cloud-conversations.md); Codex runs in its `workspace-write` sandbox, limited to the directory. With `bypass` (a per-session choice made at creation), Claude Code runs with `--dangerously-skip-permissions` and Codex with `danger-full-access`, as in a pod.
- **Lifecycle without a pod.** A pause drains the turn and checkpoints as in a pod, then the host exits; the session stays `paused` until its host hosts it again. Resuming (`POST .../resume`) is accepted only from the host device and moves the session to `resuming` with `phase = waiting_host`, for the device's [daemon](#sessions-started-by-a-devices-daemon) to pick up when the session was started through it (it has a folder), or `teamcode remote resume` otherwise (`teamcode attach` on the host device picks up the wake of a message it sends). An execution silent for 90 s (120 s before its first registration) ends as `host_lost`: a `ready` or `active` session is paused crash-consistent with the retryable failure `host_offline`. The idle pause follows the team setting `remoteIdleTimeoutMinutes` (default 60, 0 to 1440, dashboard Settings). A remote session is never transferred (`409 remote_not_transferable`) and its directory is never deleted: deleting the session ends its execution and keeps the files. Removing the host device terminates its remote sessions (`terminated_reason = device_removed`).
- **CLI.** `teamcode remote start [DIRECTORY] [--agent claude|codex] [--name] [--model] [--effort] [--label k=v] [--message] [--bypass-permissions] [--detach|--attach] [--json]` creates the session in DIRECTORY (the current one by default; the file system's root, the home directory and system directories are refused) and hosts it. In the foreground (the default) Ctrl-C asks for a pause. `--detach` starts the host in the background and returns once it is online (or after 30 s, saying it is still starting): the host is `teamcode remote host SESSION` in its own session (POSIX `setsid`, a detached process with no console on Windows), so closing the terminal or a Ctrl-C there never reaches it, and its output, which never holds a prompt, an answer or a credential, is appended to `remote/<session>.log` (emptied past 1 MiB). `--attach` does the same, then attaches the terminal like `teamcode attach`; `/detach` leaves the host running. `--json` prints the created session on standard output, for the desktop app. `teamcode remote resume SESSION [--detach|--attach]` hosts a session of this device again (paused, woken, or left by a lost connection; a session still pausing is retried for 90 s) and does nothing for one already online; `teamcode remote host SESSION` is the host itself, in the foreground. `teamcode remote stop SESSION [--force]` pauses a remote session from any of the member's devices: the agent finishes its turn and its [background work](#background-work) (up to the pause deadline), the host checkpoints and exits, the directory is untouched. `teamcode remote list [--all-devices] [--json]` lists the remote sessions this device hosts (id, state, name, agent, online or offline, and the directory's full path from this device's record), and drops the records of terminated sessions. The directory's full path, the agent's conversation id and the host's log stay in `remote/` beside `config.json`, written under `config.lock`, never on the server. The host gets the team's MCP servers, the artifact tools, the [wait tools](waits.md#agents) (`ask_human`, when the server advertises `waits.v1`), the member's environment variables and, for Claude Code, the member's approved team hooks. `teamcode attach SESSION` (the same command as `teamcode cloud attach`) follows either kind; on a remote session recorded on this device, a message that wakes it also starts its host here in the background, so a terminal can wake a session its daemon does not host. `teamcode cloud list` lists both kinds where the server has remote sessions (`--kind cloud|remote` to choose) and ends each row with the kind and where the session runs (`profile ID`, or `on DEVICE (platform), online|offline`); `teamcode cloud show` prints a remote session's host, directory name and permission mode instead of its profile and image.

### Sessions started by a device's daemon

Advertised as `cloud.sessions.remote.daemon.v1`, with `cloud.sessions.remote.v1`. A member starts a remote session on one of their own devices from any client (the companion app, another computer); the device's [daemon](devices.md#device-daemon) hosts it.

- **Creation.** `POST /cloud/sessions` with `kind: remote`, `deviceId` and `folderId` (one of the folders the device published, `GET /devices/{id}/folders`), plus `agent`, `permissionMode` (`ask` or `bypass`, chosen at launch), `name`, `labels` and `initialMessage` as above. `directoryName` is the folder's name: omit it (another value is `400 invalid_directory_name`). Refusals: a service key `422 remote_requires_login`; on behalf of another member `403 on_behalf_forbidden`; a device that is not the caller's own, whoever the caller is (an administrator on another member's device included), `404 device_not_found`; a daemon offline `409 device_offline` (nothing is queued for later); a folder the device did not publish `422 folder_not_published`; a `folderId` without `deviceId`, or an invalid one, `400 invalid_folder`. The access policy's `create` permission still applies. The owner check compares the device row's member with the caller, never the caller's role.
- **The order is the session.** The session is created at once (`creating`, `phase = waiting_host`) with `host.folderId`, and the client follows it like any other. The daemon's queue is the list of its device's sessions that carry a folder, wait for a host (`phase = waiting_host`) and should run: new ones (`creating`), woken ones (`resuming`, after a message with `wake` or a resume) and ones whose host was lost before it was ready (`preparing`). `POST /devices/current/daemon/poll {waitMillis, version}` answers them, oldest first, at most 16, and waits up to 20 s for one (one indexed read per second, no transaction held between reads). A session created on the device itself (`teamcode remote start`, no folder) is never in the queue.
- **Accepting and refusing.** The daemon checks `folderId` against its own configuration, then accepts with the existing `POST /cloud/sessions/{id}/host` from the device (the session leaves the queue as `starting_host`), or refuses with `POST /devices/current/daemon/sessions/{id}/refuse {reason}`: the session ends with `failure.code = host_refused` and the reason code in its message (`409 not_waiting_host` once it no longer waits, `409 remote_host_mismatch` from another device). A session left in the queue while the device is offline starts when its daemon polls again.
- **Continuing a conversation of the device.** Advertised as `cloud.sessions.remote.resume.v1`, for Claude Code only. `GET /devices/{id}/folders/{folderId}/resumable?limit=&before=` lists the folder's Claude Code conversations on the device, the most recent first (20 by default, at most 50; `nextBefore` is the next page's `before`). Creation then takes `resumeSessionId`, one of these ids (a lowercase UUID). The server checks the format (`400 invalid_resume`, also without `deviceId`), the agent (`422 resume_unsupported` for Codex), the folder (`folder_not_published`) and the daemon (`409 daemon_resume_unsupported` when it did not announce `resume.v1`), and stores it with the host. The daemon checks the id again before it accepts the session: it must be a transcript of that very folder (its own `cwd`), or the session is refused with `resume_not_found`. The host starts Claude Code with `--resume ID --fork-session` the first time only, so the device's conversation stays as it was and the session continues its own copy (its later restarts resume the copy). A session already known to the daemon (woken, restarted) never takes the id again. Without `resumeSessionId` nothing changes, and an older client or server ignores the field: the create request's idempotency digest is the same when it is absent. On the device itself, `teamcode remote resumable [DIRECTORY] [--limit N] [--before MS] [--json]` prints the same list read locally with the daemon's code (nothing sent to the server), or `unavailable` (`server_unsupported`, `platform_unsupported` on Windows, `daemon_offline`, `daemon_too_old`) when this device cannot continue one; `teamcode remote start DIRECTORY --resume ID` (Claude Code only, a UUID) checks the id against the folder, then always hands the session to the daemon, and refuses with the reason instead of hosting it itself. The daemon takes the id while it has no conversation recorded for the session, so a session `remote start` recorded before the daemon picked it up is still forked.
- **The CLI's daemon.** The local service is the device's daemon ([services](services.md#device-daemon)): `teamcode folders add|list|remove` chooses the folders, the daemon refuses an order its own `folders.json` does not allow, hosts the others with the runner of `teamcode remote host`, starts a host that died again, pauses its sessions when it stops and resumes them when it starts again. `teamcode remote start DIRECTORY` goes through it when it is online (`POST /cloud/sessions` with this device's `deviceId`; DIRECTORY becomes one of its folders under the same rules, and the terminal attaches unless `--detach`), and so does `teamcode remote resume` for a session it started; `teamcode attach` leaves the wake of such a session to the daemon. Without an online daemon (or on Windows) both host the session from the command as before.

### Bounds and capacity

- Settings `maxRunningSessionsPerMember` (default 2) and `maxRetainedSessionsPerMember` (default 20) apply to every member; per-member overrides in member policy are planned.
- Each cluster has `maxRunningPods`. Executions not yet ended count, for all sessions on the cluster.
- A creation or resume beyond the running caps waits in `creating`/`resuming` with `phase = waiting_capacity`. Admission is FIFO per cluster: an older waiting session goes first unless its owner is at their own cap.
- The retained cap (sessions neither terminated nor failed) is enforced synchronously: `409 cloud_session_limit`.
- Inference from a pod uses the existing ledger, routing and pacing, under the member the execution runs for (see [inference](#inference-from-the-pod)). Pod-hours are not metered as quota.

## Persistent settings

Administrators edit them through `PUT /api/v1/cloud/settings` or **Dashboard → Cloud sessions** (`/dashboard/cloud`), like the `experimentalCrossProviderTranslation` model setting. They live in `cloud_settings`; a team without a row uses the defaults.

| Setting | Default | Meaning |
| --- | --- | --- |
| `pausedRetentionDays` | 30 | Days a paused session keeps its workspace. `null` keeps it indefinitely. |
| `failedWorkspaceRetentionDays` | 7 | Days a session that failed after its first execution keeps its workspace. |
| `maxRunningSessionsPerMember` | 2 | Running cap per member. |
| `maxRetainedSessionsPerMember` | 20 | Retained cap per member. |
| `transcriptRetentionDays` | 30 | Days transcript events are kept (1 to 3,650). `null` keeps them indefinitely. |
| `memberTransfers` | `offer` | `offer`: an owner may offer their own session and the recipient accepts; `disabled`: only administrators transfer. |
| `transferOfferDays` | 7 | Days a recipient has to accept an offer (1 to 30). |
| `transferPendingInputs` | `cancel` | Messages not yet consumed when the owner changes: `cancel` (reason `transferred`) or `keep` (delivered to the recipient's next execution). |
| `permissionDeadlineMinutes` | 0 | Minutes a cloud agent's [permission request](cloud-conversations.md#permission-requests) waits for an answer before the runner denies it (1 to 1,440). 0 waits without a deadline. Read once per execution, so a change applies to sessions started or resumed afterwards. |
| `fileMaxMebibytes` | 20 | Largest [file](cloud-conversations.md#files) a member may send to a session, in MiB (1 to 100). |
| `messageFileMebibytes` | 25 | Largest total of the files of one message, in MiB (1 to 100). |
| `backgroundWorkMaxMinutes` | 240 | Minutes an unbroken stretch of the agent's [background work](#background-work) keeps an otherwise idle session running, counted from its start (0 to 1,440; 0: background work never does). Applies to cloud and remote sessions at the next idle check. |

In `PUT /cloud/settings`, an absent transfer field, `permissionDeadlineMinutes` or file limit keeps its stored value, so a client written before they existed does not reset them; responses always carry them. On the dashboard form, an empty deadline means no deadline.

`expiresAt` is computed when the session pauses, from the setting in force at that moment; changing the setting applies to sessions paused afterwards, so shortening it never deletes existing work by surprise. Resuming clears it. At expiry the session is terminated with reason `expired` and its workspace deleted as below. The 7-day and 1-day expiry notices need the transcript and feed, and are planned.

The pause before a change of owner and the end of the former owner's access are not settings: they are what makes a transfer safe (see [transfer](#transfer)). The pending-input policy is copied onto the transfer when it is accepted, so a later change of the setting does not alter a transfer in progress.

## Workspace and proven deletion

Each session has one PersistentVolumeClaim, `tc-ws-<session>`, created before its first pod, kept while paused, and deleted at the end. Deleting a claim is not enough: the provider volume behind it (for example an OpenStack Cinder volume) must be gone too.

- **Refusing retention.** Publishing a profile checks the workspace storage class on the cluster and refuses one whose `reclaimPolicy` is not `Delete` (`422 storage_class_retains_volumes`), or a missing one (`422 storage_class_missing`). The reconciler checks again before creating a claim and fails the session with the same code, since the class can change after publication.
- **Proof.** When a session ends, the reconciler records the bound PersistentVolume name and the provider volume handle (for CSI volumes, `spec.csi.volumeHandle`), deletes the claim, waits until the claim is gone, then waits until the PersistentVolume is gone. With `reclaimPolicy: Delete`, the external provisioner removes the PersistentVolume only after the driver's `DeleteVolume` call succeeded on the provider, so its disappearance is the proof that the provider volume was deleted. `workspaceDeletion.state` becomes `proven` with `claimDeletedAt` and `volumeDeletedAt`; the handle stays on the session as evidence, and `cloud.session.workspace_deleted` is journaled.
- **Alerts.** A volume found with a non-`Delete` policy, in phase `Failed`, or still present one hour after its claim was deleted marks the deletion `blocked` with `volume_retained` or `volume_deletion_stalled`, rechecked every 10 minutes. The administrator deletes the provider volume and the PersistentVolume; the next check then proves the deletion.
- **Garbage collection.** For each cluster, a pass lists TeamCode-labelled pods and claims (`app.kubernetes.io/managed-by=teamcode` and the cluster id label, so another cluster record or server sharing a namespace is never touched) in the allowed namespaces and in any namespace that still holds a session not yet proven deleted, and the released or failed volumes of TeamCode workspaces, before reading which claims and current-epoch pods the database still accounts for. Objects are created only after their row commits, so this order never mistakes a fresh object for an orphan. Orphaned pods and claims are deleted; orphaned volumes (claim in one of those namespaces) that would not be deleted by their provisioner are counted in the cluster's `orphanedVolumes`, with `lastGarbageCollectionAt`. A scheduled worker runs it every 10 minutes on one replica.
- **Acceptance.** `CloudSessionPersistenceTest` verifies that no claim or volume remains after deletion with a fake cluster that models the provisioner. `KindSmokeTest` verifies it on a real cluster through the Kubernetes adapter; on OpenStack, the recorded handle can also be checked with `openstack volume show`.

## Pause and resume

1. `POST /pause` sets `desiredState = paused`. The reconciler moves `ready`/`active` to `pausing`; a checkpoint the runner sends first (it learns of the pause from its heartbeat) is accepted and makes the same move.
2. The runner's heartbeat response carries `desiredState` and `pauseDeadline` (10 minutes after the request, or immediate with `force: true`). The runner drains, stops its child processes, writes its checkpoint and calls `checkpoint {completed}`. Draining waits for the turn and for the agent's [background tasks](#background-work) (subagents, background commands, monitors: they die with the agent's process, and Claude Code does not restart them on `--resume`), including the turn in which Claude Code reports their end, until the deadline less a minute. Work still running then is stopped: the transcript gets a `status` event `{agent: "background_stopped", tasks: N}` and the checkpoint is `failed`, so the workspace is `crash_consistent`. Scheduled wake-ups are not waited for, since `--resume` restores them. `teamcode cloud pause` and `teamcode remote stop` say this, and `--force` stops at once.
3. The reconciler deletes the pod, confirms its deletion, ends the execution and marks the session `paused` with `consistent`.
4. A failed checkpoint, missed heartbeats or the 15-minute pausing deadline force-delete the pod: `paused` with `crash_consistent`. It is never advertised as `consistent`.
5. A resume during the pause (`POST /resume` or a waking message) is accepted, never refused. Before the runner's checkpoint, the reconciler cancels the pause: the session goes back to `ready` on the same pod and the runner, which learns it from its input long-poll, stops draining and takes messages again. Once the checkpoint is taken, the pod is going away anyway: the pause completes and the session resumes at once into the next execution. Cancelling saves the whole pause and resume (no new pod, no volume attachment, no image pull); waiting for an already checkpointed pause keeps the workspace consistent.
6. `POST /resume` rechecks the owner and assignment, then sets `desiredState = running`. The reconciler moves the session to `resuming`, waits for capacity, starts epoch n+1 on the same workspace with the pinned digest, and the runner's ready heartbeat makes it `ready`.

### Idle pause

A session that wants to run is paused after `idleTimeoutMinutes` without activity. Activity is:

- the last turn start or end, and the moment the session became `ready` (`activity.lastActivityAt`);
- a message or interrupt waiting for the agent (queued or delivered, not yet acknowledged), from when it was queued or last delivered: it counts once, not forever, so an input stuck on a broken runner does not keep a session running;
- an attachment lease: a member attached with `teamcode cloud attach` (or any client holding a lease) keeps the session running, and the end of the lease (detach or expiry) counts as the last activity;
- the agent's [background work](#background-work) (subagents, background commands, monitors, scheduled wake-ups), for at most `backgroundWorkMaxMinutes` after it started.

Only a `ready` session is a candidate: a turn in progress (`active`), a preparation, a resume or a transfer never is. The reconciler checks on its monitoring pass (every 15 s), reads leases and inputs only when the session row already looks idle, and commits an ordinary, non-forced pause (`desiredState = paused`, audit action `cloud.session.idle_paused`), so the session checkpoints and keeps its workspace. A message with `wake` (the default) resumes it.

The administrator sets the timeout per profile: the default `idleTimeoutMinutes` and the bounds a member may choose within (`minIdleTimeoutMinutes`, `maxIdleTimeoutMinutes`, 5 to 1,440 minutes). Ended attachment rows are kept as long as the longest timeout (a day), then purged with the transcripts.

Inactivity only pauses; it never deletes. The idle warning and `maxTurnMinutes` are planned.

#### Background work

A turn can end while the agent still has work in flight: a subagent started in the background, a `run_in_background` command, a `Monitor`, or a scheduled wake-up (`CronCreate`, `ScheduleWakeup`, `/loop`). The session is then `ready`, but pausing it stops the pod and kills that work, and a scheduled prompt cannot fire in a paused session. Capability `cloud.sessions.background-work.v1`.

- **What the runner reports.** Every heartbeat carries `background: true` while the agent has work in flight or wake-ups scheduled (only once the environment is ready). For Claude Code, the work in flight is the live set of its `background_tasks_changed` messages in stream-json, without the tasks Claude Code marks `ambient` (its own housekeeping) ([Agent SDK reference](https://code.claude.com/docs/en/agent-sdk/typescript#sdkbackgroundtaskschangedmessage)); scheduled wake-ups are not in that set, so the runner adds a `Stop` hook to the agent's settings (`teamcode cloud agent-state`) that hands the size of the hook input's `session_crons` to the runner over its environment socket at the end of each turn ([Stop input](https://code.claude.com/docs/en/hooks#stop-input)). Nothing else of the payload is read or kept. When the session's agent has the `teamcode_workflow` tool, the settings carry a second, independent `Stop` entry, `teamcode cloud workflow-stop`, which sends the agent of a workflow step back to work once if it stops without delivering or asking ([workflows](workflows.md#stop-hook)); it neither reads nor reports background work. Both counts start at zero with each agent process: Claude Code emits no task list at startup and does not restart background commands on `--resume` ([scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks#limitations)). Codex reports none.
- **What the server keeps.** The execution row records when the current (or last) unbroken stretch of heartbeats reporting background work began (`background_since`) and the last one that reported it (`background_seen_at`); only heartbeats write them. A heartbeat without background work leaves them, so the end of the work is known within a heartbeat.
- **How the idle pause counts it.** Background work counts as activity until its last report, but never later than `backgroundWorkMaxMinutes` (team setting, 240 by default, 0 to 1,440, 0 turning this off) after its stretch began; the idle timeout then runs as usual. A stuck subagent, a `tail -f` or a week-long `/loop` therefore keeps a session running for at most the cap plus the idle timeout. A gap (one heartbeat without background work) starts a new stretch. The reconciler reads the setting only once the session row already looks idle and the execution has reported background work.
- **Parity between the three kinds.** What keeps a session from the idle pause is the same wherever the agent runs. A Kubernetes cloud session and a remote session hosted on a member's device share the runner loop and the agent host: the same counts (live `background_tasks_changed` set without ambient tasks, plus `session_crons` from the `Stop` hook), the same `background` flag on the heartbeat, the same server rule (`backgroundWorkMaxMinutes`, then the idle timeout) and the same drain before a pause (up to the pause deadline). A local `teamcode run` is never idle-paused: nothing pauses it, its launch reports `working` while `background_tasks` or `session_crons` are non-empty ([agent sessions](agent-sessions.md#waiting-for-a-person)), and it holds the installation lease for the agent's whole lifetime, so an update waits for it. Remaining differences: a daemon-hosted remote session holds that lease (and so defers an update's service restart) only while background tasks are in flight, for at most four hours of one stretch, not for scheduled wake-ups (which `--resume` restores) and not by the team's `backgroundWorkMaxMinutes`; and a remote host on Windows has no Unix socket, so it reports no wake-ups (above). Codex reports none in either place.
- **Timed waits are not background work.** A pending [`time` or `event` wait](waits.md#waits-that-resolve-by-themselves) is held by the server, not by the pod: the session stays pausable, and the server's message resumes it when the wait resolves.
- **Limits.** The cap only governs the idle pause. An explicit pause, a transfer, the device daemon stopping (for example for `teamcode update`, see [updating while agent sessions run](distribution.md#updating-while-agent-sessions-run)) and the idle pause itself drain first: the agent gets until the pause deadline to finish its background tasks ([pause and resume](#pause-and-resume)). A deletion or a lost pod stops the work at once. A remote session reports both the same way: its host opens a private socket beside its records (`remote/<first 8 characters of the session id>.wake.sock`, removed when the host ends) that takes only the `wakeups <n>` line of the same `Stop` hook. Where Unix sockets do not exist (Windows) or the socket cannot be opened, the agent runs without the hook and its scheduled wake-ups are not reported, so a remote session whose agent has only a wake-up can be paused for inactivity there. A runner older than this field reports none, and a server older than it ignores it.

## Transfer

A session can change owner and keep its identity, workspace, transcript and executions. Capability `cloud.transfer.v1`.

### Who may transfer

- **Administrators** transfer any team session to any eligible member at once: the transfer is created `accepted`. With `TeamCode-On-Behalf-Of`, the delegated member is recorded as the transfer's effective member; the call is still authorized with the administrator's rights, as everywhere else. An administrator's transfer cancels a pending offer for the same session (`superseded`).
- **An owner who is not an administrator** can only offer their own session (`offered`), and only while `memberTransfers` is `offer`. The recipient, or an administrator, accepts or declines it within `transferOfferDays`; the owner can withdraw it until it is accepted. Switching `memberTransfers` to `disabled` also stops pending offers: a member can no longer accept one (`403 transfer_disabled`), an administrator still can. Acceptance keeps the offer's `resume` unless it sends one. Nobody can take a session they do not own: a member asking to transfer someone else's session gets `404`, and only the recipient or an administrator can accept.
- A session has at most one open transfer (`409 transfer_pending`). A session being created or prepared cannot be transferred (`409 session_preparing`): its preparation runs with the owner's credentials and recipe. An ended session cannot either (`409 session_not_running`).
- `POST /transfer` requires `Idempotency-Key`; a retry replays the transfer even after the session changed (`Idempotency-Replayed: true`).
- **Picking the recipient.** `GET /cloud/transfer-recipients` (capability `cloud.transfer.recipients.v1`) lists the members a session can be given to at all: the team's enabled members who completed password setup, the caller included, by username, at most 500, each with only `{id, username, administrator}` (no email, role name, state or anything else of the member). It answers whoever may request a transfer: administrators, and members while `memberTransfers` is `offer` (`403 transfer_disabled` otherwise, so a team that keeps transfers to administrators does not show members its directory); it needs an interactive login or a `cloud:write` key, like the transfer itself. A listed member can still be refused for a given session by the [recipient checks](#recipient-checks). The covering index `member_recipients (team_id, disabled, must_change_password, username, role, is_owner)` serves it: on 300,000 members (300 teams of 1,000), a team's page reads 500 index entries in 0.17 ms instead of filtering 625 rows of `member_username` after the lookup (1.2 ms).

Transfer states: `offered` → `accepted` → `completed`, or `declined`, `cancelled` (by a member, `superseded`, or because the session ended), `expired` (offers past their validity; a maintenance worker records it, and reads show such an offer as `expired` before it does), `failed` (the recipient was no longer eligible at the boundary, or `transfer_timeout`).

### Recipient checks

The recipient is checked when the transfer is requested, when it is accepted, and again by the reconciler right before the owner changes, on fresh data. A refusal at request or acceptance is `422 recipient_ineligible`, naming every problem code; a refusal at the boundary fails the transfer with that code and returns the session to `paused` for its former owner.

| Check | Code |
| --- | --- |
| A team member, enabled, password setup completed | `recipient_not_found`, `recipient_unavailable` |
| Assigned to the session's profile (administrators use every profile) | `profile_unassigned` |
| `create` under the [access policy](cloud-conversations.md#access), as for a creation on their behalf | `cloud_permission_denied` |
| The session's recorded agent model and effort against the team's model policy, exactly as inference will check them | `model_not_allowed`, `effort_not_allowed` |
| An inference allowance at all (a pool weight or daily allowance of zero refuses). Today's consumption is not checked: a transfer neither resets nor borrows allowances | `recipient_no_quota` |
| The retained-session cap, in the owner-change transaction under the recipient's member row lock | `cloud_session_limit` |

The checks are a list of `CloudRecipientCheck` ports. Environment variables, MCP servers and skills are delivered to cloud sessions by other branches (environment preparation, the MCP gateway and the skill catalog); their assignment checks (for example the profile's `requiredVariables` for the recipient) join this list when they are merged, without changing the transfer flow.

### The boundary: pause first, then change owner

**Decision.** The owner changes only at a paused boundary, never in a running pod. Accepting a transfer sets the desired state to `paused` (keeping `transferId` on the session); a running session drains and checkpoints exactly like an explicit pause (the running turn finishes, or is interrupted 60 s before the deadline; `force` pauses at once and leaves a crash-consistent workspace), the reconciler deletes the pod and confirms it is gone, and only a `paused` session moves to `transferring`. There, the reconciler deletes any pod of the session still listed by the cluster, ends any execution still open, rechecks the recipient, and commits the change in one transaction. The next execution is a new epoch, started for the recipient, by `resume` on the transfer (or the acceptance) or later by the recipient.

**Why.** Everything that acts for the owner inside a pod is bound to that pod or was resolved for the owner when it started: the agent process and its memory, the Git and GitHub credentials and the variable values the runner fetched for the owner, MCP credentials, and the pod's projected token. None of it can be proven revoked while the process lives, and the agent may have copied a credential into a child process. Ending the execution is the only revocation that holds, and the epoch fence already guarantees that nothing of an ended epoch can call the server again. The other options were set aside:

- *Live hand-off in the running pod* (rotate credentials, keep the process): the former owner's credentials stay in the process and its children, and the work in progress would be billed partly to one member and partly to the other within one turn.
- *Cancel the turn and transfer at once*: loses the running turn's work for no gain over `force`, which administrators can already ask for.
- *Refuse transfers of running sessions*: pushes the pause onto every caller (an orchestrator would have to pause, poll and transfer), with a race between the pause and someone resuming it.

The cost is the drain (bounded by the pause deadline) and one pod restart. The workspace, the transcript and, for agents that support it, the conversation (resumed by id) are kept, so the recipient continues the same session.

While a transfer is accepted and not finished, an explicit resume is refused (`409 session_transferring`), a message never wakes the session, and a new transfer is refused. Deleting the session cancels the transfer. `transferring` is bounded: the reconciler checks a 30-minute deadline, counted from the moment the session entered it (`cloud.transfer.started`), before any cluster call; past it (a cluster that never confirms the pod deletion), the transfer fails with `transfer_timeout` and the session returns to `paused` for its former owner, who can offer it again.

A message sent or an attachment requested by a member authorized against the former owner can race with the owner change: both lock the session row and refuse with `409 session_busy` when its owner is no longer the one they were authorized against, so nothing is queued or leased for the old owner after the change.

### What changes at the boundary

In the owner-change transaction:

- `ownerId` becomes the recipient; the transfer becomes `completed` with `atEpoch` (the last epoch run for the former owner) and `eventSeq`.
- Every attachment lease of the session is removed. The former owner's `attach` stops at its next renewal, and their transcript stream ends with `event: denied` at its next access check.
- Messages not yet consumed follow the transfer's `pendingInputs`: `cancel` marks them `cancelled` with reason `transferred` (each with its `input` transcript event), `keep` queues them for the recipient's next execution. Wake requests are cleared either way: with `keep`, a former owner's message is delivered to the recipient's agent when the recipient resumes the session (or at once with `resume`), but it never resumes the session by itself.
- A server-written `transfer` event `{transferId, fromMemberId, toMemberId, atEpoch}` is appended to the transcript.
- `cloud.session.transferred` is journaled with the initiator, the recipient and the former owner.
- Without `resume`, the session stays `paused` and its expiry restarts from the recipient's full paused retention. With `resume`, it moves to `resuming` and starts for the recipient.

After it, the former owner has no owner rights on the session (it is a `404` for them), unless the team's access policy grants them access to other members' sessions. The recipient sees the whole history.

### Former-owner credentials

- **Pod and execution.** No pod of the session exists after the boundary, and every execution of the former owner ended; their projected tokens are fenced by epoch. Their `tcex_` inference credentials were deleted when their execution ended (the pause before the boundary), and the owner-change transaction deletes any credential of the session again.
- **Git, GitHub and variables.** The environment branch resolves the Git identity, the GitHub user token and the variable values for the session's current owner on every runner `environment` call, which only the registered runner of the current epoch can make. After a transfer, that is the recipient's first execution. Nothing of the former owner's is stored with the session or in the pod spec. The runner's credential helper and `GH_TOKEN` live in memory and in child-process environments of the ended pod only, and the agent's `gh` configuration in that pod's memory volume, which ends with it. The recipient's runner writes the recipient's token, or only the not-linked notice when the recipient has no usable link: `gh` is then unauthenticated, never the former owner's. A `gh` login the agent made itself under `$HOME` is ignored, since `GH_CONFIG_DIR` points `gh` elsewhere.
- **Attachments.** Removed in the transaction.
- **Who the agent is told it runs for.** The agent's instructions name the owner (`I am <username>[, known as <login> on GitHub].`, see [artifacts](artifacts.md)), read from `POST /cloud/runner/agent` at each execution start: the recipient's first execution names the recipient, as its `gh` uses the recipient's account. A resumed conversation that was told the former owner gets the recipient's sentence before its next message, since Codex keeps a thread's first developer instructions.
- **Workspace content.** The workspace is transferred as it is: that is the point of a transfer. Files the former owner (or their agent) wrote there belong to the session. Credentials never reach the workspace through TeamCode, but a secret that a member typed into a file goes with the session.
- **Untrusted until the recipient prepared it.** Content the former owner left must not run with the recipient's credentials without a word. `POST /cloud/runner/environment` returns `untrustedWorkspace: true` while another member's execution ran on the workspace after the current owner's last execution that reached `ready` (an execution recorded before transfers existed counts as the creator's, and a history longer than the 100 executions read is untrusted). The runner then resets the workspace first (`securing_workspace`), before the Git identity, a fetch or a setup command, in the agent's container:
  - **Agent home.** `/workspace/.agent-home` moves to `/workspace/.teamcode/quarantine/agent-home` (replacing the previous quarantine) and starts over empty: settings and hooks (`.claude/settings.json`, `.claude.json`, `.codex/config.toml`), MCP servers, plugins, shell profiles and `.gitconfig` never carry over. Only the conversation transcripts move back (`.claude/projects`, `.codex/sessions`, plain directories only), so the recipient's agent resumes the conversation.
  - **Repositories.** In each recipe repository, `.git` must be a plain directory without `commondir` (a link or a gitfile fails the step `workspace`). Its `config`, `config.worktree` and `hooks` move to `/workspace/.teamcode/quarantine/repository-<n>`, and a new `config` keeps only the repository format, its `extensions.*` and each branch's `origin` tracking, with `origin` set to the recipe's URL and the standard refspec: an `uploadpack` command, a credential helper, a proxy, `sslVerify`, `insteadOf`, an extra remote or a hook never runs with the recipient's token. The working tree, the index, the refs and the objects are untouched.
  - **What stays the former owner's.** Files in the working tree are not reviewed: package scripts that a setup command runs (`npm ci`), a `Makefile`, a project's `.claude/settings.json` committed or not, or a prompt left in a file run or are read by the recipient's agent with the recipient's GitHub token, variables and inference. Accepting a session means continuing someone else's work: review what you resume, as you would a branch from a colleague before running it. `teamcode cloud transfers accept` says so on every acceptance, and the API reference of the accept route too.

### Attribution and billing

Each execution records the owner it ran for (`ownerId` in `GET /cloud/sessions/{id}/executions`). Work of an execution (inference through its `tcex_` credential, which is issued for `ownerId`, and pod time) is attributed to that member, so the former owner's executions stay theirs and the recipient's start at `atEpoch + 1`. Transcript events carry their epoch, and `message.user` events their author, so history remains attributable after the change. Usage already recorded in the ledger is never moved, and allowances are neither reset nor transferred.

## The runner and the pod

- **Pod.** One bare pod per execution, `tc-<session>-e<epoch>`, `restartPolicy: Never`, labelled `app.kubernetes.io/managed-by=teamcode` with the session, cluster and epoch, created only after the namespace's [session network policy](#session-network-policy) (no ingress; full internet access, cluster-internal and metadata endpoints blocked). Non-root (GID/fsGroup 1000, `runAsNonRoot`), `seccompProfile: RuntimeDefault`, no privilege escalation, all capabilities dropped, `automountServiceAccountToken: false`, no service links, no shared process namespace. Two containers from the team image share the workspace claim (`/workspace`), a memory-backed `emptyDir` at `/run/teamcode` that holds two sockets, and a memory-backed `emptyDir` at `/run/teamcode-gh` for the agent's [`gh` configuration](#github-cli) (read-only in `agent`), a disk-backed `emptyDir` `uploads` (`sizeLimit: 1Gi`) at `/var/teamcode/uploads` for the [files of members' messages](cloud-conversations.md#files) (read-write in `session`, read-only in `agent`), and nothing else:
  - `session` is the runner, UID 1000. Its `HOME` is `/var/teamcode/runner-home`, an `emptyDir` only its container mounts, so nothing the agent writes on the workspace steers it; its state (the agent's conversation id) stays in `/workspace/.home/.teamcode/cloud-agent.json`, which it alone reads and writes. It alone mounts the projected token and holds every server credential, and it runs no command of its own: preparation commands run in the agent's container. It has fixed small resources (250m CPU, 256Mi).
  - `agent` runs the exec supervisor, UID 1001 (`HOME=/workspace/.agent-home`, which its UID creates on the volume so agent state survives pauses). It has no token, no server URL and no session identifier in its environment, and it gets the profile's CPU and memory requests and limits.
  The two UIDs must differ (`KubernetesPodOptions` refuses equal or root UIDs). Both are in group 1000, so the workspace is shared; the runner's own files are private to it. The pod's total resources are the profile's plus the runner's.
- **Delivery.** An init container from the runtime's runner image copies the `teamcode` Linux binary (the runtime's binary path, default `/usr/local/bin/teamcode`) into an `emptyDir` at `/opt/teamcode`, with `cp`; the `session` container runs `/opt/teamcode/teamcode cloud runner` and the `agent` container `/opt/teamcode/teamcode cloud agent-supervisor`; the copied file must be executable by other users (mode 0755 in the runner image), since the agent's UID runs it. The team image stays a pure toolchain (Linux with the published binaries' glibc baseline, `/bin/sh`, `git`, usable by UIDs 1000 and 1001), plus the agent CLIs; see the [image contract](#image).
- **Identity.** A projected ServiceAccount token, audience `teamcode`, 600 s expiry (the API minimum; the kubelet rotates the file, and the runner reads it for every call). The server reviews it with `TokenReview` using the cluster credential and requires the bound namespace to be the session's and the bound pod name to be the current execution's pod; the pod name always comes from the review, never from the request. A pod of the session with another epoch gets `409 execution_fenced` and exits. Reviews are cached 60 s per token (refusals 10 s, in a separate cache so bad tokens never evict accepted ones), so a heartbeat every 15 s costs one review a minute per pod. No TeamCode secret exists in the cluster, and the pod environment holds only the server URL, the token file path and the team, session and epoch identifiers.
- **Channel.** HTTPS only (the client refuses plain HTTP except on loopback): register, heartbeat every 15 s (the response carries the desired state and pause deadline), checkpoint; later batched event upload and an input long-poll. It fits stateless replicas with MySQL as the only bus and needs no inbound connectivity to the pod. Network failures are retried with backoff; the server marks the execution lost after 90 s without heartbeats.
- **Runner.** This release's runner starts no agent: it registers, [prepares the environment](#environment-preparation) while heartbeating, reports ready once prepared, and checkpoints immediately when a pause is requested (there is nothing to drain yet). It exits on `409 execution_fenced` or when the session is being deleted, retries any other `409` (for example a checkpoint refused because the pause was cancelled), and exits with code 2 on `401`. The client reads only the error code of a failed runner call, never its message.
- **Token exposure.** The projected token is mounted in the runner's container only, which the agent shares neither by mount nor by process namespace. The agent cannot call the runner channel (report a clean checkpoint, fetch a `tcex_` credential) and cannot read the runner's memory, environment or files.
- **Exec supervisor.** `teamcode cloud agent-supervisor` is the agent container's entrypoint. It listens on `/run/teamcode/agent.sock` (mode 0660, created under a narrowed umask so it is never wider) and starts what the runner asks for, as its own UID: the agent and the [environment preparation](#environment-preparation) commands. The protocol is one JSON line per message on a connection per process: `start` (command, arguments, environment overrides with removals, directory), then `in`, `close` and `stop` from the runner and `out` and `exit` back; a failed start answers `error` and the runner sees exit code 127. A `hold` connection is the runner's lifeline: the supervisor stops every process and exits when it closes (so the pod ends when the runner does, whatever its exit code), and exits with 1 if the runner never connects within two minutes. A connection that drops stops its process. The runner retries the connection for a minute while the agent container starts, and never falls back to running the agent in its own container: when the socket is configured and unreachable, the agent does not start (`agent_start_failed`). Anything holding the socket's group can use it, which is only the two containers.
- **Credential socket.** The runner serves `/run/teamcode/credential.sock` (same mode). The agent container carries `GIT_CONFIG_*` variables that set `credential.helper` to `teamcode cloud credential`, which implements git's helper protocol: `get` sends the remote git describes (protocol, host, path) and prints the one credential the runner answers, `store` and `erase` do nothing, and without a socket, a host or a credential it prints nothing and succeeds so git moves on (`GIT_TERMINAL_PROMPT=0` keeps it from asking). The runner asks its token sources in order, each answering only for the hosts it owns, with a 15 s limit per request and at most 8 at once; a source that fails is logged without its message and skipped. The one source is GitHub: for `https://github.com` only, it returns `x-access-token` and the token of the member the current execution runs for, fetched with `POST /cloud/runner/github` when first asked and again five minutes before it expires, kept in the runner's memory only. Without a linked account it answers nothing (public repositories clone anonymously) and the server is not asked again for 30 seconds. The same source feeds the agent's `gh`, below.
- <a id="agent-variables"></a>**Environment variables for the agent.** The agent starts with the owner's variables in its environment, read with `POST /cloud/runner/variables` at each agent start (Claude Code and Codex alike; names the agent's own settings use are dropped, and TeamCode's settings are applied after them). For Claude Code the runner also serves `/run/teamcode/environment.sock` (same mode) and writes `/run/teamcode/agent-env.sh`, a script with no value, which the agent receives as `CLAUDE_ENV_FILE`: Claude Code reads it once and runs it before every Bash command, and it runs `teamcode cloud environment --socket /run/teamcode/environment.sock`, which prints `export`/`unset` lines for the current owner. The runner keeps the variables in memory and asks the server again when a command needs them and its last answer is older than 30 seconds (a command waits at most 3 seconds, then runs with the last values; a failed read is retried after 15 seconds; a fenced execution serves nothing, and a server without the route is not asked again). So a variable rotated, added or removed while the session runs reaches the next Bash command within 30 seconds, a removed one is unset, and an idle session costs no request. Values never reach the pod spec, a file, the workspace, the pod log or the transcript; the agent can read them, as they are its own. Codex has no equivalent of `CLAUDE_ENV_FILE`: it gets the values of its start, and a change reaches it when the agent process starts again. The process environment of a running agent (and of its MCP servers and hooks) is not updated either; only its Bash commands are.
- <a id="github-cli"></a>**GitHub CLI.** The agent container's environment sets `GH_CONFIG_DIR=/run/teamcode-gh`, a path and not a token. That directory is its own memory-backed `emptyDir` (1Mi): the runner (`TEAMCODE_GH_CONFIG_DIR`) mounts it read-write and writes one file, `hosts.yml`, with the execution owner's token and linked login for `github.com` (HTTPS), and the agent mounts it read-only. The runner writes it once preparation succeeds and before the agent starts, rewrites it (atomically) whenever the GitHub source renews the token, five minutes before it expires, removes it when the owner has no usable link (asking the server again every five minutes, so a link made during the session is picked up; the runner logs it once per streak, and leaves `TEAMCODE-GITHUB-NOT-LINKED.txt` in the directory, a notice without any token that tells the agent why `gh` is signed out and that the owner runs `teamcode github link` or links GitHub in the companion or on the dashboard), and removes both files before it exits. After a failed renewal the last token stays until it expires and is then removed (retried after 30 s, then every five minutes, logged once per streak without the cause). A token or login outside GitHub's alphabet is not written (logged once, without the value); logins are quoted. The file has the runner's default mode: the volume is mounted in the pod's two containers only. Because `gh` reads its configuration directory on every run, it is authenticated however the agent starts it: by name or by absolute path, from a login or interactive shell whose profile resets `PATH`, through `bash -c`, `xargs`, `make`, npm scripts, git aliases or a long-lived shell, and `gh auth git-credential` (which `gh repo clone` and other `gh` git calls use) answers with the same token as the runner's git helper. Without a usable link the directory holds only that notice and `gh` behaves as unauthenticated `gh` (`gh auth status`: "You are not logged into any GitHub hosts"). The directory is read-only for the agent, so `gh auth login`, `gh config set` and `gh alias set` fail there; set such options per command or with environment variables instead. The agent can read the token, as it can already ask the credential socket for it; it cannot replace it, and the token is never in the pod spec, the image, a container's base environment or the workspace. `gh` is optional in the image: without it nothing changes. `GH_HOST` and GitHub Enterprise are not configured.
- **Planned.** A one-time Secret fallback where `TokenReview` is not permitted.
- **Kubernetes client.** The adapter (`KubernetesClusterPort`) calls the Kubernetes REST API with the Ktor client the server already uses, rather than fabric8 or the official Java client. The surface is small (pods, claims, volumes, storage classes, TokenReview), the server stores each cluster's URL, CA and token instead of a kubeconfig, and the adapter is tested with Ktor's mock engine. Each cluster gets its own client whose trust store holds only that cluster's CA bundle; the connection is reloaded from the database at most every 30 s, so a rotated token applies quickly. Lists are paged (500 per page, at most 20 pages, 200 for the cluster-wide PersistentVolume list); a page missing mid-list fails the call rather than passing for a complete list. Concurrent first uses of a cluster build one client, and a client replaced after a rotation stays open until shutdown for requests in flight. API error bodies are never kept or logged. It adds no dependency, and nothing reaches the native CLI, which keeps `cli -> client -> api`.

## Environment preparation

Toolchain and preparation are separate. The **image** carries what is installed (for example Node.js, a JDK, Gradle); the **recipe** says what to do with it in each session. Neither contains a TeamCode or provider credential.

### Image

- **Per profile, per session.** The profile names the image; a session may name another one only if it matches the profile's `allowedImageOverrides`. Private registries authenticate through the profile's `imagePullSecrets`, Kubernetes Secrets the administrator manages in the namespace; TeamCode never stores registry credentials.
- **Digest.** The digest of the first running container is recorded on the session (`image.digest`) and on the execution; every later execution starts `reference@digest`, so a resume prepares on the same bits even if the tag moved.
- **Template.** [Cloud session image](cloud-session-image.md) gives a Dockerfile that meets this contract, with one block for your tools; the same image can also be the runner image.
- **Contract.** Linux with the published binaries' glibc baseline, `/bin/sh` and POSIX `mkdir`, `rm`, `mv`, `rmdir`, `dirname`, `touch`, `test`; `git` 2.31 or later (credentials are configured through `GIT_CONFIG_COUNT`); the runtime libraries of the copied `teamcode` binary (`libcrypt.so.1`, `libcrypto` 3, libcurl, zlib), which both containers run; writable by UID 1000 and usable by UID 1001 (the agent); the agent CLIs (`claude`, `codex`) on `PATH`, installed outside any home directory. `gh` is optional. No TeamCode binary is required: the runner binary is copied in by the init container. [Cloud session image](cloud-session-image.md) details each point.
- **No baked identity.** Nothing in the pod spec identifies a member or a provider account: the pod environment holds only the server URL, the token file path and the team, session and epoch identifiers. Credentials reach the pod only through the runner channel, at preparation time, for the current owner.

### Recipe

The recipe is part of the immutable profile version (`spec.environment`). At creation, the session's `environment` overrides are merged in and the result is stored on the session (`cloud_sessions.environment`, JSON without any secret), so a resume prepares exactly what the first execution did, even after the profile changed. It is never edited afterwards.

| Field | Meaning |
| --- | --- |
| `repositories` | Up to 16 `{url, path, ref?, branch?}`. `https://` URLs without credentials, query or fragment; `path` relative to `/workspace` (not under `.teamcode` or `.home`, never nested in another repository); `ref` is a branch, tag or commit; `branch` is a local branch created at `ref`. Option-like and malformed refs are refused |
| `workingDirectory` | Relative to `/workspace`; must exist after cloning. Setup commands run there |
| `setup.create` | Up to 16 commands run once per workspace, in order, with `/bin/sh -c` |
| `setup.start` | Up to 16 commands run on every execution, after `create` |
| `requiredVariables` | Variable names the owner must be assigned; preparation fails without them |
| `requireGitHub` | Preparation fails when the owner has no usable GitHub access |
| `gitEmailDomain` | Email domain of the Git identity for owners without a linked GitHub account |
| `repositoryHosts` | Hosts repositories may be cloned from, `["github.com"]` by default; session repositories are checked against the profile's list, so a request cannot point the pod at metadata or cluster-internal endpoints |

A session that replaces the repositories while the profile's working directory is not inside any of them must set `workingDirectory` too (`400 invalid_environment`), rather than failing in the pod after a full clone.

### What the runner does

After registering, the runner prepares while it keeps heartbeating (`ready: false`), so a long clone or dependency install never looks like a lost pod:

1. `POST /cloud/runner/environment` returns the recipe and, resolved for the **current owner** on every call: the Git identity, the variable values and the GitHub token. A transferred session therefore never keeps its former owner's values.
0. **Untrusted workspace** (`securing_workspace`, step `workspace`): after a transfer, the agent's home and each repository's Git configuration are reset first, see [former-owner credentials](#former-owner-credentials).
2. **Git identity** (`configuring_git`): `git config --global user.name/user.email` in the agent's home (`HOME=/workspace/.agent-home`), so the agent commits as the owner, rewritten on every execution. A linked GitHub account gives `<login>` and `<id>+<login>@users.noreply.github.com`; otherwise the member name and `<name>@<gitEmailDomain>` (`users.noreply.teamcode.invalid` by default).
3. **Repositories.** If `/workspace/<path>/.git` exists, only `git fetch --prune origin` (`fetching_repositories`): work on the workspace is never reset or re-cloned. Otherwise (`cloning_repositories`) clone into `/workspace/.teamcode/clone-<n>`, check out `ref`, create `branch`, then move it into place; an interrupted clone is cleaned and retried, and a non-empty directory at the path is never overwritten.
4. The **working directory** must exist.
5. **Setup** (`running_setup`): each `create` command whose marker `/workspace/.teamcode/setup/create-<n>-<hash>.done` is missing (the hash is the command's, so an edited command runs again on a new session), then every `start` command.
6. The next heartbeat reports `ready: true`, and only then does the session become `ready`.

**Where commands run.** Every preparation command runs in the `agent` container, started through the exec supervisor under the agent's UID, never in the runner's container: the workspace is written by the agent (which may be prompt-injected), so a repository's Git configuration or a dependency's install script must never run where the projected token is mounted. Every `git` the preparation runs gets `-c core.hooksPath=/dev/null -c core.fsmonitor=false -c protocol.allow=never -c protocol.https.allow=always -c fetch.recurseSubmodules=false -c submodule.recurse=false -c credential.helper=`, then the runner's own helper: no hook, no fsmonitor, HTTPS only, no submodule and no other credential helper, whatever the repository or the agent's home configure. A repository's `remote.<name>.uploadpack` cannot be overridden with `-c` (Git keeps the first value): HTTPS-only transport, and the reset of a transferred repository, are what keep it from running.

Command output (stdout and stderr) goes to `/workspace/.teamcode/logs/prepare-e<epoch>.log` on the session's own workspace and never reaches the server, the pod log or the transcript. It comes back to the runner over the supervisor's socket; the runner replaces known variable values and the token by `[REDACTED]` in each line before handing it to `teamcode cloud preparation-log`, a writer it starts in the agent's container, which appends it and keeps the last 4 MiB. The runner never opens the file itself, which the agent could have replaced by a link. Masking is best effort: transformed values (base64, URL-encoded) are not recognized. Setup commands must not print credentials. A runner without an agent container (started by hand) runs the commands itself and masks the file after each command, as before.

A runner error (unwritable or full workspace) is reported as step `runner` right away instead of waiting for the preparation timeout, and a runner that stops heartbeating while it prepares a resume is lost after 90 seconds, as during a first preparation.

### Credentials in child processes only

Variable values and the GitHub token live in the runner's memory and in the environment of the preparation's child processes. The runner never writes them to the pod spec, a Kubernetes Secret, a remote URL, a Git config file, the workspace or the server's database (see the log caveat above):

- `git` gets the token from a credential helper defined through `GIT_CONFIG_COUNT` for `https://github.com` only (helpers from the image are reset first), which prints `x-access-token` and the token from its own environment; other hosts never see it. The preparation's own `git` commands also reset every helper with `-c credential.helper=` and add this one back, so a helper from the repository never runs for another host either.
- `gh` reads `GH_TOKEN`.
- `GIT_TERMINAL_PROMPT=0`, and children do not inherit the runner's token file path.
- Owner variables never steer the runner's own commands: names that are not shell identifiers, and `PATH`, `HOME`, `SHELL`, `IFS`, `ENV`, `BASH_ENV`, `XDG_CONFIG_HOME` and the `LD_`, `DYLD_`, `GIT_`, `GH_`, `SSH_`, `TEAMCODE_` prefixes, are dropped (by name, in the pod log). The variants work refuses most of them at definition already.

The child processes run in the agent's container under the agent's UID, which can already read the owner's GitHub token (through `gh`) and variables: they get nothing the agent does not have, and never the runner's token. See the token exposure note in [the runner and the pod](#the-runner-and-the-pod).

### Variables and GitHub sources

- **Variables** come from `CloudVariableSource`. Its source is the environment/MCP variants (`ResolveCloudVariablesUseCase` over `ResolveEffectiveVariantsUseCase`, environment entries only, `unavailable` slots by name), resolved for the session owner at every preparation, so a rotation, an exclusion or a transfer applies at the next start or resume, and served to the running agent by `POST /cloud/runner/variables` ([agent variables](#agent-variables)). A member without an assignment receives none, and a profile with `requiredVariables` fails preparation with the missing names.
- **GitHub** comes from `GitHubAccessSource`, implemented on the members' links (see [GitHub access](#github-access)): the owner's GitHub App user-to-server token, refreshed on the server, scoped to what both the App installation and the owner can reach. An owner without a usable link gets `not_linked`: public repositories clone anonymously and `requireGitHub` profiles fail preparation. Installation tokens and personal access tokens are never handed to a session.

### Progress and failures

`phase` shows `securing_workspace` (after a transfer), `configuring_git`, `cloning_repositories`, `fetching_repositories` or `running_setup`. A failed step is reported as `{step, index, exitCode}` only; the server writes the message (for example "Cloning https://github.com/example/api.git into api failed (exit code 128). Private repositories need the owner's GitHub access."), so no command output or runner text reaches the API. The session gets `failure.code = preparation_failed`, is never reported ready, and the reconciler then stops the pod and:

- on the first execution, fails the session and deletes its workspace;
- on a resume, returns the session to `paused` with `resumeBlocked = preparation_failed` and keeps the workspace.

Clone, fetch and GitHub failures are `retryable`; setup, path and `workspace` (a transferred repository whose `.git` is not a plain directory) failures are not. The 30-minute preparation timeout applies to resumes too once the runner registered.

## GitHub access

Each member links their own GitHub account to the team's GitHub App. The link gives **only that member's cloud sessions** Git and `gh` access, with the member's own permissions intersected with the App installation's; it serves no other purpose (the skill catalog is published from CI, not synchronized from GitHub). The token is handed out on one path only: `POST /cloud/runner/environment`, to the registered runner of the current epoch of a session the member owns, resolved for the current owner on every call. No other API returns it, and it is never logged, journaled or written to the session.

### Who instructs an agent that holds the token

The agent does what its messages say, including running `gh auth token` or printing the credential it was handed. Anyone who can message a session can therefore use, or read, its owner's token. Each session has a **GitHub access** mode, shown as `githubAccess` in the session view and in `teamcode cloud show` (`cloud.sessions.github-access.v1`):

- `owner` (the default for a session the member created): the owner's token; while the owner has linked GitHub, only the owner sends messages, uploads files and answers permission requests (`403 github_owner_only` for everyone else, cloud administrators and team-scope `message` grants included). Interrupts and bare denials of a permission request (no message, no answers) stay open to everyone with `message`: they only stop something. An owner without a GitHub link has no token to expose, and the session behaves as before. Delivery checks again: a non-owner's message accepted while the owner had no link, or while the session was shared, is rejected (`github_owner_only` on the input) instead of reaching an agent that now holds the token.
- `shared`: the owner's token, instructed by everyone the access policy lets message the session. The owner chooses it, knowing they lend their GitHub access.
- `none`: no GitHub token (`not_linked` for the runner, no token at preparation). A session **created on someone's behalf** (`TeamCode-On-Behalf-Of`) starts here: its first instructions are the creator's, not the owner's. Creating one on a profile that requires GitHub is refused (`422 github_owner_consent`); the owner creates that session themselves.

`PUT /cloud/sessions/{id}/github` with `{"access": "owner" | "shared" | "none"}`, or `teamcode cloud github SESSION --access MODE`, changes it. Only the owner, signed in or with their own key, never on their behalf (`403 github_owner_only`); another member gets `404`. Turning access on for a session someone else created hands your token to an agent whose conversation and workspace hold what they asked for: read its transcript first (the CLI says so). Instructions the agent already consumed stay in its context; for a fresh start, create a new session. With `owner`, other members' messages the agent has not read yet are acknowledged as failed (`github_owner_only`) instead of delivered, an interrupt or a bare denial excepted; `shared` lets the agent act on them. A profile that requires GitHub cannot be set to `none` (`422 github_required`). Turning access off (`none`) waits for a pause (`409 session_not_paused`), because a running agent keeps a token it already received until it expires; turning it on or sharing applies from the next token renewal and the next message. A transfer resets `shared` to `owner`: the former owner's choice does not lend the recipient's token. Each change is journaled as `cloud.session.github_access_changed`. Sessions that existed before this version are `owner`, including those created on someone's behalf. Remote sessions run on the owner's device with its own credentials and have no mode.

### The team's App (administrator)

Create a GitHub App owned by the organization:

- **User-to-server token expiration** enabled (the default): 8-hour access tokens, 6-month rotating refresh tokens.
- **Repository permissions** the sessions need, for example Contents and Pull requests: read and write; Metadata: read. No organization or account permissions are required.
- **Callback URL**: `<TEAMCODE_PUBLIC_URL>/dashboard/github/callback` (shown on the dashboard and in `GET /github/app`).
- **Enable Device Flow** for `teamcode github link`; without it members link from the dashboard.
- Install it on the repositories sessions may reach.

Then save the App id, client id, client secret and private key on **Dashboard → GitHub** (`/dashboard/github`) or with `PUT /api/v1/github/app`. Before storing anything the server signs a JWT with the private key and reads `GET /app`: the key must belong to that App id and client id (`422 github_app_rejected`, `422 github_app_mismatch`). Only GitHub App client ids (`Iv...`) are accepted; an OAuth App's tokens (`gho_`) are refused at link time. The client secret and key are encrypted at rest; an update may omit them to keep the stored ones, except when the client id changes. `version` is required to update (`409 github_app_conflict`). Replacing the App (another client id) deletes the links made with the previous one, which it could never refresh again, and revokes their access tokens with the previous App's credentials; members link again.

### Linking (member)

- **CLI, device flow.** `teamcode github link` asks the server to start GitHub's device flow and prints the verification URL and user code. The member enters it on github.com; the CLI polls `POST /github/link/device/{id}` at the interval GitHub asked for. The server asks GitHub at most once per interval whatever the client's pace: the next poll time is moved with a compare-and-set before GitHub is called, so concurrent polls and GitHub errors do not shorten it. It honors `slow_down`, and stores the device code encrypted; the attempt expires with GitHub's code (15 minutes at most) and is single-use. The token exchange happens on the server: the CLI never sees a GitHub token.
- **Dashboard, web flow.** **Link GitHub** on `/dashboard/github` starts an authorization with `state` and PKCE (S256) and sets a browser-binding cookie (`HttpOnly`, `SameSite=Lax`, path `/dashboard/github/callback`, 10 minutes). The callback runs without the strict session cookie (GitHub's redirect is cross-site), so it is authenticated by the single-use state, whose hash identifies the attempt and its member, and by that cookie: a link sent to someone else cannot bind their GitHub authorization to the sender's member (`403 github_link_browser_mismatch`).
- One GitHub account per member and per team (`409 github_account_in_use`; the fresh token is revoked). Linking again replaces the member's link. Disabled members and members awaiting a password change cannot link.
- Device-flow phishing is inherent to the flow: a member must enter only codes their own `teamcode github link` printed. GitHub shows the App's name on the authorization page.

### Refresh and revocation

- A token that expires within an hour is refreshed before it is handed out. The refresh is serialized like provider accounts: the right to spend the rotating refresh token (`refresh_pending`, start time) is committed before GitHub is called, and an owner silent for 60 s is taken over. Other callers get the current token if it stays valid for more than 5 minutes, and otherwise wait for the owner (up to 20 s, then `unavailable`). The owner writes only if it still holds the claim (same token version and start time), so a relink, an unlink or a takeover is never overwritten; a token refreshed by a fenced owner is revoked. A refreshed pair that cannot be saved because of a database error is retried three times and the new token is still handed out.
- GitHub refusing the refresh token (`bad_refresh_token`: revoked by the member on GitHub, expired or already used) marks the link `reconnect_required`: sessions get `not_linked` until the member links again. Any other failure (GitHub unreachable, wrong client secret) keeps the tokens for a later attempt; the session gets the current token while it is valid for more than 5 minutes, `unavailable` otherwise. Limit: GitHub rotates the refresh token as soon as it processes the request, so a response lost in transit (timeout after the request reached GitHub) or tokens that could not be saved leave a spent refresh token, and the next refresh ends the link: the member links again. GitHub offers no way to recover that pair.
- **Unlink** (`teamcode github unlink`, dashboard, `DELETE /github/link`; administrators `DELETE /github/links/{memberId}`) deletes the link and pending attempts in one transaction, then revokes the access token at GitHub (`DELETE /applications/{client_id}/token`, best effort, only with the App that issued it). The member's authorization of the App stays on GitHub, where only they manage it; TeamCode no longer holds any token for it. Members deleted from the team lose their link with them.
- Journaled actions: `github.app.saved`, `github.link.created` and `github.link.removed` (actor, member as subject and effective member), and `github.link.reconnect_required` when a link ends without anyone asking (the member as actor and subject, details `{"reason":"refresh_rejected"}` when GitHub refused the refresh token, `{"reason":"refresh_expired"}` when the refresh token had expired or was missing and the access token is spent; never a token), so an administrator reading `GET /api/v1/audit` sees when a member's sessions lost `git` and `gh` access. Successful refreshes are not journaled. Each refresh the server asks GitHub for logs one line, `TeamCode github refresh member=<id> outcome=<outcome>`, with `refreshed`, `refreshed_unsaved` (GitHub rotated the tokens but the database kept failing: the next refresh will end the link), `refreshed_fenced` (a relink, an unlink or a takeover won; the new token is revoked), `rejected` (`bad_refresh_token`), `failed cause=<timeout, error code or exception class>` or `cancelled`; never a token, a GitHub body or an exception message.

### Routes under `/api/v1/github`

Advertised by `github.link.v1` whenever the server offers GitHub links, so `teamcode github status` and `unlink` keep working while cloud sessions are off. While they are off, starting a new link answers `404` (polling a device link already started still completes it); reading and removing one's own link still work (`GET`/`DELETE /github/link`, and the dashboard's GitHub page, which stays in every member's menu). Interactive logins only: service and CI keys are refused.

| --- | --- | --- |
| `GET /github/app` | `{configured, appId, clientId, slug, name, version, updatedAt, callbackUrl}`; never the secret or key | Administrator |
| `PUT /github/app` | `{appId, clientId, clientSecret?, privateKey?, version?}`; verified with GitHub first | Administrator |
| `GET /github/link` | The caller's link: `{memberId, state, appConfigured, login, userId, linkedAt, refreshedAt, accessExpiresAt}`, `state` is `not_linked`, `linked` or `reconnect_required` | Member |
| `DELETE /github/link` | Unlink; `204`, also when not linked | Member |

GitHub failures are `502 github_unreachable` without GitHub's response, which may echo request content. GitHub Enterprise Server is not supported: the runner's credential helper and the App endpoints are github.com only.

## Inference from the pod

The agent in the pod reaches models exactly like a local `teamcode run`: through a loopback proxy, to the TeamCode gateway, with the member's model policy, quotas, pacing and routing. Capability `cloud.inference.v1`.

- **The credential.** After registering, the runner asks `POST /cloud/runner/inference` with its projected token. The server issues a `tcex_` token for the member the execution runs for (`cloud_executions.owner_id`, fixed when the epoch started), limited to the `inference`, `mcp` and `skills:read` scopes (see [team MCP servers and skills](#team-mcp-servers-and-skills)): it cannot read usage, publish, manage anything or call any interactive route. It is a row of the existing `tokens` table (SHA-256 digest only), linked to its execution in `cloud_inference_credentials`, so the gateway authenticates it, revalidates it on every request and on the cancellation polls of a running stream, and charges the member's ledger like any other member token. It is not a service key: it is absent from service-key lists and limits.
- **Lifetime.** One hour (the response also gives `expiresInMillis`). The runner keeps it in memory only and renews it after a third of that lifetime, measured on its own clock, so clock skew does not matter; while a renewal is in flight other requests keep the current credential, and one is never offered in its last five minutes; the server keeps at most the current credential and the one before it per execution, so a request in flight during a renewal is not cut. Issuance takes the session row lock and checks that the execution is the registered current epoch of a session in `preparing`, `resuming`, `ready`, `active` or `pausing`, and that its member is enabled.
- **Revocation.** The transaction that ends an execution (pause, crash-consistent pause, lost execution, failed or blocked start, deletion) deletes its credentials; so does any write that leaves the running states, the start of a later epoch, and the owner change of a [transfer](#transfer). A draining execution keeps its credential until its pod stops, so the running turn can finish. A disabled member's credentials stop authenticating at once, and a password reset deletes them with the member's other tokens. A maintenance pass every minute deletes expired credentials and any whose execution is no longer live.
- **The proxy.** The runner serves the local proxy of `teamcode run` on `127.0.0.1` with a random local token, and starts the agent with that proxy's settings (Claude Code: `ANTHROPIC_BASE_URL`, and `ANTHROPIC_AUTH_TOKEN` set to the local token, other provider variables removed; Codex: the `teamcode` model provider and `TEAMCODE_LOCAL_TOKEN`). When the runner has no usable credential (the server is unreachable, or refused it), the proxy answers `503` with `Retry-After` instead of forwarding a request it knows will be refused. A server without this route answers `404`; the runner then starts the agent with its own provider configuration and says so in its log. The agent never receives the `tcex_` token from the runner. The proxy listens on the pod's loopback, which both containers share, and the agent runs in its own container with no way to read the projected token, so it cannot ask for a credential itself; see [the runner and the pod](#the-runner-and-the-pod).

## Team MCP servers and skills

A cloud session gets exactly what its owner gets from `teamcode run`: the team MCP servers assigned to the owner (the [MCP gateway](mcp-gateway.md)) and the owner's pinned skills (the [skill catalog](skills.md)). Both are resolved for the **current owner** every time the agent process starts, so a new pod, a resume, a crash restart and a [transfer](#transfer) never keep the former owner's servers or skills.

- **Credential.** The runner uses the execution's `tcex_` credential (scopes `inference`, `mcp`, `skills:read`). The agent never holds it: for MCP it gets the loopback proxy's random local token, exactly as for inference.
- **MCP.** Before each agent start the runner lists the owner's servers (`GET /api/v1/mcp/servers`) and starts the agent with one agent-side MCP server per assignment, each on the proxy's `/mcp/<server>` relay, as `teamcode run` does (`teamcode-<server>`; Claude Code reads the token from `TEAMCODE_MCP_TOKEN`, Codex from `TEAMCODE_LOCAL_TOKEN`; neither is on a command line). Authorization stays the gateway's on every message with the owner's current assignments: a server revoked while the session runs is refused at the next message, and the execution's credential disappears when the execution ends. Upstream MCP credentials never reach the pod. A server list that cannot be read starts the agent without MCP (the pod log says so).
- **Skills.** The runner reads the owner's delivery (`GET /api/v1/skill-delivery`) and installs it for the session's agent, in the agent's own home and under its own UID: `~/.claude/skills/<name>` for Claude Code, `~/.codex/skills/<name>` for Codex. The runner cannot write there (separate UID and container), so it starts `teamcode cloud install-skills --agent <kind>` through the exec supervisor and talks to it in JSON lines:
  1. The runner sends the manifest (name, version, digest); the installer answers which skills it needs: missing, or installed with another digest. Unchanged skills are not downloaded again.
  2. The runner downloads each needed artifact, checks every file's size and SHA-256 and the canonical digest against the manifest, then streams the files in chunks of at most 192 KiB. The installer checks the digest again, stages next to the skills directory and swaps the directory in.
  3. A `.teamcode-skill` marker names a delivered directory. A directory of the same name **without** the marker belongs to the member and is never touched (reported as a conflict, counted in the pod log). A marked directory no longer in the manifest (unassigned, unpinned, retired, or a former owner's) is removed.
  - Paths follow the catalog's rules and the installer refuses anything else. Bounds: at most 100 skills and 64 MiB per start (the rest is skipped and logged), 120 s overall; on failure the previous installation stays and the agent still starts. The pod log carries counts only, never skill names or contents.
  - Skill files can be copied by whoever receives them; they are not an access boundary (see [skills](skills.md)). Installation status is not reported to the server: the report route is for registered CLI devices.
- **Team hooks.** For Claude Code, the runner also downloads the owner's delivered [team hooks](hooks.md), verifies each digest (definition and files), installs the files under `~/.teamcode/hooks/<name>/` with `teamcode cloud install-hooks` (same protocol, marker `.teamcode-hook`, hooks no longer delivered removed) and starts Claude Code with `--settings` naming them. No per-member approval applies in a pod: the administrator's pin and the owner's *yes* are the approval. Codex sessions get no team hook, because Codex runs only hooks a person trusted and TeamCode does not bypass that trust.
- **Not covered.** MCP servers, skills and team hooks are read when the agent process starts: one added or pinned during a long turn applies at the next start (a pause and resume, or a restart). A skill directory inside a repository of the workspace is the agent's own business.

## Deployment

The deployment carries no cloud, GitHub or Kubernetes setting but one: the [session network policy](#session-network-policy), which the operator sets on purpose so that no dashboard administrator or `admin:cloud` key can widen it. Otherwise the [Helm chart](../helm/teamcode/README.md) only sets the image version, the public URL and the ingress (plus the database and encryption-key secrets every server needs). Everything else below is configured by an administrator on **Dashboard → Cloud sessions** (`/dashboard/cloud`) and **Dashboard → GitHub** (`/dashboard/github`), or through the API, and stored in the database. The **Settings** section of the dashboard menu always shows both pages to administrators, whether cloud sessions are on or off.

### Runtime: on, off, runner image and pod callback

| Field | Default | Purpose |
| --- | --- | --- |
| On | off | Whether cloud sessions can be started. Off: members see no cloud page, `cloud.*` capabilities are not advertised, and the requests that start new work (create, resume, message, attach, transfer, new GitHub link) answer `404`; reading, pausing, interrupting and deleting existing sessions and unlinking GitHub stay available through the API. Sessions that already exist are not abandoned: the runner channel stays open and the reconciler, garbage collection and maintenance keep running (idle pause, retention, deletion, cancelling ended conversations), so a running agent is never killed by the switch. No new pod starts while off: a session still queued waits (it can be deleted) until cloud sessions are on again. The workers start once a runtime is stored |
| Runner image | (none) | Image holding the `teamcode` Linux binary and `cp`, copied into each session pod. Required to turn cloud sessions on, together with a usable callback origin. Off, the runtime may stay incomplete, so an administrator can always save it. Pin it by digest (`image@sha256:...`); it is pulled with the profile's `imagePullSecrets`, so host it publicly or where those secrets reach. The [session image template](cloud-session-image.md) can serve as one |
| Runner binary | `/usr/local/bin/teamcode` | Path of the binary in that image |
| Server URL for pods | the public URL | HTTPS origin the runner calls, reachable from the cluster. Turning cloud sessions on is refused while the effective origin is not HTTPS or is loopback |
| Workspace access mode | `ReadWriteOncePod` | `ReadWriteOnce` for drivers without `ReadWriteOncePod` |

The runtime lives in `cloud_runtime` (`GET/PUT /api/v1/cloud/runtime`, administrators only; no field is a credential). A save carries the `updatedAt` it was based on and is refused with `409 cloud_runtime_conflict` if another administrator saved meanwhile. The replica that saves it applies it at once; the others reread it every 5 seconds (keeping the last value if the database is briefly unreachable), taking the stored row as is unless the replica saved while the read was in flight. Once a runtime is stored, the former variables are ignored without a warning. Every pod is built from the replica's current value, so a change reaches new pods within those seconds, without a restart or a redeployment.

**Former variables.** Before this, the runtime came from `TEAMCODE_CLOUD_RUNNER_IMAGE`, `TEAMCODE_CLOUD_RUNNER_BINARY`, `TEAMCODE_CLOUD_SERVER_URL` and `TEAMCODE_CLOUD_WORKSPACE_ACCESS_MODE`. When the database holds no runtime yet and `TEAMCODE_CLOUD_RUNNER_IMAGE` is set, the server stores them once at startup, turned on (journaled as `cloud.runtime.seeded`); an invalid combination, such as a plain-HTTP server URL, is stored turned off with a startup warning, keeping the fields that are valid on their own (the image included), instead of preventing the start. From then on the database is the source of truth: the variables are never read again, and they can be removed from the deployment.

### Clusters and GitHub

Clusters are connected on the same page (or with `POST/PUT /api/v1/cloud/clusters`): name, API URL, CA bundle, service-account token, allowed namespaces, pod cap and default storage class. The token is encrypted with the server's credential key; neither it nor the CA bundle is ever displayed again: the page says they are defined, and an empty field keeps the stored value. A cluster can also be created from a kubeconfig: drop or choose the file, or paste its contents, under *Import a kubeconfig*. The server reads it (the browser only fills a text area from the file) and prefills the form from one context: API URL, CA bundle, token and namespace. With several contexts a picker lists them, `current-context` selected, and contexts that cannot be imported disabled with their reason. The CA bundle and token are never put in a page: they travel back to the browser only inside an opaque value, encrypted with the server's credential key and bound to the administrator's session, which expires after 15 minutes and is opened by the save itself, so a replica other than the one that read the file can finish the import. The kubeconfig is not stored. Only what a cluster stores is supported: a bearer `token` (with `certificate-authority-data` for the CA); `exec` and `auth-provider` plugins, client certificates, username and password, impersonation, `proxy-url`, `tls-server-name` and `insecure-skip-tls-verify` are refused with `422 unsupported_kubeconfig` (or listed as disabled in the picker), and so are files referenced by path (`certificate-authority`, `tokenFile`), which only exist on the administrator's computer: `kubectl config view --raw --flatten --minify` embeds them. A context without a CA or token keeps those fields to fill by hand, and manual entry works as before. ![The context picker](images/kubeconfig-import-contexts.png) ![The prefilled cluster form](images/kubeconfig-import-prefilled.png) Profiles are created and edited on the same page too (see [profiles](#profiles)). The team's GitHub App is saved on the GitHub page, its client secret and private key encrypted and never shown again either (see [the team's App](#the-teams-app-administrator)).

The cluster's service account (its token is saved with the cluster) needs, in each allowed namespace, `get`, `list`, `create` and `delete` on `pods` and `persistentvolumeclaims`, and `create` and `patch` on `networkpolicies` (API group `networking.k8s.io`) for the [session network policy](#session-network-policy); cluster-wide `get` and `list` on `persistentvolumes` and `storageclasses`; and `system:auth-delegator` for `TokenReview`. Nothing else is required: TeamCode never deletes a PersistentVolume itself.

Two rights are optional; they only fill the [profile form](#profiles)'s lists, and without them the form asks for the name instead, without an error:

- `get` on `namespaces`, limited with `resourceNames` to the allowed namespaces: the form then marks an allowed namespace that does not exist. Without it, the allowed namespaces are offered as they are.
- `list` on `secrets` in each allowed namespace: the form then offers the namespace's `kubernetes.io/dockerconfigjson` secrets as image pull secrets. Kubernetes cannot grant listing without reading: whoever holds this right can read the contents of every secret of the namespace, so grant it only where the service account may see them. TeamCode itself lists them as metadata only (`Accept: application/json;as=PartialObjectMetadataList;g=meta.k8s.io;v=v1` with `fieldSelector=type=kubernetes.io/dockerconfigjson`), so the API server never sends their `data`; an API server that cannot answer in that form fails the read (`406`) instead of sending whole secrets. Only names are kept, never annotations (`kubectl.kubernetes.io/last-applied-configuration` may hold a copy of the data), and only names reach the browser.

`scripts/smoke-cloud-kind.py` creates exactly these roles, the optional ones included.

**Upgrading.** A service account without the `networkpolicies` right gets no new pod: each start refused with `403` fails with `network_policy_refused` (a `401`, such as a token being rotated, is retried) (a resume is blocked with it, keeping the workspace) until the right is granted, and the session can then be created or resumed again. Running pods are not touched.

Each server replica runs the reconciler continuously (leased per session) and, through scheduled work, garbage collection every 10 minutes and the idempotency-record purge every minute. A failed reconciliation step is logged with the session id and the error class or Kubernetes status only.

### Session network policy

**Sessions keep full internet access; only cluster-internal and metadata endpoints are blocked.** Web search, fetch, `npm`, `pip`, `git` and third-party APIs work as on a developer's machine. What a prompt-injected agent (running with full bypass) can no longer reach is the cloud metadata service (node or IAM credentials), the cluster's pods and services (the TeamCode server's internal port, a bundled MySQL, other namespaces, other sessions), the nodes and the Kubernetes API server.

Before creating any session pod, the server applies a NetworkPolicy named `teamcode-sessions` to the session namespace, with server-side apply (field manager `teamcode`, forced), and creates the pod only once the API server has accepted it. It is applied again before every pod, so a policy deleted or edited by hand is restored at the next start, and it covers every TeamCode pod of the namespace (`podSelector` `app.kubernetes.io/managed-by=teamcode`), including pods that were already running. It is never deleted; removing it by hand is the way to drop it once TeamCode no longer uses the namespace.

| Direction | Allowed |
| --- | --- |
| Ingress | Nothing, from other session pods included. The runner only dials out, and `kubectl exec` goes through the kubelet, not the pod network |
| Egress, DNS | Port 53, UDP and TCP, to any destination, so CoreDNS, NodeLocal DNSCache (a link-local address) and cloud resolvers all work |
| Egress, the TeamCode server | The addresses the server URL for pods resolves to (as the server resolves it, at every pod start), on its port, even when they are private; never a link-local one. If the URL does not resolve, or the cluster's API URL does not, no policy and no pod are sent and the start is retried: a policy without them would cut running pods from the server or let them reach the API server |
| Egress, internet | Every port of every public address: `0.0.0.0/0` and `::/0` except this host, RFC 1918, carrier-grade NAT (`100.64.0.0/10`, where Alibaba's metadata answers), loopback, link-local (`169.254.0.0/16`, `fe80::/10`: `169.254.169.254` and `metadata.google.internal` for AWS, GCP and Azure), IETF, benchmark, multicast and reserved IPv4 ranges, Azure's WireServer `168.63.129.16`, every blocked IPv4 range as embedded in NAT64 (`64:ff9b::/96`) and 6to4 (`2002::/16`), which otherwise stay open so DNS64 clusters keep IPv4-only sites, Teredo and local-use NAT64, unique-local `fc00::/7` (AWS's IPv6 metadata `fd00:ec2::254`), IPv6 multicast, the Kubernetes API server's addresses (resolved from the cluster's API URL, often public on managed clusters), and any `blockedCidrs`. Pod and service CIDRs are inside these private ranges on usual clusters |
| Egress, extra | The operator's `extraEgress` rules, verbatim |

The agent needs no route to model providers: inference goes through the runner's loopback proxy to the TeamCode server ([inference from the pod](#inference-from-the-pod)).

The policy is an operator setting, read from the server's environment at startup when the server has a database (an invalid value stops the start), set in the [Helm chart](../helm/teamcode/README.md) under `cloudSessions.networkPolicy`:

| Value | Variable | Default | Meaning |
| --- | --- | --- | --- |
| `enabled` | `TEAMCODE_CLOUD_SESSION_NETWORK_POLICY` | `true` | `false` applies no policy: pods are then unrestricted unless the cluster's own policies apply. Not recommended |
| `lockdown` | `TEAMCODE_CLOUD_SESSION_EGRESS_LOCKDOWN` | `false` | A stricter option for teams that want it: `true` removes the internet rule, leaving DNS, the server and `extraEgress`, so git hosts, registries or a proxy must be listed there. Web search, fetch, `npm` and `pip` then stop working unless allowed. Kubernetes NetworkPolicy cannot name hosts; with a CNI that can (Cilium `toFQDNs`, Calico DNS policies), write those policies for the same pods: policies add up |
| `blockedCidrs` | `TEAMCODE_CLOUD_SESSION_EGRESS_BLOCKED_CIDRS` (comma-separated) | none | More ranges to block: a pod, service or node range outside the private ranges (some IPv6 clusters give pods public addresses), or a host to keep away from sessions |
| `extraEgress` | `TEAMCODE_CLOUD_SESSION_EGRESS_EXTRA` (a JSON array) | none | NetworkPolicy egress rules appended verbatim, checked at startup against the API server's rules (peers, selectors, `except` strict subsets, protocols, ports and `endPort`). Each holds `to` (required, not empty) and `ports` only, and an `ipBlock` may not reach link-local: a block that contains `169.254.0.0/16` or `fe80::/10` must list it in `except` |

Cases that need a setting:

- **The server through the cluster's own load balancer.** When the server URL for pods resolves to the cluster's own load balancer, kube-proxy often short-circuits that address to the ingress controller's pods, whose private address the policy blocks, and runners cannot register (`start_timeout`). Allow the ingress controller, for example `extraEgress: [{to: [{namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: ingress-nginx}}}], ports: [{protocol: TCP, port: 443}]}]`.
- **Private git hosts, registries or proxies** on private addresses: an `extraEgress` rule for each.
- **Enforcement.** A NetworkPolicy does nothing on a CNI that does not implement it (for example flannel alone). `scripts/smoke-cloud-kind.py` checks on a real `kind` cluster that the policy is applied with `create` and `patch` only, that DNS resolves, and that a session pod reaches neither the API server's service, a node nor `169.254.169.254` while an unlabelled pod reaches the service.

Not covered: a CNI enforces the policy for a new pod a few seconds after the pod starts (kindnet: up to about 5 s); the runner's first calls fall in that window, the agent starts after preparation, well after it. The policy is per namespace, not per profile, so every profile of the server shares it, and two TeamCode servers sharing a namespace overwrite each other's (the last pod start wins). The server URL and the API server are resolved by the TeamCode server, which may see other addresses than the pods (split-horizon DNS), and the policy holds the latest answer: a server URL whose private addresses rotate should be allowed by `extraEgress` (a CIDR or the ingress selector) rather than rely on the resolved rule. `extraEgress` and `blockedCidrs` cover these cases. Public egress stays open by design, so an agent can send what it reads to a public host. The TeamCode server's own egress is not restricted by the chart.

### Profiles

An administrator creates and edits profiles on **Dashboard → Cloud sessions**, under *Profiles*, or with `POST/PUT /api/v1/cloud/profiles`: the form has every field the API accepts. A profile is versioned and each version is immutable, so the form edits a draft: *New profile* starts one for version 1, *Edit* starts one for the next version from the current one. The draft is not stored; the form carries it from step to step. *Check draft* runs the profile validation of a publication without publishing (`checkProfile`): cluster, allowed namespace, storage class, bounds, recipe, and that the profile has not been published again since the draft started (a name already used is only found at publication); *Publish version N* creates the version. A refused check or publication shows the form again with the reason and everything typed. Sessions keep the version they were created with.

The choices come from the API of the cluster chosen in the form, read with its service account (`GET /api/v1/cloud/clusters/{id}/choices`), and the lists are read again when the cluster or the namespace changes (the storage class and the pull secrets of the previous cluster are dropped) (a small script submits *Reload choices from the cluster*, which works without it too):

| Field | Choices |
| --- | --- |
| Cluster | The connected clusters |
| Namespace | The cluster's allowed namespaces; one that does not exist on the cluster is marked and cannot be chosen, unless the profile is already on it (needs the optional `get` on `namespaces`) |
| Workspace storage class | The cluster's storage classes with their reclaim policy and provisioner, the default marked; *Cluster default* keeps the class unset, so the cluster record's default class (or the Kubernetes default) applies. A class whose `reclaimPolicy` is not `Delete` (`Retain`) shows a warning: TeamCode deletes a workspace's claim but never a PersistentVolume, so its volumes would accumulate; publishing a profile on it is refused (`422 storage_class_retains_volumes`) |
| Image pull secrets | The `kubernetes.io/dockerconfigjson` secrets of the namespace, by name (needs the optional `list` on `secrets`); other names can be typed |
| Image | Free, with the images of the other profiles offered |
| CPU, memory, workspace size, idle pause and its bounds | Presets within the validated ranges; a value saved through the API is kept as a choice |
| Agent | Claude Code or Codex, and a version (empty installs the latest) |
| Environment recipe | Repositories (clone URL, directory, ref, new branch), repository hosts, working directory, setup commands (one box per command), required variables, GitHub required, Git email domain |
| Members | The team's enabled members; administrators may use every profile |

When a list cannot be read (the right is missing, the cluster is unreachable, or the list is empty), the field becomes a text box with the reason; the form never fails for it. The lists only help: publishing keeps the server's validation (namespace allowed, storage class present with `reclaimPolicy: Delete`, bounds, recipe). ![The profile form](images/cloud-profile-form.png)

## The agent in the pod

See [transcript, messages and attach](cloud-conversations.md#the-agent-in-the-pod): Claude Code and Codex run in bypass mode as one long-lived process with streaming input, resumed by conversation id after a new pod. Agents authenticate only through the loopback proxy; refusing to checkpoint a credential file found under the agent homes is planned.

## Other planned parts

- **GitHub in the long-lived agent.** Preparation passes the token to Git and `gh` through child-process environments only (see [GitHub access](#github-access)); for the long-lived agent, the token moves to a credential helper over a tmpfs socket that asks the runner channel again before expiry, never the workspace, a remote URL, an event or an image. On transfer, the recipient's link replaces the former owner's at the next preparation.
- **Transfer.** Administrator transfer is immediate; an owner's request is an offer the recipient accepts within 7 days. Transfer happens at a checkpoint, revokes execution and attachment credentials, rechecks the recipient, and charges future work to the recipient while historical usage stays with the original member. The policy follows the settings above.

`teamcode cloud profiles` lists the profiles the caller can create sessions from (every profile for an administrator), one per line: id, name, published version, cluster and namespace, image, and agent kind with its version; an administrator adds `--member ID` to list what that member can use (refused before any request when the server does not advertise `cloud.profiles.member.v1`). `create --profile` takes an id or a name. A value shaped like a generated id (a UUID) is sent as is, without listing anything, so a script that retries with the same `--idempotency-key` sends the same body; scripts should pass ids, since a name resolves to whatever profile carries it at the time. Any other value is looked up in the owner's list (the member's with `--member` when the server advertises `cloud.profiles.member.v1`, the caller's otherwise): as an id when a listed profile has it, otherwise as a name, the exact name before the name ignoring case. A name that matches several profiles (`Default` and `default` for `--profile DEFAULT`) is refused with their ids. A value that matches nothing listed is sent as an id, and the server answers `profile_not_found` or `profile_unassigned`; the CLI explains both and points to `teamcode cloud profiles`. A list that cannot be read sends the value as an id.

`teamcode cloud transfer` without `SESSION` picks one of the caller's own cloud sessions that can change owner (ready, working, pausing, paused or resuming, none already transferring); without `--to`, it picks the recipient among `GET /cloud/transfer-recipients`, the session's owner left out. Both pickers are the CLI's shared one: arrow keys and Enter on a terminal, a numbered list answered by one line otherwise; cancelling, or input that ends (a script without `--to`), stops before any transfer. A server without the recipients' list asks for `--to MEMBER_ID`. Scripts keep passing both.

`--member` sends `TeamCode-On-Behalf-Of` (and, for `list`, filters by owner; for `profiles`, names the member), `--json` prints the API DTOs unchanged, and `create` sends a random idempotency key unless one is given, so a script can retry with its own. `list` follows pages up to 500 sessions. `delete` refuses without `--yes`. `--repo` (repeatable) replaces the profile's repositories, the path defaulting to the repository name; `--branch` creates that local branch in each of them. `create --message -` reads the message from standard input; `--message` is refused before any request when the server does not advertise `cloud.sessions.initial-message.v1`, so an older server never drops it silently. `teamcode github link` prints the verification URL and code, then waits until GitHub authorizes, the code expires or the member cancels; it points to the dashboard when the App is not configured or device flow is disabled. `--member` on `github status` and `github unlink` is for administrators. The GitHub App itself is configured on the dashboard or through the API, which keeps the client secret and private key off command lines. `logs`, `send`, `attach`, `interrupt` and the administration commands come with their features.
