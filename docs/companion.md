# Companion app

The companion app is a TeamCode client for iOS, Android and the desktop (macOS, Windows, Linux). It follows and steers the cloud sessions a member (or an administrator) can see, and opens artifacts. Nothing runs in it: every session lives on the server. It is a Kotlin Multiplatform module that depends only on the typed client, like the CLI (`companion -> client -> api`).

## Client contract

The app reuses `TeamCodeClient` as is: the SDK still owns no operating system keychain and receives a token provider (`token: suspend () -> String?`); the HTTP engine comes from the caller's factory (Darwin on iOS, OkHttp on Android, a JVM engine on the desktop).

**Event streams.** `followCloudEvents(id, after, onEvent)` follows one session's transcript and `followTeamEvents(after, types, onGap, onOpen, onEvent)` the caller-wide feed (`after` has no default: the caller decides whether it resumes). Both read their response with the same internal SSE reader: lines bounded at 256 Ki characters and the data of one event at 1 Mi characters, comments (keep-alives), `id:` and `retry:` skipped (resumption uses the `seq` in the event), multi-line `data:` joined, frames without a name (or with an empty one) ignored. A stream that closes throws `TeamCodeException` with status `0` and no code: reconnect from the last `seq`. An event the client cannot decode, a line over the line bound or an event over the data bound throws status `0` with code `malformed_event` (`TeamCodeClient.MALFORMED_EVENT`): reconnecting would replay it, so a caller stops or updates instead of retrying (`teamcode cloud logs --follow` stops with a message naming `--after` to follow from a later event, and `attach` detaches; both exit 1); the decoder's own exception is not kept, since its message quotes the payload. Bytes that are not UTF-8 are decoded with replacement characters. A network failure, when opening the stream or in the middle of it, surfaces as the engine's own exception, as before, and an exception from the caller's handler is rethrown as is.

| Call | Ends with | Throws |
| --- | --- | --- |
| `followCloudEvents` | `ENDED` after `event: end` (the session ended and every event was sent), `DENIED` after `event: denied` | `TeamCodeException` with status `0` when the stream closes, with the API error code for a refused request |
| `followTeamEvents` | `DENIED` after `event: denied` (the credential stopped being valid); the feed never ends otherwise | The same |

Both take an optional `onOpen`, called once the server accepted the stream and before any frame: from then on the feed's cursor is fixed, so a caller that opened the feed with `null` loads what it shows in `onOpen` and misses nothing changed in between. `followTeamEvents` sends `after` as `Last-Event-ID` (`null` starts with what happens from now on, so events published between two connections opened with `null` are never delivered; `0` replays every retained event) and `types` as `?types=a,b`. When the events after the cursor were purged, `onGap(oldestSeq)` is called before the events that follow, so the caller reloads what it shows. Event types are an open list: an unknown type reaches `onEvent` like the others; `gap` and `denied` are the feed's control frames and never event types. To resume after a network failure, call it again with the last `seq` handled: the server's sequence is gap-free, so nothing is lost or seen twice.

**Builds.** The Android targets need an Android SDK only for their own tasks (`ANDROID_HOME` or `local.properties`); JVM, native CLI and server tasks configure and run without one. Publishing the iOS targets, like the macOS ones, needs a Mac.

## App

`:companion` is the shared app (Compose Multiplatform); `:companion-android` and the Xcode project `companion-ios/` are thin shells around it, and the desktop entry point lives in its `jvmMain`. Inside, the code is split by layer, checked by `scripts/check-module-graph.py`:

| Package | Holds | May import |
| --- | --- | --- |
| `domain` | Models (`Account`, `ServerInfo`, `CloudSession`, `TranscriptEvent`...), repository and service ports, use cases (inspect a server, sign in, change a temporary password, sign out, refresh, rename the device, list and follow sessions, load and follow a transcript) | Nothing from the other layers, nor `api` or `client` |
| `infrastructure` | `TeamCodeClient` per account, the typed client mapped to domain errors, settings-backed repositories, one credential store per platform, the reconnection policy of streams | `domain`, `api`, `client` |
| `presentation` | Theme (the dashboard's palette), navigation, screens and view models | `domain` only |
| `di` | Koin modules; each platform adds its own (`platformModule()`) | Everything |

**Sign-in.** The user enters a server address; the app normalizes it (HTTPS required except on loopback) and checks, without any credential, that it answers like TeamCode. The server keeps its version and capabilities behind authentication, so an anonymous `GET /api/v1/capabilities` answers `401` with the `authentication_required` error code: that answer means "a TeamCode server, sign in next", never "signed out". A redirect, a `404`, a page that is not TeamCode's JSON, or a `401` or other `4xx` without TeamCode's code is another server; a `5xx` is reported as a server failure. Before sign-in the app therefore shows the origin but not the server's version, and checks the API version only if a server announces its capabilities without a credential. It then signs in with `POST /api/v1/auth/login` and the installation id, which registers the app as one device; signing in again to an account revokes the session it replaces, since the server keeps every session until it is logged out or expires. With the new session, the app reads `GET /api/v1/capabilities`: it keeps the server's version for Settings and refuses a server whose API version it does not speak, revoking that session instead of storing it. Features (sessions, messages, the first message of a new session, artifacts) are read with the account's token, once and again when a list comes back to the foreground. A temporary password leads to the password change (at least 14 characters), after which the app signs in again; if that sign-in fails, the change has already revoked the temporary session, so the app returns to the sign-in form and asks for the new password. Several accounts, on one or several servers, can be signed in; one is active.

**Credentials.** Accounts (server, member, device name) are stored in the platform settings; tokens never are. Tokens go to the platform's secure storage: the iOS Keychain (`AfterFirstUnlockThisDeviceOnly`, never synced), an AES-256-GCM key in the Android Keystore (the account id as associated data; backups disabled), and the operating system keyring on the desktop (Keychain, Credential Manager, Secret Service). When the desktop has no keyring, or it refuses a write, tokens stay in memory and the app asks to sign in at each launch, never writing them to disk.

**Navigation and look.** Before any account, the app is a plain stack: add a server, sign in, change a temporary password. Signed in, it has three tabs over a bottom bar: Sessions, Artifacts and Account; a session, an artifact and a session's artifacts are pushed above them. The Sessions tab has a large title, a **+** button that opens the new-session form as a sheet, a pill naming the active account and its server that opens the account switcher (every account, the active one checked, a signed-out one with "Sign in", "Add an account", "Manage" leading to the Account tab), the state filter (Active, Paused, Ended) and, for administrators, a Mine or Team pill. The Account tab holds what Settings held: the active account (switch, sign out), the other accounts (sign in again, add one), this device's name, the appearance (system, light, dark) and the app and server versions. The look follows the dashboard: a green accent, monospace for identifiers and metadata, and its own light and dark palettes (`TeamCode.colors`), chosen by the system or the Account tab. A disabled button dims its colors rather than the whole control, so it stays legible on both palettes. On Android the artifact web view is themed from the app, not the activity, so it follows the same choice. Every action used in tests has a `testTag`.

**Sessions.** The Sessions tab lists the active account's cloud sessions (newest first, 50 per page, keyset cursor), filtered as active, paused or ended, and for administrators as their own or the whole team's. While it is visible, it follows the caller-wide feed (`cloud.events.v1`): the list is loaded once the feed is open (`onOpen`), and again after a `gap`; each session event updates its row from the event itself (`data.state`, a `cloud.turn` phase), and only an event about a session the list does not hold but may (another filter, an older page excluded), or a turn of a row still shown in a passing state, reads it with `GET /cloud/sessions/{id}`. The feed is asked only for the six session types of its first version (`cloud.session.created`, `.paused`, `.woken`, `.resumed`, `.ended`, `cloud.turn`). Some changes have no event (a new session becoming ready, a pause or a resume completing): rows in a passing state (creating, preparing, pausing, resuming, transferring) are read again every 15 seconds, at most five per tick, taken in turns so rows that never settle do not hide the others. A reload replaces the first page and keeps the rows of the pages loaded after it, so a refresh never collapses a list scrolled further down, and shows no spinner over a list already shown. A finished turn marks its row until the session is opened. Feed events, filter changes and "load more" are applied one at a time, so an event received while a page loads is applied after that page. A server without the feed is polled every 15 seconds. After the list stopped on an error, changing the filter starts it again; a change of the account's role or server starts a new list. A session screen shows the header (state, agent, model, effort, repositories, the failure code), the newest 100 events, older pages on request ("Load earlier events", never automatically), and the live stream after the newest sequence; events are merged by `seq`, each once and in order. A live `turn` moves the header between ready and working; since the transcript carries no pause, resume or failed pod, the header is read again every 30 seconds while the screen is visible, and "Working…" shows only while the session is working. Tool results join their call by id, runs of tool uses with no text between them fold into "N actions", subagent steps are indented, turn ends show their duration and steps, and status, errors, rejected or cancelled messages, permission requests (answered from a card, below), expiries, transfers and events the server replaced for size are system lines; unknown types are skipped. Agent text is Markdown (`multiplatform-markdown-renderer`); a link opens in the system browser only after the full URL is shown, and only `http` or `https`.

**Acting on sessions.** A session screen has a composer: the message (1 to 32,000 characters, no control characters except newlines and tabs, checked before any request) shows at once as a pending bubble and goes with `wake: true` and its own id as `Idempotency-Key`. Its states: sending, sent (or "the session is waking up" when the receipt says `woke`), failed (a network failure, a `5xx` or a `429`: "Retry" sends it again with the same id, so the server returns the first receipt instead of queueing it twice) and refused (any other refusal, or a later `input` event that rejected or cancelled it, with its reason). A pending bubble disappears when the transcript's `message.user` event carries its input id. While a turn runs, "Interrupt" sends `POST …/interrupt` with a fresh idempotency key; `409 nothing_to_interrupt` only says nothing is running. The owner and administrators get "Pause" (ready, active or resuming sessions) and "Resume" (paused or pausing ones); the header shows the answer. An ended or transferring session takes no message.

**Answering the agent.** When the agent waits on a `permission.request` (an `AskUserQuestion` question, or a tool use matched by an `ask` rule; see [permission requests](cloud-conversations.md#permission-requests)), a card above the composer shows it. The open requests are derived from the merged transcript, so a request found in a history page and one received live are handled alike: a request is open until an `input` event with its `requestId` and status `consumed`, a `permission.expired` naming it, a finished `turn` (completed, interrupted or failed), or a `status` event (the agent process that asked exited or a new one started); none is shown while the session is not ready or active (pausing, paused, ended, transferring), since the server takes no answer then. With several open requests, the oldest is shown first (the agent asked them in that order and their deadlines pass in it), with "N more waiting after this one". A question shows one question at a time: its header, its text, its options with their descriptions (radio buttons for a single choice, checkboxes for `multiSelect`) and "Other" with a free text field, with the progress ("2/3") when there are several. "Next" is enabled once the question is answered (one option or a non-empty Other for a single choice, at least one of them for several) and "Back" returns to the previous question with its choice kept; on the last question, "Send" sends every answer in one `POST …/permissions` with `behavior: allow`: an option by index, Other as `text`. The API takes options or a text per question, so Other is exclusive in a single choice, and in a multi-select question with options and Other both chosen the answer goes as one `text`, the chosen labels in option order then the other text joined with `, `, which is what Claude Code receives when the runner joins labels itself. Texts are trimmed and checked like the server (1 to 4,000 characters, no control characters except newlines and tabs) before any request; a repeated question text is shown and answered once (Claude Code keys answers by text). "Decline" sends `behavior: deny`. A tool use shows the tool name, its description and its input (indented JSON, scrolled in its own box) with "Allow" and "Deny"; they are shown to everyone, and a `403 permission_answer_denied` (only the owner or an administrator decides a tool use) is a notice. A request whose input was left out of the event (`inputTruncated`, or no readable input) shows its preview and can only be declined or denied. Every text in the card is the agent's and is plain text, never Markdown. Each answer draws an idempotency key kept with that exact answer: a network failure, a timeout, a `5xx` or a `429` shows "Not sent" with "Retry", which sends the same body under the same key, and any edit drops the key so a changed answer gets a new one. A `202` shows "Answer sent, waiting for the agent" until the request closes; a later `input` event that rejected or cancelled that answer (the request stays open, e.g. `agent_unavailable`) brings the card back to editing with a notice. A `409` (answered by someone else, expired, ended, or `nothing_to_answer`) hides the card with a notice; a `400` keeps the draft with a notice. Answers go only to a server announcing `cloud.permissions.v1` (the only one that relays requests). "New session" lists the member's profiles (`GET /cloud/profiles`), takes a name (1 to 120 characters), optional model and effort, and a first message only when the server announces `cloud.sessions.initial-message.v1` (otherwise the field is hidden and a message is never sent). The form draws one idempotency key and keeps it while its fields are unchanged, so a retry after a network failure returns the session the first attempt created; editing a field draws a new key. The new session opens at once.

**Transfers.** On a server that announces `cloud.transfer.v1`, a cloud session's "…" menu has "Transfer…" for its owner and administrators while the session can change owner (ready, working, pausing, paused or resuming; never a remote session, one being created or prepared, an ended one or one already transferring). An administrator searches the team's members (`GET /members`, administrators only, by username or ID; disabled members and those who have not set their password are shown but cannot be picked) and transfers at once, optionally resuming the session for the recipient and pausing at once instead of letting the running turn finish (`resume`, `force`). A member, who cannot list the team, names the recipient by member ID and sends an offer, without those options. The form draws one `Idempotency-Key` and keeps it while what it sends is unchanged, so a retry after a network failure replays the first transfer. The Sessions tab's title has a Transfers button opening the member's transfers to them and from them (`GET /cloud/transfers?direction=incoming|outgoing`, 50 per page, keyset cursor): the state, both members (names for administrators from one member list, IDs and "you" otherwise), the offer's expiry and why a transfer failed; the recipient (or an administrator) accepts or declines an offer, its owner withdraws it, an administrator also cancels an accepted transfer before the owner change. Every refusal is worded from its code (`transfer_pending`, `session_preparing`, `session_not_running`, `transfer_disabled`, `transfer_expired`, ...), and `422 recipient_ineligible` names each failed check of the recipient (profile, access policy, model or effort, allowance, session limit): the typed client keeps those problem codes, checked against the error-code alphabet, and nothing else of the message. A decision refused because the transfer changed meanwhile reads the list again. The transcript's `transfer` event already reads "The session changed owner".

**Streams.** Both streams are open only while their screen is visible (Android and iOS lifecycle `STARTED`, the desktop window shown), closed in the background, and resumed from the last sequence on return. A stream that closes, a network failure, `408`, `429` or `5xx` reconnects after 2 s, doubling up to 30 s, each delay shortened by up to a fifth at random; the count restarts when an event arrives or after a connection that stayed open at least 30 s (a connection accepted then dropped at once keeps backing off), and a `429` waits at least its `Retry-After` (at most 5 minutes). `401` checks the account once (`GET /auth/me`, which signs it out only if refused again) and stops; `404` says the session is gone (the server hides what a member may not read behind `404`), and a `403` is shown as a refusal of the action; `denied` (which the server also sends when the token expired) checks the account the same way and offers a retry; an unreadable event stops (a reconnection would replay it). Nothing is written to disk: the transcript lives in memory while its screen exists.

**Artifacts.** The Artifacts tab is the gallery (`artifacts.v1`): the member's own artifacts or everything they can read in the team (`GET /artifacts?scope=mine|team`, 50 per page, keyset cursor, the next page loaded near the end of the list), with a search over the titles and descriptions already loaded. A session screen's Artifacts button pushes the artifacts that cloud session published (`?session=<id>`). A card shows the title, description, owner, access, version and age. The viewer has a native bar (title, version picker, copy link, open in the browser, where access is managed) and, on iOS and Android (`artifacts.tickets.v1`), the content in a web view: the app asks `POST /artifacts/{id}/tickets` for the version shown, refuses a content URL that is not on the account's own origin under `/artifact/<id>/<ticket>/`, and loads it. The web view keeps no cookie or storage (`WKWebsiteDataStore.nonPersistent()`; cookies off, DOM storage off, cache cleared on close on Android), has no JavaScript bridge and no file or content access, refuses mixed content, geolocation, camera and microphone, and lets the main frame navigate only under the ticket's directory (no `..`, no escaped dot or slash); a link elsewhere that the member followed, or a pop-up, is offered to the browser after its URL is shown, and any other scheme is refused. The content's sandbox does not depend on the app: the server sends `Content-Security-Policy: sandbox` with every file. When a page answers `404`, the app asks for a ticket again: a different one (the old one expired, or is only older than the server's 10-minute rounding of expiries) loads that same page again under it, in a new web view; the same one (a ticket asked again soon comes back unchanged) means a link led to a file the version lacks, which the screen says with "Back to the start". A crashed page (renderer or content process) is loaded again, at most once a minute. While the viewer is visible, the artifact is read again every 30 seconds and a newer version is offered ("Version N was published. Show it"), never loaded by itself. The version picker asks for a ticket fixed on the chosen version.

**Links.** Universal Links and App Links need each server's domain in the app at build time, which a self-hosted server cannot have, so the app registers the `teamcode` scheme: the viewer page's **Open in app** link is `teamcode://open?url=<the viewer URL>`. Android also takes a link shared as text (`ACTION_SEND`), and every platform has an "Open a link" field in the gallery (the clipboard is never read by itself). A link resolves only to `<server>/artifact/<id>` with an optional `?v=<version>`; its origin must equal an account's exactly (the active account first when several share it). A link to a server with no account shows that origin in full and offers to sign in to it as a new server. A link never carries a secret, so the worst a crafted one does is offer a sign-in to a server whose origin is shown.

**Desktop.** Artifacts open in the browser on the viewer page; there is no embedded browser, and no ticket is asked for.

## Distribution

Store builds are made and uploaded from a maintainer's Mac with fastlane (`Gemfile`, `fastlane/Fastfile`); there is no publication job yet. Nothing in the repository holds a key, a certificate or a password: each lane reads them from files next to the Fastfile and from the environment, all ignored by git.

| Lane | Does | Needs (local only) |
| --- | --- | --- |
| `bundle exec fastlane ios beta version:X.Y.Z` | Archives `companion-ios/TeamCode.xcodeproj` (shared scheme `TeamCode`, Release) with automatic signing through the App Store Connect key (Xcode cloud signing, no certificate in the keychain), then uploads to TestFlight without submitting | `fastlane/api_key.json`, `fastlane/key.p8` |
| `bundle exec fastlane android beta version:X.Y.Z` | `:companion-android:bundleRelease --no-daemon`, signed with the upload key, then uploads to Play's internal track | `fastlane/play-key.json`, `fastlane/keystore.jks`, `SIGNING_STORE_PASSWORD`, `SIGNING_KEY_ALIAS`, `SIGNING_KEY_PASSWORD` |

Only builds are uploaded. Store listings, screenshots and descriptions are kept in App Store Connect and the Play Console, never in this repository (`fastlane/metadata/` and `fastlane/screenshots/` are ignored), and no lane submits for review or releases. App Review needs a demo account on a demo server, entered in App Store Connect only.

**Versions.** The app carries the TeamCode version given to the lane (`MARKETING_VERSION`, `versionName`, and the shared code's `BuildInfo.VERSION` through `teamcodeVersion`). The build number (`CFBundleVersion`, `versionCode`) is `(major × 1,000,000 + minor × 1,000 + patch) × 100 + n`, where `n` counts the uploads of that version (read from TestFlight and the Play tracks, at most 99). Without the lane, Gradle builds use `n = 0`, and the Xcode project's `CURRENT_PROJECT_VERSION` stays 1.

**Android release signing.** `companion-android` signs its release build only when `fastlane/keystore.jks` exists, with the passwords from `SIGNING_*`; otherwise the release build is unsigned, and the lane refuses to run.

**iOS privacy.** `PrivacyInfo.xcprivacy` declares no tracking and no collected data, plus the two required-reason APIs the app uses: UserDefaults (`CA92.1`, the app's own settings) and system boot time (`35F9.1`, elapsed time for timeouts and reconnection delays). There are no analytics.

**Desktop.** `:companion:packageDmg`, `packageMsi` and `packageDeb` build on the matching host. The `.dmg` is signed with a Developer ID and notarized when the Mac provides `TEAMCODE_MACOS_SIGNING_IDENTITY` (the identity's name in the keychain) and `TEAMCODE_NOTARIZATION_APPLE_ID`, `TEAMCODE_NOTARIZATION_PASSWORD` (an app-specific password) and `TEAMCODE_NOTARIZATION_TEAM_ID`; without them it is unsigned. Windows installers are not signed in v1 (SmartScreen warns). Attaching the desktop packages to TeamCode's GitHub release, with their lines in `manifest.json` and `SHA256SUMS`, is still to do.
