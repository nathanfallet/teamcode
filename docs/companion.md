# Companion app

The companion app is a TeamCode client for iOS, Android and the desktop (macOS, Windows, Linux). It follows and steers the cloud sessions a member (or an administrator) can see, and opens artifacts. Nothing runs in it: every session lives on the server. It is a Kotlin Multiplatform module that depends only on the typed client, like the CLI (`companion -> client -> api`).

## Client contract

The app reuses `TeamCodeClient` as is: the SDK still owns no operating system keychain and receives a token provider (`token: suspend () -> String?`); the HTTP engine comes from the caller's factory (Darwin on iOS, OkHttp on Android, a JVM engine on the desktop).

**Event streams.** `followCloudEvents(id, after, onEvent)` follows one session's transcript and `followTeamEvents(after, types, onGap, onOpen, onEvent)` the caller-wide feed (`after` has no default: the caller decides whether it resumes). Both read their response with the same internal SSE reader: lines bounded at 256 Ki characters and the data of one event at 1 Mi characters, comments (keep-alives), `id:` and `retry:` skipped (resumption uses the `seq` in the event), multi-line `data:` joined, frames without a name (or with an empty one) ignored. A stream that closes throws `TeamCodeException` with status `0` and no code: reconnect from the last `seq`. An event the client cannot decode, a line over the line bound or an event over the data bound throws status `0` with code `malformed_event` (`TeamCodeClient.MALFORMED_EVENT`): reconnecting would replay it, so a caller stops or updates instead of retrying (`teamcode cloud logs --follow` stops with a message naming `--after` to follow from a later event, and `attach` detaches; both exit 1); the decoder's own exception is not kept, since its message quotes the payload. Bytes that are not UTF-8 are decoded with replacement characters. A network failure, when opening the stream or in the middle of it, surfaces as the engine's own exception, as before, and an exception from the caller's handler is rethrown as is.

| Call | Ends with | Throws |
| --- | --- | --- |
| `followCloudEvents` | `ENDED` after `event: end` (the session ended and every event was sent), `DENIED` after `event: denied` | `TeamCodeException` with status `0` when the stream closes, with the API error code for a refused request |
| `followTeamEvents` | `DENIED` after `event: denied` (the credential stopped being valid); the feed never ends otherwise | The same |

Both take an optional `onOpen`, called once the server accepted the stream and before any frame: from then on the feed's cursor is fixed, so a caller that opened the feed with `null` loads what it shows in `onOpen` and misses nothing changed in between. `followTeamEvents` sends `after` as `Last-Event-ID` (`null` starts with what happens from now on, so events published between two connections opened with `null` are never delivered; `0` replays every retained event) and `types` as `?types=a,b`. When the events after the cursor were purged, `onGap(oldestSeq)` is called before the events that follow, so the caller reloads what it shows. Event types are an open list: an unknown type reaches `onEvent` like the others; `gap` and `denied` are the feed's control frames and never event types. To resume after a network failure, call it again with the last `seq` handled: the server's sequence is gap-free, so nothing is lost or seen twice.

**Builds.** The Android targets need an Android SDK only for their own tasks (`ANDROID_HOME` or `local.properties`); JVM, native CLI and server tasks configure and run without one. Publishing the iOS targets, like the macOS ones, needs a Mac.

## App

`:companion` is the shared app (Compose Multiplatform); `:companion-android`, `:companion-desktop` and the Xcode project `companion-ios/` are shells around it. `:companion-desktop` (JVM only, `companion-desktop -> companion + config + client`) carries what only makes sense on a member's computer; see [Desktop](#desktop-sessions-on-this-device). Inside, the code is split by layer, checked by `scripts/check-module-graph.py`:

| Package | Holds | May import |
| --- | --- | --- |
| `domain` | Models (`Account`, `ServerInfo`, `CloudSession`, `TranscriptEvent`...), repository and service ports, use cases (inspect a server, sign in, change a temporary password, sign out, refresh, rename the device, list and follow sessions, load and follow a transcript) | Nothing from the other layers, nor `api` or `client` |
| `infrastructure` | `TeamCodeClient` per account, the typed client mapped to domain errors, settings-backed repositories, one credential store per platform, the reconnection policy of streams | `domain`, `api`, `client` |
| `presentation` | Theme (the dashboard's palette), navigation, screens and view models | `domain` only |
| `di` | Koin modules; each platform adds its own (`platformModule()`) | Everything |

**Sign-in.** The user enters a server address; the app normalizes it (HTTPS required except on loopback) and checks, without any credential, that it answers like TeamCode. The server keeps its version and capabilities behind authentication, so an anonymous `GET /api/v1/capabilities` answers `401` with the `authentication_required` error code: that answer means "a TeamCode server, sign in next", never "signed out". A redirect, a `404`, a page that is not TeamCode's JSON, or a `401` or other `4xx` without TeamCode's code is another server; a `5xx` is reported as a server failure. Before sign-in the app therefore shows the origin but not the server's version, and checks the API version only if a server announces its capabilities without a credential. It then signs in with `POST /api/v1/auth/login` and the installation id, which registers the app as one device; signing in again to an account revokes the session it replaces, since the server keeps every session until it is logged out or expires. With the new session, the app reads `GET /api/v1/capabilities`: it keeps the server's version for Settings and refuses a server whose API version it does not speak, revoking that session instead of storing it. Features (sessions, messages, the first message of a new session, artifacts) are read with the account's token, once and again when a list comes back to the foreground. A temporary password leads to the password change (at least 14 characters), after which the app signs in again; if that sign-in fails, the change has already revoked the temporary session, so the app returns to the sign-in form and asks for the new password. Several accounts, on one or several servers, can be signed in; one is active.

**Credentials.** Accounts (server, member, device name) are stored in the platform settings; tokens never are. Tokens go to the platform's secure storage: the iOS Keychain (`AfterFirstUnlockThisDeviceOnly`, never synced), an AES-256-GCM key in the Android Keystore (the account id as associated data; backups disabled), and the operating system keyring on the desktop (Keychain, Credential Manager, Secret Service). When the desktop has no keyring, or it refuses a write, tokens stay in memory and the app asks to sign in at each launch, never writing them to disk.

**Navigation and look.** Before any account, the app is a plain stack: add a server, sign in, change a temporary password. Signed in, it has three tabs over a bottom bar: Sessions, Artifacts and Account; a session, an artifact and a session's artifacts are pushed above them. The Sessions tab has a large title, a **+** button that opens the new-session form as a sheet, a pill naming the active account and its server that opens the account switcher (every account, the active one checked, a signed-out one with "Sign in", "Add an account", "Manage" leading to the Account tab), a status filter pill next to **+** (All, Active + Paused, Ended; Active + Paused by default) and, for administrators, a Mine or Team pill. The Account tab holds what Settings held: the active account (switch, sign out), the other accounts (sign in again, add one), this device's name, the appearance (system, light, dark) and the app and server versions. The look follows the dashboard: a green accent, monospace for identifiers and metadata, and its own light and dark palettes (`TeamCode.colors`), chosen by the system or the Account tab. A disabled button dims its colors rather than the whole control, so it stays legible on both palettes. On Android the artifact web view is themed from the app, not the activity, so it follows the same choice. Every action used in tests has a `testTag`.

**Sessions.** The Sessions tab lists the active account's cloud sessions (newest first, 50 per page, keyset cursor), filtered by status (all, active and paused together, or ended; the filter menu sits next to the **+** button, and the list always shows cloud and remote sessions alike) and, for administrators, as their own or the whole team's. While it is visible, it follows the caller-wide feed (`cloud.events.v1`): the list is loaded once the feed is open (`onOpen`), and again after a `gap`; each session event updates its row from the event itself (`data.state`, a `cloud.turn` phase), and only an event about a session the list does not hold but may (another filter, an older page excluded), or a turn of a row still shown in a passing state, reads it with `GET /cloud/sessions/{id}`. The feed is asked only for the six session types of its first version (`cloud.session.created`, `.paused`, `.woken`, `.resumed`, `.ended`, `cloud.turn`). Some changes have no event (a new session becoming ready, a pause or a resume completing): rows in a passing state (creating, preparing, pausing, resuming, transferring) are read again every 15 seconds, at most five per tick, taken in turns so rows that never settle do not hide the others. A reload replaces the first page and keeps the rows of the pages loaded after it, so a refresh never collapses a list scrolled further down, and shows no spinner over a list already shown. A finished turn marks its row until the session is opened. Feed events, filter changes and "load more" are applied one at a time, so an event received while a page loads is applied after that page. A server without the feed is polled every 15 seconds. After the list stopped on an error, changing the filter starts it again; a change of the account's role or server starts a new list. A session screen shows the header (state, agent, model, effort, repositories, the failure code), the newest 100 events, older pages on request ("Load earlier events", never automatically), and the live stream after the newest sequence; events are merged by `seq`, each once and in order. A live `turn` moves the header between ready and working; since the transcript carries no pause, resume or failed pod, the header is read again every 30 seconds while the screen is visible, and "Working…" shows only while the session is working. Tool results join their call by id, runs of tool uses with no text between them fold into "N actions", subagent steps are indented, turn ends show their duration and steps, and status, errors, rejected or cancelled messages, permission requests (answered from a card, below), expiries, transfers and events the server replaced for size are system lines; unknown types are skipped. Agent text is Markdown (`multiplatform-markdown-renderer`); a link opens in the system browser only after the full URL is shown, and only `http` or `https`.

**Remote sessions.** From a server that announces `cloud.sessions.remote.v1`, the list asks for both kinds (`?kind=cloud&kind=remote`) and follows the feed with both, and a third filter appears under the state filter: All, Cloud or Remote; a filter change reloads the list without reopening the feed, which carries every kind and whose events of another kind (`data.kind`) are not read. Each card says where the session runs, "Cloud" or "Remote · <device>" (the device's name, "unnamed device", or "removed device" once it was removed), and a remote one shows its folder's name instead of repositories. A remote session paused because its device went quiet (`host_offline`) is marked "Offline" on its card, and its screen says so in plain words instead of the failure code. The session header shows "Remote · <device>"; its details add where it runs, the device's system, the folder and the permission mode. A remote session resumes only from its own device, which this app never is: its screen offers no Resume (the dock says "Paused on <device>. A message asks it to resume.", since a message with `wake` asks the host), and transfer is never offered for it (`canTransfer`). From an older server nothing changes: no `kind` is sent, the filter and the kind labels stay hidden.

**Acting on sessions.** A session screen has a composer: the message (1 to 32,000 characters, no control characters except newlines and tabs, checked before any request) shows at once as a pending bubble and goes with `wake: true` and its own id as `Idempotency-Key`. Its states: sending, sent (or "the session is waking up" when the receipt says `woke`), failed (a network failure, a `5xx` or a `429`: "Retry" sends it again with the same id, so the server returns the first receipt instead of queueing it twice) and refused (any other refusal, or a later `input` event that rejected or cancelled it, with its reason). A pending bubble disappears when the transcript's `message.user` event carries its input id. While a turn runs, "Interrupt" sends `POST …/interrupt` with a fresh idempotency key; `409 nothing_to_interrupt` only says nothing is running. The owner and administrators get "Pause" (ready, active or resuming sessions) and "Resume" (paused or pausing ones); the header shows the answer. The same menu has "End session" (red, behind a confirmation) for any session that has not ended: it sends `DELETE /cloud/sessions/{id}`, which ends the session and deletes its workspace, and the header then follows the server until it reads ended. An ended or transferring session takes no message.

**Sending files.** Behind `cloud.files.v1` the composer has a paperclip that attaches up to 5 files (photos, camera, documents, drag-and-drop on the desktop, and pasting files or a screenshot into the field: Ctrl/Cmd+V on the desktop, the keyboard's or the paste menu's image on Android, not yet on iOS) to the next message, each uploaded at once with its progress; the full behavior, limits and the storage requirement are in [files in the apps](cloud-conversations.md#files-in-the-apps).

**Sessions on an online device.** From a server that announces `cloud.sessions.remote.daemon.v1`, the new-session sheet starts with **Cloud | Online device**, on every app (phones and desktop); a team without a cloud profile opens on **Online device**. The device list is `GET /devices` (the member's own devices only, never another member's, an administrator's included) kept to those whose daemon is online (`daemon.online`); an offline device is never offered, and with none online the sheet says how to bring one online (`teamcode login`, then `teamcode service install`) with **Refresh**. A single device is chosen at once; this device comes first, marked "This device", then the others by name, and sentences name a device by its own name ("Start on Ada's Mac"). The folders are the device's published ones (`GET /devices/{id}/folders`, owner only), shown by name and label (`~/git/app`): no path is typed or sent, and with none the sheet says to add one on the device (`teamcode folders add PATH`). A single folder is chosen at once and names the session until the member types a name (a cleared name follows the folder again; another device without a chosen folder leaves it empty). The sheet then takes Claude Code or Codex, the first message (when announced), model and effort, and the permission mode, **Ask** or **Bypass** (a warning names the device for Bypass). The mode starts at the last launch's choice, here or "On this device" on the desktop, kept in the app's settings (`preferences.permissionMode`) once a session started with it: a launch refused or failed keeps the previous one. **Start on <device>** sends `POST /cloud/sessions {kind: remote, deviceId, folderId, agent, permissionMode, name, initialMessage}` without `directoryName` (the server takes the folder's name), under the form's idempotency key (kept while nothing sent changes, as for a cloud session), and opens the session. A device whose folders answer that it is offline or gone is dropped from the list without reading it again (its presence can lag), until Refresh; switching to Online device reads the list again. Refusals are worded from their code: `device_offline` (the list is read again), `folder_not_published` (the folders are read again), `device_not_found`, `remote_requires_login`, `device_target_unsupported`, `invalid_folder`; any other failure keeps its usual wording. The session screen and its card then say what the daemon does with it: while `phase = waiting_host` (created, or woken, and not picked up yet) a banner reads "Waiting for <device> to start the session", the card shows "Waiting for the device" and the phase reads "waiting for the device" instead of the code; a session the daemon refused (`failure.code = host_refused`) shows "Refused by the device" and "<device> refused to start this session:" followed by its reason in words (`folder_not_configured`, `folder_missing`, `folder_moved`, `folder_refused`, `folder_mismatch`, `agent_unsupported`, `host_failed`). The reason is the snake_case code the server puts in parentheses in the failure's message; nothing else of that message is shown, and a message without one says the device gave no reason.

**Answering the agent.** When the agent waits on a `permission.request` (an `AskUserQuestion` question, or a tool use matched by an `ask` rule; see [permission requests](cloud-conversations.md#permission-requests)), a card above the composer shows it. The open requests are derived from the merged transcript, so a request found in a history page and one received live are handled alike: a request is open until an `input` event with its `requestId` and status `consumed`, a `permission.expired` naming it, a finished `turn` (completed, interrupted or failed), or a `status` event (the agent process that asked exited or a new one started); none is shown while the session is not ready or active (pausing, paused, ended, transferring), since the server takes no answer then. With several open requests, the oldest is shown first (the agent asked them in that order and their deadlines pass in it), with "N more waiting after this one". A question shows one question at a time: its header, its text, its options with their descriptions (radio buttons for a single choice, checkboxes for `multiSelect`) and "Other" with a free text field, with the progress ("2/3") when there are several. "Next" is enabled once the question is answered (one option or a non-empty Other for a single choice, at least one of them for several) and "Back" returns to the previous question with its choice kept; on the last question, "Send" sends every answer in one `POST …/permissions` with `behavior: allow`: an option by index, Other as `text`. The API takes options or a text per question, so Other is exclusive in a single choice, and in a multi-select question with options and Other both chosen the answer goes as one `text`, the chosen labels in option order then the other text joined with `, `, which is what Claude Code receives when the runner joins labels itself. Texts are trimmed and checked like the server (1 to 4,000 characters, no control characters except newlines and tabs) before any request; a repeated question text is shown and answered once (Claude Code keys answers by text). "Decline" sends `behavior: deny`. A tool use shows the tool name, its description and its input (indented JSON, scrolled in its own box) with "Allow" and "Deny"; they are shown to everyone, and a `403 permission_answer_denied` (only the owner or an administrator decides a tool use) is a notice. A request whose input was left out of the event (`inputTruncated`, or no readable input) shows its preview and can only be declined or denied. Every text in the card is the agent's and is plain text, never Markdown. Each answer draws an idempotency key kept with that exact answer: a network failure, a timeout, a `5xx` or a `429` shows "Not sent" with "Retry", which sends the same body under the same key, and any edit drops the key so a changed answer gets a new one. A `202` shows "Answer sent, waiting for the agent" until the request closes; a later `input` event that rejected or cancelled that answer (the request stays open, e.g. `agent_unavailable`) brings the card back to editing with a notice. A `409` (answered by someone else, expired, ended, or `nothing_to_answer`) hides the card with a notice; a `400` keeps the draft with a notice. Answers go only to a server announcing `cloud.permissions.v1` (the only one that relays requests). "New session" lists the member's profiles (`GET /cloud/profiles`), takes a name (1 to 120 characters), optional model and effort, and a first message only when the server announces `cloud.sessions.initial-message.v1` (otherwise the field is hidden and a message is never sent). The form draws one idempotency key and keeps it while its fields are unchanged, so a retry after a network failure returns the session the first attempt created; editing a field draws a new key. The new session opens at once.

**Transfers.** On a server that announces `cloud.transfer.v1`, a cloud session's "…" menu has "Transfer…" for its owner and administrators while the session can change owner (ready, working, pausing, paused or resuming; never a remote session, one being created or prepared, an ended one or one already transferring). The recipient is picked from a searchable list (by username or ID, with initials and an administrator mark): `GET /cloud/transfer-recipients` on a server with `cloud.transfer.recipients.v1`, for members and administrators alike; on an older server, administrators get `GET /members` (disabled members and those who have not set their password shown but not selectable) and members type a member ID. An administrator transfers at once, optionally resuming the session for the recipient and pausing at once instead of letting the running turn finish (`resume`, `force`); a member sends an offer, without those options. The form draws one `Idempotency-Key` and keeps it while what it sends is unchanged, so a retry after a network failure replays the first transfer. The Sessions tab's title has a Transfers button opening the member's transfers to them and from them (`GET /cloud/transfers?direction=incoming|outgoing`, 50 per page, keyset cursor): the state, both members (names from one request, the recipients' list or an administrator's member list; IDs for members who left it, and "you"), the offer's expiry and why a transfer failed; the recipient (or an administrator) accepts or declines an offer, its owner withdraws it, an administrator also cancels an accepted transfer before the owner change. Every refusal is worded from its code (`transfer_pending`, `session_preparing`, `session_not_running`, `transfer_disabled`, `transfer_expired`, ...), and `422 recipient_ineligible` names each failed check of the recipient (profile, access policy, model or effort, allowance, session limit): the typed client keeps those problem codes, checked against the error-code alphabet, and nothing else of the message. A decision refused because the transfer changed meanwhile reads the list again. The transcript's `transfer` event already reads "The session changed owner".

**Streams.** Both streams are open only while their screen is visible (Android and iOS lifecycle `STARTED`, the desktop window shown), closed in the background, and resumed from the last sequence on return. A stream that closes, a network failure, `408`, `429` or `5xx` reconnects after 2 s, doubling up to 30 s, each delay shortened by up to a fifth at random; the count restarts when an event arrives or after a connection that stayed open at least 30 s (a connection accepted then dropped at once keeps backing off), and a `429` waits at least its `Retry-After` (at most 5 minutes). `401` checks the account once (`GET /auth/me`, which signs it out only if refused again) and stops; `404` says the session is gone (the server hides what a member may not read behind `404`), and a `403` is shown as a refusal of the action; `denied` (which the server also sends when the token expired) checks the account the same way and offers a retry; an unreadable event stops (a reconnection would replay it). Nothing is written to disk: the transcript lives in memory while its screen exists.

**Subscription accounts.** The Account tab's Team section opens Subscription accounts, for the active signed-in account: the pool (`GET /accounts`, administrators only; a member is told only administrators see it) and "Add a subscription account", which does what `teamcode accounts add` does, with the same shared code from the typed client (`AccountType`, `OAuthSignIn`, `accountEnrollmentAccess`). The screen first asks whether the member may add accounts (`GET /policy/account-enrollment` on a server that announces `accounts.enrollment-policy.v1`, the member's role otherwise) and, when not, shows why instead of the button; the check is asked again before every sign-in. The member then picks the kind of account in the CLI's order: Anthropic subscription, Codex subscription, and the Anthropic API key shown disabled ("Not available yet": the pool holds subscription sign-ins only). The app draws the PKCE verifier, the state and the enrollment operation id from the platform's secure random source (`SecureRandom`, `SecRandomCopyBytes` on iOS), opens the provider's page in the system browser (once, with "Open the sign-in page again"), and takes the pasted code (Claude's `code#state`, or Codex's `localhost:1455` callback URL) in a hidden field; no custom redirect is registered. It exchanges the code with the provider from the device, without any TeamCode credential, then sends the credentials with `POST /accounts` (`freshSignIn`), and the list is read again. A paste that is not the code can be corrected with the same attempt; another state, a code the provider refused or used, or a server refusal (`account_enrollment_forbidden`, `account_in_use`, in TeamCode's words) spends it, and "Start again" draws a new one. The pasted code and the tokens are never logged, shown or kept beyond the screen, and no provider message is shown.

**GitHub link.** The Account tab's GitHub section opens the member's GitHub link for the active signed-in account, with the same typed client calls and routes as `teamcode github status|link|unlink` (`GET` and `DELETE /api/v1/github/link`, `POST /github/link/device`, `POST /github/link/device/{id}`; see [cloud sessions](cloud-sessions.md#github-access)); nothing is added to the server and the app never sees a GitHub token. The screen reads the capability `github.link.v1` first (a server without it is told so, as the CLI does) and shows the GitHub login that is linked, "must be renewed" when GitHub refused the stored refresh token (`reconnect_required`), or that nothing is linked, and, while an administrator has not saved the team's GitHub App, why linking is unavailable. **Link GitHub** starts the device flow on the server, then, as the subscription sign-in does, once per attempt: copies the user code to the clipboard and opens GitHub's verification page in the system browser; the code is also shown large, with "Copy the code" and "Open GitHub again". The member pastes the code on github.com and authorizes. The app polls the server at the interval GitHub asked for (never faster than 1 s nor slower than 60 s, slowed when the server says so, as the CLI does), waits out two network failures in a row (a third ends the attempt), and ends on `linked` (the screen shows the login), `expired` or `denied` (said in words; the Link button starts a new attempt). Cancel stops the polling. A `409` on start (`github_app_not_configured`, `github_device_flow_disabled`) is worded and the link is read again. **Unlink** removes the link and revokes its token at GitHub, as `teamcode github unlink` does. Interactive logins only, as on the server: a service key cannot link.

**Artifacts.** The Artifacts tab is the gallery (`artifacts.v1`): the member's own artifacts or everything they can read in the team (`GET /artifacts?scope=mine|team`, 50 per page, keyset cursor, the next page loaded near the end of the list), with a search over the titles and descriptions already loaded. A session screen's Artifacts button pushes the artifacts that cloud session published (`?session=<id>`). A card shows the title, description, owner, access, version and age. The viewer has a native bar (title, version picker, copy link, open in the browser, where access is managed) and, on iOS and Android (`artifacts.tickets.v1`), the content in a web view: the app asks `POST /artifacts/{id}/tickets` for the version shown, refuses a content URL that is not on the account's own origin under `/artifact/<id>/<ticket>/`, and loads it. The web view keeps no cookie or storage (`WKWebsiteDataStore.nonPersistent()`; cookies off, DOM storage off, cache cleared on close on Android), has no JavaScript bridge and no file or content access, refuses mixed content, geolocation, camera and microphone, and lets the main frame navigate only under the ticket's directory (no `..`, no escaped dot or slash); a link elsewhere that the member followed, or a pop-up, is offered to the browser after its URL is shown, and any other scheme is refused. The content's sandbox does not depend on the app: the server sends `Content-Security-Policy: sandbox` with every file. When a page answers `404`, the app asks for a ticket again: a different one (the old one expired, or is only older than the server's 10-minute rounding of expiries) loads that same page again under it, in a new web view; the same one (a ticket asked again soon comes back unchanged) means a link led to a file the version lacks, which the screen says with "Back to the start". A crashed page (renderer or content process) is loaded again, at most once a minute. While the viewer is visible, the artifact is read again every 30 seconds and a newer version is offered ("Version N was published. Show it"), never loaded by itself. The version picker asks for a ticket fixed on the chosen version.

**Links.** Universal Links and App Links need each server's domain in the app at build time, which a self-hosted server cannot have, so the app registers the `teamcode` scheme: the viewer page's **Open in app** link is `teamcode://open?url=<the viewer URL>`. Android also takes a link shared as text (`ACTION_SEND`), and every platform has an "Open a link" field in the gallery (the clipboard is never read by itself). A link resolves only to `<server>/artifact/<id>` with an optional `?v=<version>`; its origin must equal an account's exactly (the active account first when several share it). A link to a server with no account shows that origin in full and offers to sign in to it as a new server. A link never carries a secret, so the worst a crafted one does is offer a sign-in to a server whose origin is shown.

**Desktop.** Artifacts open in the browser on the viewer page; there is no embedded browser, and no ticket is asked for.

### Desktop: sessions on this device

**The CLI's account.** The app reads the CLI's `config.json` with the same `:config` code as the CLI (`$XDG_CONFIG_HOME/teamcode/config.json`, else `~/.config/teamcode/config.json`). Its sign-in is the account `cli`, marked **CLI** in the account switcher and the Account tab, which also shows the file's path; its token is never copied to the keyring, and the other accounts stay in the keyring as before. The app checks the file's modification time, size and identity every 2 s: a `teamcode login` in a terminal adds or describes the account again (`GET /auth/me`, the capabilities and this device's name, with the CLI's token), `teamcode logout` removes it. A token is handed out only for the server the account describes, so a login to another server never sends its token to the previous one. Signing the CLI account out in the app is `teamcode logout`, and the Account tab says so before: the session is revoked, then the file is deleted under `config.lock` only if it still holds that session. A sign-in again in the app replaces the file's session the same way `teamcode login` does. Without `config.json`, the sign-in form offers **Also use for the TeamCode CLI** (on by default): the session is written to `config.json` (owner-only, by atomic rename, under `config.lock`) and the account becomes the CLI's. A member already listed on the same server is merged into the CLI account, and its own login session revoked. The app and the CLI share `installation-id`, so the server lists one device for both (an app that had its own id publishes it when the CLI has none yet). The server's `401` is what signs the CLI account out: `config.json` has no expiry.

**Environment.** An app opened from the Finder or a launcher inherits neither the shell's `PATH` nor its `XDG_CONFIG_HOME`. When `XDG_CONFIG_HOME` is not set and the app was not started from a terminal, it reads both once from a login shell (`$SHELL -l -c`, 3 s at most, only the two values between markers), and gives them back to every CLI it runs, so both read the same file. `--config-path PATH` gives the file directly (what `teamcode ui` will pass).

**On this device.** On the desktop, **+** first asks where the session runs: **On this device** (a folder) or **In the cloud** (the existing sheet: a profile, or one of the member's online devices (above) when the server offers it). The app needs, in this order: the server's `cloud.sessions.remote.v1`; a CLI, found at `~/.local/bin/teamcode`, the managed launcher (`~/Library/Application Support/TeamCode/bin`, `~/.local/share/teamcode/bin`, `%LOCALAPPDATA%\TeamCode\bin`, or under `XDG_DATA_HOME`), then the `PATH`, answering `teamcode version`; a CLI of the app's minor version or newer; and the CLI's account, since the session runs with the CLI's sign-in. Each missing step is explained with the command to run (the installer pinned to the app's version, or `teamcode update`) and a **Check again** button. A missing CLI also gets **Install the TeamCode CLI** (see below). The form takes a folder (the system's picker), Claude Code or Codex, a name (the folder's by default), a first message, the model and effort, and **Act without asking** (off; on, it warns that the agent changes files and runs commands without asking). The app runs `teamcode remote start DIRECTORY --agent … --name … --json --detach`, each value its own argument and never through a shell, reads the created session's id from the JSON, and opens the session screen. The first message is not on the command line, where other processes could read it: it is sent through the server once the session exists, and a failure says so before the session opens. A refusal shows the CLI's own sentence (a home or system folder, a folder that does not exist).

**Installing the CLI.** On a release build, **Install the TeamCode CLI** downloads the install script of the app's own version (`https://github.com/nathanfallet/teamcode/releases/download/<version>/install.sh`, or `install.ps1` on Windows), never the latest alias, through the credential-free release transport (HTTPS GitHub hosts only, bounded size and time). It runs the script only when its SHA-256 is the one compiled into the app by the release pipeline (`-PteamcodeInstallShSha256`, `-PteamcodeInstallPs1Sha256`); a build without them (development, a fork) offers only the command. The script is written to a private temporary folder and run as `/bin/sh install.sh`, or `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File install.ps1`, without a shell parsing anything, with the app's `PATH` and `XDG_CONFIG_HOME`, so the CLI it installs reads the same `config.json`. The script then makes its own checks (signed manifest, hashes, native installer, [bootstrap](bootstrap.md)); its last lines show in the sheet, a non-zero exit is said, and the app checks again at the end. A script still running after 15 minutes is left to finish, never signalled.

**`teamcode ui [DIRECTORY]`.** The CLI opens the app, installing the CLI's own version first when no app of that version or newer is installed (an older one is updated after a question, or `--yes`). It looks in `~/Applications/TeamCode.app` then `/Applications/TeamCode.app` (macOS), `%LOCALAPPDATA%\TeamCode App` (Windows), `$XDG_DATA_HOME/teamcode-desktop/current` (`~/.local/share/teamcode-desktop/current`) then `/opt/teamcode` (Linux), and reads the app's version from `teamcode-desktop-version` in its resources, written by the build. To install, it downloads `desktop-manifest.json` and `desktop-manifest.sig` of the CLI's version and authenticates them with the publisher keys compiled into the CLI (those of `teamcode verify-release`); the manifest must name that version and carry `product: desktop`, so a CLI manifest cannot stand in for it. The package of this system is downloaded to a private temporary folder (at most 512 MiB, 15 minutes), and its exact length and SHA-256 are checked before anything opens it. macOS: the zipped `.app` is extracted next to `~/Applications/TeamCode.app` and must pass `codesign --verify --deep --strict` against a Developer ID requirement naming the Team ID compiled into the CLI (`-PteamcodeMacosTeamId`; without it the CLI does not install on macOS and points at the release page), then it replaces the previous app. Windows: `msiexec /i … /qb /norestart MSIINSTALLPERUSER=1` installs the per-user package (no administrator rights). Linux: the `.tar.gz` becomes `teamcode-desktop/<version>`, `current` is relinked atomically, the previous version is kept until the next update and a menu entry `applications/teamcode-desktop.desktop` is written. Each checks that the installed app reports the manifest's version, and a failure leaves the previous app in place. The app is then opened (`open … --args` on macOS, its launcher detached elsewhere, output in `desktop.log` beside `config.json`) with `--config-path` (the CLI's `config.json`) and, for a DIRECTORY that remote sessions accept, `--directory`, which opens **New session on this device** on that folder with the CLI's account. `--no-launch` only installs; `--bundle DIR` installs from a directory holding the manifest, its signature and the package (release acceptance). `--restart-app PID` (with `--yes`) is the update banner's step: once the process PID has quit, it installs if needed and reopens the app, see **Update banner** below. An app already running is not restarted: on macOS `open` brings the running one forward, without the folder; on Windows and Linux a second instance starts.

**Update banner.** The desktop app (macOS, Windows, Linux) shows **Update available: TeamCode X** at the top of the main screen's content (the content panel in a wide window, above the tabs' content in a narrow one) when a newer release exists for the CLI or the app; the iOS and Android apps, iPad included in its wide or split layout, never do. The test is the platform, not the window's size: only the desktop's module binds the `AppUpdater` the banner needs. The mobile apps ship through their own store release track, separate from the CLI and desktop releases, so the CLI's version never drives an update prompt there. The app never downloads or verifies a release itself; every step runs through the installed CLI, so the release client, the signature checks and the installers are the CLI's own:
- **Check.** `teamcode update --check --json` (the signed check of `update --check`, as one JSON line: `currentVersion`, `latestVersion`, `updateAvailable`, `sourceCommit`, `keyId`); for a CLI older than `--json`, the text of `update --check`. It runs at startup, then every 6 hours, and never more than once an hour across restarts (the last result is kept meanwhile): 3 of GitHub's 60 unauthenticated requests per hour at most. A failed check (offline, rate limited, no CLI) shows nothing. The banner offers the newer of the latest stable release and the CLI's own version; a development build of the app (`-SNAPSHOT`) offers nothing. **Not now** hides it for that version only; a newer one shows again.
- **Update.** One click runs `teamcode update` (running agent sessions keep their version, and the local service restarts when they end, see [updating while agent sessions run](distribution.md#updating-while-agent-sessions-run)), then `teamcode ui --yes --restart-app PID` with the app's own process id, showing their last lines. That command installs nothing itself: it starts the CLI again detached (`teamcode ui --yes --wait-for PID`, output in `desktop.log`) and the app quits. The detached step waits for the app to quit (2 minutes at most), installs the app of the CLI's new version with the checks of `teamcode ui` below (signed desktop manifest, SHA-256, on macOS `codesign` against the Developer ID; nothing is bypassed and no quarantine attribute is touched; on Windows the per-user installer shows its progress window) and opens it. Never under the running app: Windows keeps its files open, and a running JVM still loads classes and native libraries from its bundle. If that installation fails, the app still installed is reopened with `--update-error`, and its banner says why; with no app left to reopen, the reason is in `desktop.log`. Sessions on this device are hosted by the daemon and keep running across the restart.
- **Failures.** Each refusal is the CLI's own sentence: no CLI (with the install command), a CLI that is not a managed installation (`release_not_managed`: reinstall with the install script once), a network or signature failure, a CLI too old for `--restart-app` (run `teamcode ui --yes` in a terminal). **Try again** reruns both steps; nothing is half-applied, since a failed step leaves the previous CLI or app in place.

**Hosts and wake.** The app starts no host and watches none: the device's [daemon](devices.md#device-daemon) does. With the daemon online (installed at login by `install.sh`, `teamcode update` and `teamcode ui`), `teamcode remote start` goes through it, so a session started here is the daemon's: it starts the host, starts a host that exits again, replaces one that stopped answering once the server paused its session (`host_offline`), at most 3 starts in 10 minutes in all, and starts it again when a message wakes the session, whether the app is open or not. Past that limit the session is refused (`host_failed`), which the session and its card show as refused by the device; the app sends no notification. A session the CLI hosts itself (the daemon stopped or turned off with `--no-service`, or a session started before the daemon) is woken by `teamcode attach` on this device, which also hosts a daemon's session while its daemon is offline, or by `teamcode remote resume SESSION`. Earlier versions of the app did this themselves while they ran, and still do beside a newer CLI: on a daemon's session, `remote resume` only puts it back in the queue while the daemon is online; if the daemon is seen offline at that moment, the CLI hosts it and the daemon's host, if any, is fenced by the newer epoch, which may interrupt a turn.

**Menu bar.** Closing the window keeps the app in the menu bar (the notification area on Windows and Linux): **Open TeamCode**, and **Quit TeamCode (sessions on this device keep running)**. Without a tray (some Linux desktops), closing the window quits. On macOS, the Dock icon brings the window back.

### Language

The app is available in English (the default) and French. Every text lives in `companion/src/commonMain/composeResources/values/strings.xml` (English) and `values-fr/strings.xml` (French), read with `stringResource`, `pluralStringResource` or `getString`; no screen carries a literal sentence. The app follows the system language (the JVM's default locale on the desktop, the device language on Android and iOS) and falls back to English for any other. French addresses the member as `tu`; `session`, `workspace`, `token`, `device flow` and product, command and flag names stay as the CLI words them, and the CLI's own explanations (a folder refused by `teamcode remote start`, the install script's output) are shown as the CLI wrote them.

Failures are worded where they are shown: the domain throws typed errors (`CompanionException`, `InvalidInput`) whose English `message` stays for logs and tests, and `userMessage()` words them from the resources. Event names sent to analytics, if any, are never translated.

To add a language `xx`: translate `values/strings.xml` into `values-xx/strings.xml` (every key, the same `%1$s` placeholders, a bare apostrophe, never `\'`; a plural needs its `other` form), then declare it to the systems: a `<locale android:name="xx"/>` in `companion-android/src/main/res/xml/locales_config.xml` (the manifest already references it; this enables Android 13+'s per-app language picker), the language in `CFBundleLocalizations` of `companion-ios/TeamCode/Info.plist` and in `knownRegions` of `companion-ios/TeamCode.xcodeproj/project.pbxproj` (otherwise iOS treats the app as English-only and shows no language setting). `LocalizationTest` (`:companion:jvmTest`) fails when a key or a placeholder is missing from a language, or when a declaration is missing or extra. The iOS permission prompts (`NSCameraUsageDescription` and the other `Info.plist` usage descriptions) are not localized yet.

## Distribution

Store builds are made and uploaded from a maintainer's Mac with fastlane (`Gemfile`, `fastlane/Fastfile`); there is no publication job yet. Nothing in the repository holds a key, a certificate or a password: each lane reads them from files next to the Fastfile and from the environment, all ignored by git.

| Lane | Does | Needs (local only) |
| --- | --- | --- |
| `bundle exec fastlane ios beta version:X.Y.Z` | Archives `companion-ios/TeamCode.xcodeproj` (shared scheme `TeamCode`, Release) with automatic signing through the App Store Connect key (Xcode cloud signing, no certificate in the keychain), then uploads to TestFlight without submitting | `fastlane/api_key.json`, `fastlane/key.p8` |
| `bundle exec fastlane android beta version:X.Y.Z` | `:companion-android:bundleRelease --no-daemon`, signed with the upload key, then uploads to Play's internal track | `fastlane/play-key.json`, `fastlane/keystore.jks`, `SIGNING_STORE_PASSWORD`, `SIGNING_KEY_ALIAS`, `SIGNING_KEY_PASSWORD` |

Only builds are uploaded. Store listings, screenshots and descriptions are kept in App Store Connect and the Play Console, never in this repository (`fastlane/metadata/` and `fastlane/screenshots/` are ignored), and no lane submits for review or releases. App Review needs a demo account on a demo server, entered in App Store Connect only.

**Versions.** The app carries the TeamCode version given to the lane (`MARKETING_VERSION`, `versionName`, and the shared code's `BuildInfo.VERSION` through `teamcodeVersion`). The build number (`CFBundleVersion`, `versionCode`) is `(major × 1,000,000 + minor × 1,000 + patch) × 100 + n`, where `n` counts the uploads of that version (read from TestFlight and the Play tracks, at most 99). Without the lane, Gradle builds use `n = 0`, and the Xcode project's `CURRENT_PROJECT_VERSION` stays 1.

**Android release signing.** `companion-android` signs its release build only when `fastlane/keystore.jks` exists, with the passwords from `SIGNING_*`; otherwise the release build is unsigned, and the lane refuses to run.

**iOS privacy.** `PrivacyInfo.xcprivacy` declares no tracking and no collected data, plus the two required-reason APIs the app uses: UserDefaults (`CA92.1`, the app's own settings) and system boot time (`35F9.1`, elapsed time for timeouts and reconnection delays). There are no analytics.

**Desktop.** `:companion-desktop:packageDmg`, `packageMsi`, `packageDeb` and `packageRpm` build on the matching host, and every packaging task refuses a 0.x version: the packages carry TeamCode's own version (without a pre-release suffix, which installers do not take). A local `.app` is signed with a Developer ID when the Mac provides `TEAMCODE_MACOS_SIGNING_IDENTITY` (the identity's name without "Developer ID Application: ", optionally `TEAMCODE_MACOS_SIGNING_KEYCHAIN`), and notarized with `TEAMCODE_NOTARIZATION_APPLE_ID`, `TEAMCODE_NOTARIZATION_PASSWORD` (an app-specific password) and `TEAMCODE_NOTARIZATION_TEAM_ID`; without them it is unsigned. Windows installers are not signed (no paid signing service; SmartScreen warns). The Windows package installs for the current user in `%LOCALAPPDATA%\TeamCode App` (`perUserInstall`, a fixed upgrade code), where `teamcode ui` looks.

**Desktop release pipeline** (`.github/workflows/build.yml`, on version tags and `full_validation` only). After `signed_bundle` generates `install.sh` and `install.ps1`, the `desktop` job builds the app on each of the five targets with their SHA-256 (`-PteamcodeInstallShSha256`, `-PteamcodeInstallPs1Sha256`), so "Install the TeamCode CLI" runs only those exact scripts. On macOS it imports the Developer ID into a temporary keychain, checks its Team ID, signs the app (hardened runtime, the JIT entitlements the JVM needs), notarizes it with `notarytool` and an App Store Connect API key, staples it, checks it with `codesign`, `spctl` and `stapler`, then zips it with `ditto`; the `.dmg` is signed, notarized and stapled too. `scripts/release-desktop.py` stages each package (format and layout checked), `desktop_manifest` assembles `desktop-manifest.json` (`product: desktop`, one package per target) and signs it with the publisher key, like the CLI's manifest. On the five release hosts, `signed_installation` runs `scripts/smoke-desktop-install.py`: the signed CLI of the same release refuses a package with one modified byte, installs the real one with `teamcode ui --bundle … --yes --no-launch` (the CLI, run from the bundle, reports that it is not a managed installation and leaves the local service alone), finds it at its version (and on macOS `codesign`, `spctl` and `stapler validate` accept it), and installs nothing on a second run. Publication attaches the desktop packages, the `.dmg`, `.deb` and `.rpm`, and the signed manifest, lists every file in `SHA256SUMS`, and adds the desktop downloads to the release notes. The CLI is compiled with the Team ID (`-PteamcodeMacosTeamId`, from the repository variable `TEAMCODE_MACOS_TEAM_ID`).

Repository settings it reads: secrets `TEAMCODE_MACOS_CERTIFICATE_P12` (base64 of the Developer ID Application certificate and key), `TEAMCODE_MACOS_CERTIFICATE_PASSWORD`, `TEAMCODE_NOTARY_KEY` (the `.p8` contents), `TEAMCODE_NOTARY_KEY_ID`, `TEAMCODE_NOTARY_ISSUER_ID`, and the variable `TEAMCODE_MACOS_TEAM_ID`. A tag or a publication fails unless all of them are set. A validation run without any of them builds an unsigned macOS app and checks that `teamcode ui` refuses it.
